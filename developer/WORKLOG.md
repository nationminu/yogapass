## 2026-09-12 · P3 · 검토 (디자인 산출물 R1 — 기술 관점)
- 요청: 오케스트레이터가 P3 디자인 산출물 v0.1(디자인 시스템, 페이지 디자인 명세, 목업 4종)의 **교차 검토 R1**을 기술 관점으로 요청했다. 관점은 7가지였다 — 구현 가능성(토큰·CSS 변수 블록·구간 오버라이드·`prefers-reduced-motion`), 컴포넌트 재사용성(1차 30종 → 2차 39화면, 확장 예고 27종이 1차 토큰을 깨는가), 성능(Lighthouse 90+ 대비 폰트·이미지·CLS), 접근성 구현 가능성, designer가 확인 요청한 **z-index 쌓임 순서(D-2)**, **1차 구현 착수 준비도**, 목업 HTML과 실제 구현(시맨틱·SEO·JS 비활성)의 정합. **문서·목업 읽기만 · 명령 실행·코드 작성·웹 검색 금지 · 디자인 산출물 직접 수정 금지 · 2차 상세와 공수 재산정은 범위 밖 · PM 방침 "최대한 빨리, Must는 게이트를 막아야 할 사안에만"**.
- 수행:
  - 디자인 시스템 986행 전문, 페이지 디자인 408행 전문, 목업 4종(scr-001·002·003·008)의 토큰 블록·마크업 구조를 읽었다. 대조 기준으로 `planning/02_requirements.md` §3.0(G-0~G-13)·§5.0(M-1~M-8)·§5.1, `interviews/2026-09-12_infra-constraints.md` v0.4, `design/assets/SOURCES.md`를 확인했다.
  - **대비값을 표본 재계산해 designer 계산의 신뢰도를 먼저 확인했다.** sRGB 선형화 → `0.2126R+0.7152G+0.0722B` → `(L1+0.05)/(L2+0.05)`로 `#0B4F9E`(7.995), `#5A6B7D`(5.477), 오버레이 `rgba(10,37,64,.68)`의 백색 합성색(`#586B7D`, ≈5.50)을 직접 계산했고 세 건 모두 문서 값과 소수 둘째 자리까지 일치했다. 이후 §4.1의 27조합은 개별 재계산 대신 신뢰하기로 했다.
  - **CSS 변수 블록을 "복사해서 쓴다"는 전제로 읽었고 실제 결함 1건을 찾았다.** `:focus-visible` 규칙의 `border-radius: var(--radius-sm)`가 outline이 아니라 **요소 자체의 모서리를 바꾼다** — pill 칩 999px → 6px, 버튼 8px → 6px로 포커스 순간 모양이 변한다. 같은 규칙의 `:where()`(특이성 0)가 뒤에 오는 클래스 규칙에 덮일 수 있다는 점도 함께 적었다.
  - **변수 캐스케이드를 추적해 파생 문제 3건을 찾았다.** ① 헤더가 `min-height`인데 `--header-h`는 고정값이라 200% 확대·로고 폴백 시 `--anchor-offset`이 실제 높이를 따라가지 못해 앵커 진입 시 제목이 헤더 뒤로 숨는다(G-10). 문서가 고정 바에만 건 `ResizeObserver` 보정을 헤더에도 걸면 해결된다. ② 그 `ResizeObserver`가 `documentElement.style`(인라인)로 값을 넣으면 `≥1280px`의 `--fixed-bar-h: 0px`와 `max-height:420px` 블록을 **이긴다** → 해제 조건(`removeProperty`) 명시가 필요하다. ③ `max-height:420px`에서 헤더가 static이 되는데 `--anchor-offset`이 그대로라 420px 뷰포트의 약 20%가 앵커 여백이 된다.
  - **성능은 "1차 위험이 어디로 수렴하는가"로 좁혀 봤다.** 사진 0장·외부 도메인 요청 0건·인라인 SVG·지도 클릭 투 로드·`aspect-ratio` 고정·지도 대체 영역 로드 전후 동일 높이라 **CLS·LCP 유발 지점이 설계 단계에서 이미 제거돼 있다.** 남는 변수는 한글 웹폰트 하나뿐이라고 판단해 여기에 Should 하나를 집중했다(파일 구성 ⓐ/ⓑ/ⓒ 택일, `--fw-medium: 500` 실사용 여부, swap 폴백 메트릭 보정). "Variable 단일 파일이면 weight를 덜 써서 작아진다"는 문서의 전제가 사실과 다르다는 점도 적었다.
  - **z-index D-2는 동의로 답했다.** sticky 표 헤더가 사이트 헤더를 덮으면 안 되므로 10 < 20이 맞다. 다만 z-index는 같은 쌓임 맥락 안에서만 비교되므로 표 래퍼에 `transform`·`filter`·`opacity<1`·`will-change`·`contain: paint`·`isolation`이 붙으면 숫자 비교가 무의미해진다는 조건과, 2차 sticky 표 헤더의 `top`을 `var(--header-h)`로 잡아야 한다는 점을 Could로 남겼다.
  - **2차 확장 예고 27종이 1차 토큰을 깨지 않는 것을 확인했다**(신규 예약 토큰 5계열뿐, §1 토큰 값 변경 0건). 검산 중 `--week-col-min-w` 하한 120px이 1024px 실측에서 118.86px로 1.1px 모자란 것을 발견했으나 **1차 영향 0이라 Could**로만 남기고 2차 착수 시 재확인 항목으로 넘겼다.
  - **목업과 명세의 차이 2건**을 찾았다 — 목업 4개 전부에 skip link 마크업과 `<main id="main">`이 없다(CSS 규칙만 있음), CMP-005는 명세가 `<details>` 기반인데 목업은 `<button aria-expanded>`다. 둘 다 명세를 정본으로 보고 구현하겠다는 전제 확인 요청으로 처리했다(`<main tabindex="-1">`이 필요한 이유, `<summary>`에 `aria-expanded`를 수동 부착하면 중복이라는 근거 포함).
  - **Must를 0건으로 판정했다.** #1(포커스 radius)이 유일하게 "화면에 보이는 결함"이지만 한 줄 삭제로 끝나고 developer가 구현 시 흡수할 수 있어 게이트 차단 사유가 아니라고 봤다. PM 방침("Must는 게이트를 막아야 할 사안에만")에 맞춰, designer가 문서를 고치지 않고 "구현 시 developer가 제거한다"고 처리 결과만 적어도 해소되는 경로를 함께 제시했다.
  - 디자인 취향(색·여백·톤), 2차 39화면 상세, 공수·일정은 범위 밖으로 두고 지적하지 않았다.
- 산출물: `shared/reviews/P3_design-docs_developer_r1.md` (판정: **조건부 승인**, Must 0 · Should 9 · Could 5)
- 티켓·리뷰: 발행 티켓 없음. 디자인 산출물은 수정하지 않았다
- 이슈·다음 할 일:
  - **1차 기술 설계(P4-①) 착수 가능**하다고 판단했다. G3 승인 후 `developer/04_tech-design.md`를 작성한다.

  - 선택지별 공수를 추정했다(부록 A). A' +4~10작업일, B +17~24작업일. 현재 P4 구현 기간(약 4일)은 A·C안 분량이므로 "A' 기준 달성 가능" 평가는 근거가 부족하다 → Must. 대안으로 O-6(P3 기간에 서버 측 영역 선착수)과 단계 오픈을 제안했다.
  - 누락된 기술 리스크를 확인했다. 폼·API 악용, 메일 발신 도메인 인증과 기존 메일 레코드 충돌, 무료 요금제 약관(상업 이용 제한, 비활성 일시 중지), Windows 환경의 Safari 검증 경로, 운영 환경 준비와 TTL 조정 시점이다 → Should.
  - 무료 요금제 약관은 공개 문서로 사실을 확인했다. Vercel Hobby는 비상업 개인 용도로 한정되고, Supabase Free는 7일간 활동이 적으면 일시 중지된다.
  - §7은 "확정은 P4"라고 명시되어 있어 과도한 선결정은 아니라고 판단했다. 표현 완화만 Could로 제안했다.
