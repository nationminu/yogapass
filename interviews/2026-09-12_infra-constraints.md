# 인프라 전제 — 기존 호스팅과 컨테이너 구성

> **출처**: 2026-09-12 총괄 PM 지시
> 1. "호스팅은 이미 있다 검색하지말자"
> 2. "운영 docker-compose 환경으로 구성되어 있다"
> 3. "로컬환경도 compose 환경으로 컨테이너로 구성한다"

## 1. 확정된 전제

| 항목 | 내용 |
|---|---|
| 호스팅 | **이미 보유**. 신규 서비스 선정·요금제 비교는 하지 않는다 |
| 운영 환경 | **docker-compose 기반 컨테이너 환경**이 이미 구성되어 있다 |
| 로컬 개발 환경 | **docker-compose로 동일하게 구성**한다 (개발·운영 환경 일치) |
| 서버 (I-1) | **서버 호스팅 · 리눅스 · 8코어 16GB** |
| 데이터베이스 (I-3) | **오픈소스 DB 사용.** MySQL(MariaDB)·PostgreSQL 경험 보유 → 권고는 §4 |
| 메일 발송 (I-5) | **SMTP 사용 예정** |
| 운영 주체 (I-7) | **운영자 있음** — 백업·모니터링·패치 수행 주체 확보 |
| HTTPS·프록시 (I-4) | **로컬은 http 직접 접근. 운영은 앞단에 nginx를 두고 nginx에서 HTTPS 처리.** 도메인은 **미정** |
| 스테이징 (I-8) | **운영팀이 진행** — 제작 범위 밖, 환경 제공 주체 확보 |
| 로고 (T-B) | **디자인팀이 임시 로고를 제작**해 진행. 고객 원본 확보 시 교체 |

## 2. 이 전제가 바꾸는 것

### 무효가 된 분석
- `shared/reviews/CR-001_impact_developer.md` §2의 **호스팅 후보 비교(Cloudflare·Vercel·Supabase·VPS)와 월 비용 산정은 적용되지 않는다.** 보유 호스팅에서 컨테이너로 운영한다.
- 계획서 v1.0 §7의 "호스팅 후보", 인터뷰의 "월 5만 원 예산" 항목도 같은 이유로 재검토 대상이다.
- "Vercel Hobby 상업 사용 금지", "Supabase 서울 리전" 같은 제약은 더 이상 판단 근거가 아니다.

### 새로 생기는 것
| 항목 | 내용 |
|---|---|
| 구성 방식 | 애플리케이션·데이터베이스·리버스 프록시 등을 컨테이너로 묶어 compose로 운영 |
| 개발 환경 | 로컬도 같은 compose 구성 → "내 PC에서는 되는데" 문제가 줄고, 검증 환경 재현이 쉬워진다 |
| 운영 책임 | 관리형 서비스가 아니므로 **백업·보안 패치·모니터링·인증서 갱신을 직접** 해야 한다 |
| 배포 방식 | 이미지 빌드 → 배포 절차를 정해야 한다 (수동 compose 명령 / CI 자동화) |

### 공수 영향 (developer 재산정 필요)
- 관리형 인증·DB 서비스를 쓰지 않으면 **인증·세션·메일 발송을 직접 구성**해야 한다. 라이브러리로 상당 부분 대체되지만 설정·검증 작업이 늘어날 수 있다.
- 반대로 **기반·인프라 항목(2~2.5작업일)** 중 계정 생성·서비스 연동 부분은 줄어든다.
- 로컬 compose 구성 자체가 P4 초기 작업으로 들어간다 (0.5~1작업일 예상).
- → `CR-001_impact_developer.md`의 공수표를 이 전제로 다시 계산해야 한다.

## 4. 데이터베이스 권고 (I-3)

**결론: PostgreSQL을 권고한다. MariaDB(MySQL)도 충분히 가능하다.**

두 가지 모두 경험이 있다고 하셨으므로, 차이는 "익숙함"이 아니라 **이 프로젝트의 규칙을 DB가 얼마나 지켜 주는가**에서 갈린다.

| 우리 규칙 | PostgreSQL | MariaDB / MySQL |
|---|---|---|
| **슬롯 시간 겹침 금지** (공간 1개 — B-15) | 범위 타입 + 배제 제약으로 **DB가 직접 막는다**. 코드 실수와 무관하게 겹친 슬롯이 저장될 수 없다 | 제약 기능이 없어 **애플리케이션에서 검사 + 트랜잭션 잠금**으로 막아야 한다 |
| **중복 상담 신청 차단** (일자+시간+연락처 동일, 취소 건 제외 — C-6) | 조건부 유니크 인덱스로 **한 줄에 해결** | 조건부 인덱스가 없어 생성 컬럼을 만들어 우회해야 한다 |
| **정원 초과 방지** (동시 예약) | 트랜잭션 + 행 잠금으로 처리 가능 | 동일하게 가능 (InnoDB) |
| 예약번호 무작위 생성 | 애플리케이션에서 생성 (동일) | 동일 |
| 운영 편의 | 컨테이너 이미지·백업 도구 성숙 | 동일하게 성숙, 국내 자료가 더 많음 |

- **권고 이유**: 예약 시스템에서 가장 위험한 두 가지(슬롯 겹침, 중복 접수)를 **데이터베이스 차원에서 차단**할 수 있다. 애플리케이션 코드에만 의존하면 동시 요청·예외 경로에서 뚫릴 수 있고, 그 사고는 고객 신뢰와 직결된다.
- **MariaDB를 골라도 되는 경우**: 운영자가 MySQL 계열 운영·백업에 이미 익숙하고 그 절차를 그대로 쓰고 싶을 때. 이 경우 겹침·중복 방지를 애플리케이션에서 엄격히 구현하고, P5에서 동시 요청 테스트를 반드시 포함한다 (**+0.5~1 작업일**).
- 어느 쪽이든 컨테이너로 올리고 **데이터 볼륨·백업 경로·백업 주기**를 배포 계획에 명시한다.
- 최종 확정은 **P4 기술 설계**에서 developer가 한다. 이 문서는 권고다.

## 6. 2026-09-12 추가 답변 반영

### 6.1 HTTPS·프록시 구조 (I-4 해결)

| 환경 | 구성 |
|---|---|
| 로컬 | **http로 직접 접근**. 인증서 없음 |
| 운영 | **앞단 nginx → 애플리케이션**. nginx가 TLS 종료(HTTPS 처리) 담당 |

- compose 구성은 **nginx + 애플리케이션 + 데이터베이스**가 기본 골격이 된다.
- 로컬이 http이므로 **HTTPS 전용 동작(보안 쿠키 등)은 로컬에서 재현되지 않는다.** 관련 요구사항은 운영·스테이징에서 확인해야 한다 → P4 기술 설계와 P5 검증 계획에 반영 필요.
- **도메인 미정 (I-9 신규)**: 1차 오픈(2026-11-06)에 도메인과 인증서가 필요하다. 발급·DNS 전파를 고려해 **늦어도 오픈 1주 전(10-30)까지 확정**되어야 한다. 미정 상태로 오픈하려면 임시 주소로 여는 방식을 PM이 결정해야 한다.

### 6.2 스테이징 (I-8 해결)
- **운영팀이 준비한다.** 제작 범위 밖이다.
- 백업 복구 리허설과 배포 리허설을 이 환경에서 수행한다. 필요 시점은 1차 배포 준비(10월 말) 전이다.

### 6.3 임시 로고 (T-B 처리 방침)
- 고객 로고 원본 확보 전까지 **디자인팀이 임시 로고를 만들어** 진행한다. 디자인 시안·목업·1차 오픈까지 이 임시 로고를 쓴다.
- 교체 시점에 브랜드 색상이 바뀌면 디자인 토큰 조정이 생길 수 있다. 영향 범위를 P3에서 명시한다.
- 추가 공수 **0.25~0.5작업일** 예상 (designer).

### 6.4 메일 발신 인증 (I-5-a) — 도메인 확정 후 처리
- SPF·DKIM은 **"이 도메인에서 나간 메일이 진짜인지"를 받는 쪽 메일 서버가 확인하는 장치**다. DNS에 설정하는 텍스트 기록이다.
  - **SPF**: "이 도메인의 메일은 이 서버에서만 보낸다"는 발신 서버 목록
  - **DKIM**: 보내는 메일에 전자 서명을 붙이고, 받는 쪽이 DNS의 공개키로 검증
  - (선택) **DMARC**: 위 둘이 실패했을 때 어떻게 처리할지 정책
- **없으면**: 예약 확정·상담 접수·비밀번호 재설정 메일이 **스팸함으로 분류되거나 차단**된다. 회원이 비밀번호를 재설정하지 못하는 상황이 생긴다.
- **설정 주체**: 도메인 DNS 관리자(운영자). 도메인이 정해진 뒤 기록 3줄을 추가하면 된다.
- **상태**: 도메인 미정이므로 **도메인 확정 시 함께 처리**한다. 기한은 1차 오픈 1주 전(10-30).

## 8. 메일 발송 처리 방침 (PM 지시 2026-09-12)

> "SMTP 구현만 해두고 나중에 넣자"

### 8.1 방침
- **발송 기능은 구현한다.** 발신 계정·서버 정보는 **설정값(환경 변수)으로 분리**해, 나중에 값만 넣으면 동작하도록 만든다.
- 로컬·검증 환경에서는 **메일 수집 도구(로컬 컨테이너)나 로그 출력**으로 대체해 내용·발송 시도를 확인한다. 실제 발송은 하지 않는다.
- SPF·DKIM 설정은 도메인 확정 후로 미룬다 (§6.4).

### 8.2 검증에 미치는 영향
- 메일 관련 수용 기준은 **"발송 요청이 생성되고 내용·수신자가 정확한가"** 로 판정한다. **실제 도달·스팸 분류는 P5에서 판정할 수 없고 운영 확인으로 이월**한다.
- qa 테스트 계획의 "메일 도달 5분 이내" 항목은 **SMTP 연결 이후 운영 스모크 테스트**로 옮긴다.

### 8.3 ⚠️ 1차 오픈에 생기는 공백 (PM 결정 필요 — I-5-c)

1차 범위에는 **일반 문의 폼**이 있고 **관리자 화면은 2차**다. SMTP가 연결되지 않은 상태로 1차를 오픈하면:

| 흐름 | 결과 |
|---|---|
| 방문자가 문의 폼 제출 | 데이터는 저장됨 |
| 스튜디오에 알림 메일 | **가지 않음** |
| 관리자 화면에서 확인 | **1차에는 관리자 화면이 없음** |
| → | **문의가 들어와도 아무도 모른다** |

**선택지**
| 안 | 내용 | 비용 |
|---|---|---|
| **ⓐ 1차 오픈 전 SMTP 연결** (권고) | 발신 계정 하나만 준비하면 된다. 도메인 인증(SPF·DKIM)은 없어도 발송은 되며, 스팸함 확인을 운영자가 감수한다 | 0 (계정 준비만) |
| ⓑ 1차 문의 폼을 전화 안내로 대체 | 폼을 2차로 미루고 1차는 전화·SNS 안내만 | 기획·화면 수정 0.5일, 고객 요청(문의 폼)과 어긋남 |
| ⓒ 간이 확인 수단 추가 | 운영자가 문의 목록을 볼 수 있는 최소 화면을 1차에 추가 | +0.5~1작업일 (1차 범위 증가) |

→ **ⓐ 권고.** 결정 기한은 1차 배포 준비(10-26) 전이다.
