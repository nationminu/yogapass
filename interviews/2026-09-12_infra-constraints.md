# 인프라 전제 — 기존 호스팅과 컨테이너 구성

> **출처**: 2026-09-12 총괄 PM 지시
> 1. "호스팅은 이미 있다 검색하지말자"
> 2. "운영 docker-compose 환경으로 구성되어 있다"
> 3. "로컬환경도 compose 환경으로 컨테이너로 구성한다"

## 1. 확정된 전제

| 항목 | 내용 |
|---|---|
| 호스팅 | **이미 보유**. 신규 서비스 선정·요금제 비교는 하지 않는다 |
| 운영 환경 | **docker-compose 기반 컨테이너 환경**이 이미 구성되어 있다 |
| 로컬 개발 환경 | **docker-compose로 동일하게 구성**한다 (개발·운영 환경 일치) |

## 2. 이 전제가 바꾸는 것

### 무효가 된 분석
- `shared/reviews/CR-001_impact_developer.md` §2의 **호스팅 후보 비교(Cloudflare·Vercel·Supabase·VPS)와 월 비용 산정은 적용되지 않는다.** 보유 호스팅에서 컨테이너로 운영한다.
- 계획서 v1.0 §7의 "호스팅 후보", 인터뷰의 "월 5만 원 예산" 항목도 같은 이유로 재검토 대상이다.
- "Vercel Hobby 상업 사용 금지", "Supabase 서울 리전" 같은 제약은 더 이상 판단 근거가 아니다.

### 새로 생기는 것
| 항목 | 내용 |
|---|---|
| 구성 방식 | 애플리케이션·데이터베이스·리버스 프록시 등을 컨테이너로 묶어 compose로 운영 |
| 개발 환경 | 로컬도 같은 compose 구성 → "내 PC에서는 되는데" 문제가 줄고, 검증 환경 재현이 쉬워진다 |
| 운영 책임 | 관리형 서비스가 아니므로 **백업·보안 패치·모니터링·인증서 갱신을 직접** 해야 한다 |
| 배포 방식 | 이미지 빌드 → 배포 절차를 정해야 한다 (수동 compose 명령 / CI 자동화) |

### 공수 영향 (developer 재산정 필요)
- 관리형 인증·DB 서비스를 쓰지 않으면 **인증·세션·메일 발송을 직접 구성**해야 한다. 라이브러리로 상당 부분 대체되지만 설정·검증 작업이 늘어날 수 있다.
- 반대로 **기반·인프라 항목(2~2.5작업일)** 중 계정 생성·서비스 연동 부분은 줄어든다.
- 로컬 compose 구성 자체가 P4 초기 작업으로 들어간다 (0.5~1작업일 예상).
- → `CR-001_impact_developer.md`의 공수표를 이 전제로 다시 계산해야 한다.

## 3. 확인 필요 사항

| # | 내용 | 왜 필요한가 |
|---|---|---|
| **I-1** | 호스팅 형태와 사양 — 클라우드 VM인지 사내·임대 서버인지, CPU·메모리·디스크 | 컨테이너 수·DB 운영 가능 여부 판단 |
| **I-2** | 현재 compose에 무엇이 올라가 있는지 (웹 서버·리버스 프록시·DB·기타 서비스) | 재사용할 것과 새로 추가할 것 구분 |
| **I-3** | **데이터베이스** — 이미 쓰는 DB가 있는지, 있다면 종류와 버전. 없으면 새 컨테이너로 올리는지 | 스택 선택의 가장 큰 변수 |
| **I-4** | 도메인 연결·HTTPS 인증서 처리 방식 (리버스 프록시·인증서 자동 갱신 여부) | 배포 계획 |
| **I-5** | **메일 발송 수단** — 예약·상담 안내 메일을 어디로 보내는지 (외부 메일 서비스 계정 보유 여부) | 알림 기능 전제 |
| **I-6** | 배포 방식 — 수동 `docker compose` 실행인지, CI로 자동 배포인지. 접근 권한은 누구에게 있는지 | P7 배포 절차 |
| **I-7** | **백업·모니터링 주체** — DB 백업, 장애 감지, 보안 패치를 누가 하는지 (제작사 유지보수 범위인지 고객인지) | 운영 가이드·유지보수 범위 결정 |
| **I-8** | 스테이징(검증용) 환경을 같은 호스팅에 둘 수 있는지 | P5 검증·P7 배포 리허설 |

> I-1~I-3은 **P4 기술 설계 착수 전에 반드시** 필요하다. I-5·I-7은 범위·운영 비용 결정과 직결된다.
