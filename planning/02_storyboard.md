# 화면정의서 (스토리보드) — 강남 요가패스 홈페이지 · 공개·회원 영역

> **이 문서의 범위: 공개 영역(`SCR-001~099`) 15화면 + 회원 전용 영역(`SCR-100~199`) 12화면 = 27화면.**
> **관리자 영역(`SCR-900~999`) 18화면은 `02_storyboard-admin.md`에 분리했다** — 문서 하나로는 45화면이 관리되지 않고, 검토도 영역 단위로 나누는 편이 정확하기 때문이다(CR-001 영향도 planner R-9, RSK-021).

## 공통 규칙

> **이 절은 "어디를 보라"만 적는다.** 규칙 본문을 여기에 복제하지 않는다 — 값이 두 곳에 생기면 다시 어긋난다(R1~R3에서 실제로 겪은 문제다).

| 주제 | 단일 기준 | 이 문서의 취급 |
|---|---|---|
| **하단 고정 바·고정 헤더·영역 구분** | `02_requirements.md` **§3.0 (G-0~G-13)** | 각 화면의 "예외·상태" 표에는 **그 화면에서 달라지는 것만** 적는다(자기 참조 여부, 대표 전화 미확정 시 처리 등). 값·수치는 적지 않는다 |
| **화면 번호·이름·차수·관련 REQ** | `02_requirements.md` **§9 (§9.0~§9.5)** | 각 화면의 "관련 REQ"는 §9의 값을 옮긴 것이다. 불일치가 생기면 **§9가 맞고 이 문서를 고친다** |
| **사이트맵·URL·메뉴·색인·title·description** | `02_information-architecture.md` **§1·§2·§6** | URL은 옮겨 적되 규칙은 IA를 따른다 |
| **측정·검증 조건** | `02_requirements.md` **§5.0 (M-1~M-7)** | Lighthouse 측정 상태가 특수한 화면(완료 화면·404)에만 "예외·상태"에 적는다 |
| **차수 판정** | `02_requirements.md` **§5.0 M-7** | 각 화면 머리표의 `차수` 값이 1차 게이트 판정 대상 여부를 결정한다 |

**작성 규칙**

- **각 화면 머리표에 `차수`와 `로그인 상태`를 반드시 적는다.** 로그인 상태에 따라 **달라지는 섹션만** "상태별 차이" 표로 적고, 화면 전체를 상태별로 두 번 서술하지 않는다.
- 실제 문구 초안은 "큰따옴표". 고객만 아는 사실 정보는 `[TBD: 고객 확인 필요 — T-x]`(요구사항 §8.1 항목 기호).
- 이미지 표기: `[IMG: 설명 · 권장 비율 · 제공 주체]`
- 와이어프레임은 **360px 기준**이며, 구조가 새로운 화면(캘린더·슬롯 목록·상담 폼 등)과 1차 화면에 둔다. 단순 폼·결과 화면은 섹션 표로 갈음한다.
- **빈 상태 문구에 "준비 중"을 쓰지 않는다**(§5.0 M-5). 대신 "공개되면 안내드립니다" 등 시점·행동을 알리는 문구를 쓴다.
- **문구 초안에 사실(연혁·수강생 수·실적·수상)은 한 글자도 넣지 않는다.**
- **값·수치를 복제하지 않는다 (v0.6 강화 — designer R1 #5).** "반응형 변화" 표와 와이어프레임 주석에도 **파생값(72px 등)이나 다른 문서의 수치를 적지 않고 계산식·REQ ID로 참조**한다. §3.0 G-2(고정 바 높이)는 P3에서 확정되는 값이고 G-3의 72px은 그 **파생값**이므로, 고정 바가 60px로 확정되면 복제해 둔 72px이 전부 틀린 값이 된다.
- **뷰포트 표기 (v0.6)**: "반응형 변화" 표의 360 / 768 / 1280px는 **측정 지점**이며, 실제 규칙은 요구사항 §3.0 G-1의 **구간**(`<768px` / `768~1279px` / `≥1280px`)을 따른다.
- **확정문 2건은 임의로 바꾸지 않는다.**
  - 상담 중복 안내(PM 확정문, REQ-F-S-006): **"이 연락처로 접수된 신청이 있습니다. 예약 확인 또는 전화로 문의주세요."**
  - 해피콜 전제 안내(REQ-F-S-014): **"신청은 접수 단계이며, 담당자가 전화로 일정을 확인한 뒤 확정됩니다."**

**2차 확장 예고 (P3 designer 입력 — 요구사항 §10)**
캘린더·데이터 표 컴포넌트 / **1024px 브레이크포인트**(관리자) / **z-index 레이어 6단**(sticky 헤더 · sticky 표 헤더 · 고정 바 · 드롭다운 · 모달 · 토스트) / **상태 배지 4군**(예약·상담·스케줄·슬롯) / 입력 8~10개 폼 대응. **1차 토큰은 폐기·재정의하지 않고 확장만 한다.**

# 2부 · 회원 전용 영역 (`SCR-100~199`)

> **전 화면 공통 전제 (화면마다 반복하지 않는다)**
> · **차수 = 2차 · 로그인 필요.** 비로그인 접근 시 SCR-032로 이동하고 로그인 후 원래 경로로 복귀한다(REQ-F-M-018). **예외는 `/booking`(SCR-110) 하나**로, 로그인 화면으로 튕기지 않고 회원 전용 안내 상태를 보여준다(REQ-F-L-021).
> · **전 화면 `noindex` + sitemap 제외 + `Cache-Control: no-store`**(REQ-N-L-005, REQ-F-M-008). **description은 요구하지 않고 title만 둔다**(REQ-N-010).
> · **헤더는 공개 헤더 + 회원 메뉴**(§3.0 G-12), **하단 고정 바 우측은 "레슨 예약"**. `/booking` 계열 4화면은 자기 참조이므로 **"전화 문의" 전폭 1버튼**이다.
> · **모든 상세·수정·취소 요청에 소유자 검사**를 적용한다(REQ-N-M-003). 다른 회원의 식별자로는 열리지 않는다(404 또는 403).
> · **URL 식별자 `{ref}`는 비연번 공개 식별자**이며 예약번호·신청번호를 URL에 쓰지 않는다(REQ-N-R-010, IA §6.1).
> · **세션 만료 2분 전 경고 + 연장 옵션**을 제공하고, 폼 작성 중 만료되어도 입력값을 잃지 않는다(REQ-N-M-006).
> · **JavaScript 비활성 화면은 REQ-N-028 적용 제외**이며 `<noscript>` 안내 + 전화 링크만 요구된다(REQ-N-029).
> · **빈 상태 문구에 "준비 중"을 쓰지 않는다.**
