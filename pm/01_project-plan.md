# 프로젝트 계획서 — 강남 요가패스 홈페이지

> **요약 (PM 확인용)**
> 1. **범위**: 요청 페이지 5종(메인·요가 강사 소개·오시는 길·예약·예약조회)과 개인정보 처리방침을 만든다. 처리방침은 예약·문의 폼 때문에 필요하다. 문의 폼, 지도, 보유 도메인 연결도 포함한다. 메뉴 페이지는 이 6종으로 한정한다(§2.1).
> 2. **핵심 쟁점**: **예약·예약조회를 어디까지 만들지** 아직 정해지지 않았다. ADR-001에서 정할 항목은 네 가지다.
>    ① 예약 방식: A 접수형 / A'-1 접수 확인형 / A'-2a 진행 상태형(기존 도구로 상태 변경) / A'-2b 진행 상태형(관리 화면) / B 자체 예약 시스템 / C 외부 예약 서비스
>    ② 스튜디오가 접수 상태를 바꾸는 수단(관리 화면을 둘지 여부)
>    ③ 신청자에게 예약번호·접수 안내를 전달하는 수단
>    ④ A' 계열을 고를 경우의 일정 대응안(S-1~S-4)
>    계획서는 범위를 세우기 위해 **A'-1(신청 접수 + 접수 내역 조회, 상태 변경·관리 화면 없음)을 임시 기준안으로 둔다(가정).** 고객 회신은 **09-16 12:00까지** 받고, ADR-001 결정은 **09-16**(늦어도 09-18)에 한다.
> 3. **일정**: 착수 09-11 → **오픈 목표 10-27(화)** → 종료 11-03. **현행 WBS는 A·C안 분량 기준이다.** developer 추정(±30%)으로는 A'-1(A' 계열 중 최소 구성)도 작업일이 **+3.5~6일**(예약번호 전달 수단에 따라 다름) 더 들어, 압축 없이는 오픈이 **11-02~11-04**로 밀린다(§4.2). 10월 말 오픈을 지키려면 일정 대응안 중 하나를 PM이 골라야 한다.
>    - **S-1 서버 측 선착수(O-6)**: 전제 조건을 모두 충족하면 10-28~10-29, 서버 측 계정 준비가 G3(10-07)까지 밀리면 10-29~10-30(버퍼 0)
>    - **S-2 오픈일 조정** / **S-3 단계 오픈** / **S-4 기준안을 A·C로 조정**
>    B안은 +3.5~5주로 10월 말 오픈이 불가하다.
> 4. **고객 확인 필요**: 질문 27건(§2.4). 이 중 범위·일정을 정하는 **묶음 ① 12건은 09-16 12:00까지** 회신이 필요하다. 가장 먼저 물을 질문은 "누가 무엇을 예약하는가"(Q23)다. 질문 문장 안에서는 번호 대신 [주제] 이름으로 서로 참조하므로, 발송본에서 번호를 새로 매겨도 된다(v0.3).
> 5. **최대 리스크**: 예약 범위 미확정(RSK-001), 일정 압박(RSK-002), 콘텐츠·사진 제공 지연(RSK-003·004). 기술 리스크는 6건(RSK-011~016)이다: 폼 악용(신청자 이메일 안내를 고르면 제3자 주소로 메일을 보내는 악용 포함), 메일 발신 인증(10-22 운영 환경 준비 때 적용), 무료 요금제 약관, 개인정보 위탁·국외 이전 고지, 조회 보안, Safari 검증.

## 2. 범위
### 2.1 포함 (In-scope)
- **페이지 (반응형)**
  - 메인 — 스튜디오 소개 요약, 예약·문의 버튼
  - 요가 강사 소개 — 강사 정보는 고객이 제공
  - 오시는 길 — 지도 표시, 길찾기 링크, 주소·교통·운영시간
  - 예약 — 기능 범위는 §7.1 선택지 중 ADR-001 결정을 따름
  - 예약조회 — 기능 범위는 §7.1 선택지 중 ADR-001 결정을 따름
  - 개인정보 처리방침 — 추론-04에 따라 추가하며, 문안 확정은 고객이 함
- **페이지 추가 원칙**: 메뉴 페이지는 요청 5종과 개인정보 처리방침으로 한정한다. 문의 폼과 공개하기로 한 수업·요금 정보는 기존 화면 안에 배치하고, 위치는 P2 IA에서 제안한다(Q4·Q13 회신 반영). 별도 페이지가 필요하면 PM이 결정한다. 폼 전송 완료·오류 화면과 404 페이지 같은 보조 화면은 페이지 수에 넣지 않는다.
- **공통 요소**: 헤더(로고·메뉴), 푸터(연락처·사업자 정보·SNS 링크 — 표시 항목은 고객 확인), 예약·문의 바로가기 버튼
- **예약 신청 처리**: 입력값 검증(서버 측 포함), 개인정보 동의, 스팸 방지, 스튜디오 알림, **신청자 접수 완료 안내**를 포함한다. 안내 수단(완료 화면 표시 / 이메일 등)은 ADR-001에서 정한다(Q25). 세부 흐름과 예외 처리는 P2 화면정의서에서 정의한다.
- **문의 폼**: 계획 기준안은 예약과 **별도의 일반 문의 폼**이다(가정, Q4에서 확인). 입력값 검증, 개인정보 동의, 스팸 방지, 스튜디오 알림을 포함한다.
- **지도**: 지도 서비스 임베드와 외부 지도 앱 길찾기 링크
- **디자인**: 화이트·블루 컨셉 시안 2~3안 → PM 선택 → 디자인 시스템·페이지 디자인·목업. 보유 로고 적용.
- **이미지**: 상업적 사용이 가능한 스톡 이미지·일러스트를 골라 출처·라이선스 기록. 고객이 제공한 사진 적용.
- **SEO·접근성·성능**: `CLAUDE.md` §6 기본 기준, 사이트 안의 SEO(메타데이터·sitemap·robots·지역 업체 구조화 데이터, 추론-07)
- **배포**: 호스팅 구성, 보유 도메인 연결, HTTPS, 운영 배포, 운영 스모크 테스트
- **인계**: 운영 가이드(콘텐츠 수정 요청 방법, 접수 확인 방법, 롤백), 최종 보고서
- **안내 문구**: 헤드라인·버튼·폼 안내 등 화면 문구 초안 작성 (사실 정보는 제외)

### 2.2 제외 (Out-of-scope)
기준안 기준이며, 포함하려면 ADR-001 결정 또는 CR이 필요하다.
- 회원가입·로그인, 회원권·수강권 관리
- 온라인 결제
- 자체 실시간 예약 시스템(시간표·정원 관리, 자동 확정, 대기 등록), 신청자가 직접 하는 예약 취소·변경 — **ADR-001에서 B안을 고르면 범위와 일정을 다시 산정한다**
- **스튜디오용 관리 화면(로그인·관리자 인증 포함)** — 기준안(A'-1) 기준으로 제외한다. ADR-001에서 A'-2b를 고르면 포함으로 옮기고 일정을 다시 산정한다.
- 기존 회원 확인·수강권 차감 — Q23 회신에서 회원 정규 수업 예약이 필요하다고 하면 ADR-001에서 B·C안과 함께 재검토
- 문자·카카오 알림톡 자동 발송(유료이고 발신번호·발신 프로필 등록이 필요함) — 기준안은 이메일 알림
- 고객이 직접 콘텐츠를 수정하는 관리 기능(CMS) — Q6 회신에 따라 재검토
- 다국어 — Q7 회신에 따라 재검토
- 블로그·게시판·공지사항·수강 후기
- 사진·영상 촬영, 로고 리디자인
- 사실 정보(강사 약력, 수업·요금, 연혁 등) 원고 작성 — 고객이 제공
- 광고 집행, SNS 운영, 유료 검색 광고

### 2.3 가정 및 제약
**가정**

- A-1. 예약 기능의 범위 기준안은 **A'-1 접수 확인형**으로 둔다. 신청 접수와 저장된 신청 내역 조회만 하고, 스튜디오의 상태 변경과 관리 화면은 없다(§7.1). 확정이 아니며 ADR-001로 결정한다. 결정이 달라지면 계획서를 1.1로 개정한다.
- A-2. 오픈 목표일은 **2026-10-27(화)** 로 둔다. 10-29~10-30 이틀은 버퍼이며, "10월 말"의 정확한 날짜는 Q5로 확인한다. **현행 WBS 날짜는 A·C안 분량 기준이다.** A' 계열로 결정되면 일정 대응안(S-1~S-4, §4.2)에 따라 WBS를 개정한다.
- A-3. 비작업일: 주말, 추석 연휴(09-24~09-26), 개천절 대체공휴일(10-05), 한글날(10-09). 공휴일은 가정이므로 실제 작업일은 PM이 확인한다.
- A-4. PM의 게이트 승인은 요청 후 **1영업일 안에** 이루어진다. 고객 질의 회신은 §2.4 묶음별 기한을 지킨다(묶음 ①은 09-16 12:00).
- A-5. 고객 콘텐츠는 구조 정보(강사 수·수업 종류·주소 등)를 09-18까지, 최종 원고·사진 파일을 10-07까지 제공한다.
- A-6. 사이트는 한국어 단일 언어로 만든다.
- A-7. 호스팅·외부 서비스는 무료 또는 저비용 요금제를 우선 검토하고, 계정은 고객 명의로 만든다(Q20-2). 무료 요금제는 **상업적 이용 허용 여부, 월 한도, 활동이 적을 때 일시 중지되는 정책**을 확인한 뒤에만 쓴다(RSK-013).
- A-8. CMS는 두지 않는다(Q6). 콘텐츠는 소스 안의 데이터 파일로 분리해 수정하기 쉽게 만든다. 오픈 후 누가 수정을 반영할지(유지보수 포함 여부)는 PM 결정 사항이며 아직 정해지지 않았다(§2.2 마지막 항목).
- A-9. 홈페이지의 '예약'은 주로 **처음 오는 사람의 체험 수업·상담 신청**으로 가정한다(Q23). 기존 회원의 정규 수업 예약이 포함되면 회원 확인·정원 관리가 필요해 B·C안 쪽으로 재검토한다.
- A-10. ADR-001 결정에 쓸 개략 비용·공수는 developer 추정(R1 리뷰 부록 A, R2 리뷰 부록 B, ±30%)과 09-15에 발행할 기술 의견 티켓의 회신을 근거로 한다. 상세 비교는 P4 기술 설계에서 한다.

**제약**

- C-1. 착수(09-11)부터 10-30까지 약 7주, 작업일 약 32일이다. 중간에 평일 공휴일 4일(09-24, 09-25, 10-05, 10-09)이 있다.
- C-2. 사진 자료가 없다.
- C-3. 운영 배포, DNS 변경, 외부 서비스 계정 생성·유료 결제, 원격 저장소 push는 PM의 명시적 승인 후에만 한다 (`CLAUDE.md` §8).
- C-4. 확인되지 않은 사실은 `[TBD: 고객 확인 필요]`로 표시하며, 이 표시가 남아 있으면 운영 배포를 하지 않는다.
- C-5. 로컬 개발 환경은 Windows라서 Safari·iOS Safari를 로컬에서 실행할 수 없다. 검증 수단은 늦어도 G3까지 정한다(RSK-016).

### 4.2 주요 경로와 일정 평가
- **주요 경로(critical path)**: 고객 질의 회신·ADR-001(09-16) → G2(09-23) → 컨셉 선택(09-30) → G3·최종 콘텐츠 수령(10-07) → G4(10-16) → G5(10-21) → G6(10-23) → 배포 승인(10-26) → 오픈(10-27)
- **병행 경로**: 외부 계정 준비·Safari 검증 수단(G3까지), 운영 환경 준비 승인(10-22). C안을 고르면 고객의 외부 예약 서비스 준비(G3까지)도 주요 경로에 들어간다.
- **여유**: 10월 말까지 작업일 2일(10-29~10-30). 게이트 하나가 1일 늦어질 때마다 버퍼가 1일씩 줄어든다.
- **평가 (v0.2 정정)**: 현행 WBS의 P4 구현 기간(실질 3.5~4작업일)과 P5(3작업일, 수정 1~2사이클)는 **A·C안 분량**이다. 이 경우에도 여유가 거의 없다(일정 리스크 높음).
  **A' 계열은 현행 WBS만으로는 10-27 오픈이 불가하다.** developer 추정(R1 리뷰 부록 A, R2 리뷰 부록 B, ±30%)으로 서버 측 구현(신청·조회 API, 저장, 알림, 파기, 상태 관리)이 더해져 P2~P5에 작업일이 추가로 든다. A'-1은 +3.5~5일(예약번호를 신청자 이메일로 안내하는 (b)를 고르면 +4~6일), A'-2a는 +4~6일, A'-2b는 +7.5~9.5일이다. 버퍼 2일로는 메울 수 없다. A'-2a·A'-2b에서도 (b)를 고르면 +0.5~1.5일이 더해질 수 있다(developer R2의 결정 항목 3 (b) 추정을 pmo가 적용함, TKT-PM-001 회신에서 확인).

### 7.1 예약·예약조회 기능 선택지 (핵심 쟁점 — ADR-001에서 결정)
> 아래 "계획 기준안"은 범위를 세우기 위한 **임시 가정**이며 확정이 아니다. 고객 회신(ADR-001 입력 질문: Q23, Q1, Q2, Q24, Q25, Q3, Q6, Q8-1, Q20-1, 일정 판단용 Q5)과 developer 기술 의견(TKT-PM-001)을 받으면 pmo가 ADR-001에 장단점을 정리하고 권고는 별도 절로 쓴다. 결정은 PM이 한다.

**A' 계열 정의 (v0.2에서 분리)**
- **A'-1 접수 확인형 (계획 기준안·가정)**: 신청자는 저장된 신청 내역(신청 일시·희망 수업·'접수 완료')만 조회한다. 스튜디오는 상태를 바꾸지 않고, 관리 화면도 없다. 예약 확정은 스튜디오가 전화 등으로 따로 연락한다.
  - **한계 (v0.3)**: 조회 결과는 보관 기간 내내 '접수 완료'로 남는다. 스튜디오가 전화로 확정·취소·일정 변경을 해도 반영되지 않는다. 그래서 신청자가 취소된 신청을 유효하다고 보거나 '접수 완료'를 '예약 확정'으로 오해할 수 있다. 조회 결과 화면에 "확정·변경·취소는 스튜디오가 연락으로 안내" 문구가 필요하다(P2 화면정의서).
  - **A 대비 추가 가치**: A안도 완료 화면과 접수 안내(§2.1)로 신청 내용을 알려준다. A'-1이 더 주는 가치는 "제출한 신청 내용을 나중에 다시 확인"하는 것에 한정된다.
- **A'-2 진행 상태형**: 신청자는 접수·확정·취소 상태를 조회한다. 스튜디오가 상태를 바꿀 수단이 필요하며, 수단에 따라 둘로 나눈다.
  - **A'-2a**: 스프레드시트 연동 같은 기존 도구로 상태를 바꾼다.
  - **A'-2b**: 간이 관리 화면을 두고 관리자 인증을 거쳐 상태를 바꾼다.
  - DB 콘솔을 직접 조작하는 방식은 운영 수단으로 부적합해 후보에서 뺀다. 비개발자가 쓰기 어렵고, 잘못 조작하면 개인정보 전체가 노출·삭제될 위험이 있다.
- **Q2와의 대응**: (가) → A'-1, (나) → A'-2(수단은 Q24), (다) 고객 직접 취소·변경 → B 수준(A' 범위 밖)

**ADR-001 결정 항목**
1. 예약 방식: A / A'-1 / A'-2a / A'-2b / B / C
2. 스튜디오 상태 변경 수단: 없음(A'-1) / 기존 도구(A'-2a) / 관리 화면(A'-2b). 관리 화면을 포함하면 §2.2의 "스튜디오용 관리 화면"을 §2.1로 옮긴다.
3. 예약번호 전달·조회 식별 수단(Q25)
   - (a) 완료 화면에만 표시: 추가 비용 없음. 번호를 잃어버리면 조회 불가
   - (b) 신청자 이메일로 안내: 이메일 수집 항목 추가, 발신 도메인 인증 필요(RSK-012). (a)·(d) 대비 **추가 +0.5~1.5작업일**(developer R2, 신청자 메일 템플릿·형식 검증·악용 방지·수신 확인 테스트). **제3자 주소 악용 방지 필요**: 봇이 남의 주소를 넣어 대량 제출하면 보유 도메인 명의 메일이 나가 발신 도메인 평판이 떨어지거나 메일 발송 계정이 정지될 수 있다. 그러면 같은 경로로 가는 스튜디오 접수 알림까지 끊길 수 있다(RSK-011). 대응은 발송 빈도 제한, 신청자 메일에 자유 입력 문구를 넣지 않음, 반송·실패 모니터링
