# 프로젝트 계획서 — 강남 요가패스 홈페이지 (v2.0, CR-001 반영)

> **요약 (PM 확인용) — 결론 먼저**
>
> 1. **이것은 개정이 아니라 기준선 교체다.** CR-001 승인으로 계획서 v1.0이 G1에서 "제외"로 승인받은 세 가지(회원가입·로그인 / 관리자 화면 / CMS)가 **포함**으로 바뀌었다. 화면 8개 → 약 42개, 요구사항 116건 → 약 225건, P4 구현 3.5~4작업일 → **39~57.25작업일**이다. v1.0의 §2.1 페이지 추가 원칙·§4 WBS·§7.1 예약 선택지는 **전부 폐기**한다.
> 2. **2차 오픈(단계 오픈 A)으로 간다.** 1차 = 소개형 + 운영과 동일한 full compose 인프라 / 2차 = 회원·레슨 예약·상담 예약·관리자. **1차 기준 오픈일 2026-11-06(금)·마감 11-12**, **2차 기준 오픈일 2027-01-22(금)·마감 02-10** (PM 지시는 "01-23(금)"이었으나 2027-01-23은 **토요일**이다 → §4.0 참조, 확정 필요).
> 3. **일정 성립 판단**: **1차는 성립한다**(중앙 추정으로 10-29 조기 오픈 가능, 기준일 11-06까지 5작업일 여유). **2차는 중앙 추정에서만 성립한다** — 상한 추정이면 오픈이 2027-02-03~02-05로 밀려 마감 02-10을 여유 0으로 지킨다. 성립 조건 5가지는 §4.5에 적었다. 하나라도 깨지면 마감을 넘긴다.
> 4. **게이트는 15개가 아니라 11개로 운영할 것을 권고한다** (§3.2). 1차는 소개형 8화면 규모이므로 기획·디자인을 한 게이트로, 구현·검증을 한 게이트로 묶는다. 진짜 비용은 게이트 문서가 아니라 **승인 대기 1영업일**이므로, 승인 대기 목표를 **당일**로 낮추고 게이트 보고와 다음 단계 비의존 구간 착수를 분리한다.
> 5. **최대 리스크 3가지**: ① 2차 일정 여유 0 (RSK-018) ② 개인정보 범위 확대 — 경고 기록·해피콜 메모 (RSK-019) ③ 백업·복구가 검증되지 않은 채 인도될 위험 (RSK-020, 대응: **복구 리허설을 G7a·G7b 통과 조건으로 고정**).
> 6. **고객 확인**: PM 지시(D-4)로 방식·범위 질문은 발송하지 않는다. 다만 **사이트에 그대로 노출되는 실제 값 8건**(§2.4)은 지어낼 수 없으므로 `[TBD: 고객 확인 필요]`로 유지하고, 차수별 오픈 전까지 확보해야 한다. **미확보 시 해당 차수 오픈을 막는다**(제약 C-4).
> 7. **PM 결정이 남은 것 6건**: 2차 오픈일 요일 정정, 게이트 운영안 확정, 1차 상담 예약 편입 여부, 유지보수·운영 범위 경계, 개인정보 보관 정책, 고객 인도 범위 (§5.3).

## 2. 범위

### 2.0 차수 구분 원칙

- **문서는 1세트로 유지하고 차수는 "열"로 표시한다** (planner 의견 §7.1 채택). 차수별로 문서를 쪼개면 같은 규칙이 두 곳에 생기고, 이 프로젝트는 정확히 그 문제로 R1~R3를 소비했다.
- REQ·SCR 표에 `차수` 열(`1차` / `2차` / `공통`)을 둔다. `공통`은 1차에 구현하고 2차에 확장되는 항목이며 **수용 기준을 1차용·2차용으로 나눠 쓴다**(qa가 1차 게이트에서 2차 기준으로 판정하지 않도록).
- SCR 번호대를 영역으로 분리한다: **001~099 공개 / 100~199 회원·예약 / 900~999 관리자** (`CLAUDE.md` §4 ID 형식은 유지). → **pmo 기준안, PM 확정 대상 아님**(진행을 막지 않는 표기 규칙).

> **1차 상담 예약은 기본 제외한다(pmo 기준안).** 근거: 상담 예약은 관리자 목록·해피콜 기록·비회원 조회 창구·중복 검사가 함께 와야 실제로 운영되며 **+3~5작업일**이 1차로 당겨진다. 1차 여유(중앙 추정 5작업일)를 전부 소진해 11-06 기준선이 버퍼 0이 된다.
> **단 조건부 편입 옵션을 둔다**: 1차 G4a·G5a 통합 게이트(10-22) 시점에 **잔여 버퍼가 5작업일 이상**이면 PM이 CR 없이 상담 예약을 1차에 편입할 수 있다. "앞당길 여지가 생기면 당긴다"는 PM 방침(D-3)의 적용 경로다.

> **1차에 시간표를 정적으로 노출하지 않는다**(planner §7.3 권고 채택). 시간표 자료가 미확보이고, 2차에서 관리자 입력으로 전환하는 작업이 추가되며, 잘못된 시간표 노출은 신뢰를 해친다. 대신 "월 시간표는 준비 중입니다 · 전화 문의" 안내를 둔다.

### 3.2 게이트 운영 방식 — **pmo 권고안**

**문제**: 차수를 나누면 게이트가 기계적으로 2배(G2a~G8a + G2b~G8b = 14 + G1 재승인 = **15개**)가 된다. 1차 가용 작업일이 36일인데 게이트마다 승인 대기가 붙으면 대기만으로 일정을 잡아먹는다.

**핵심 판단**: **비용은 게이트 문서(pmo 0.25작업일)가 아니라 승인 대기다.** 따라서 ① 게이트 수를 줄이고 ② 승인 대기 목표를 당일로 낮추고 ③ 게이트 보고와 다음 단계의 **비의존 구간 착수를 분리**한다.

| 안 | 게이트 수 | 내용 | 평가 |
|---|---|---|---|
| 안 A 완전 분할 | **15** | G2a~G8a · G2b~G8b · G1-CR-001 | 원칙에 충실하나 1차에만 게이트 7개. 승인 대기 누적 7일 = 1차 여유 전량 소진 |
| **안 B 선택적 분할 (pmo 권고)** | **11** | 아래 표 | 1차를 3게이트로 묶고 2차는 표준 운영. 대기 누적 3일 |
| 안 C 최대 압축 | 8 | 차수 구분 없이 기존 G1~G8만 운영 | **불가** — 배포·검증이 실제로 두 번 일어나는데 게이트가 한 번이면 1차 배포에 PM 승인 근거가 없다 (`CLAUDE.md` §8 위반) |

### 6.2 기능·보안 품질

- **폼**: 필수·형식 검증(서버 측 포함), 개인정보 동의, 제출 성공·실패 안내, honeypot·요청 빈도 제한, 스튜디오 알림 수신 확인
- **인증·세션** (RSK-023): 비밀번호 해싱(bcrypt 또는 argon2id), 계정 열거 방지(존재 여부를 응답으로 구분할 수 없게), 세션 고정 방지, CSRF 방어, 로그인 시도 제한, 재설정 토큰 1회용·만료
- **권한·IDOR**: **소유자 검사를 공통 레이어 한 곳에 모은다.** 관리형 RLS가 없어 전부 애플리케이션 책임이므로, 화면마다 흩어 놓으면 누락이 반드시 생긴다. P5에 권한·IDOR 시나리오를 포함한다
- **동시성** (RSK-026): 정원 초과 예약 0건, 슬롯 시간 겹침 0건, 같은 강사 동시간 중복 배정 0건, 중복 상담 접수 0건. **PostgreSQL 배제 제약·부분 유니크 인덱스로 DB가 최종 차단**하고, 화면 측 즉시 피드백은 별도로 둔다. qa와 동시 요청 검증 수단을 합의한다
- **비회원 상담 조회** (RSK-015 승계): 신청번호 + 연락처 일치 시에만 조회, 빈도 제한(기준값 10분 10회), **없을 때와 실패했을 때 같은 문구·같은 응답 시간**, 연락처 마스킹
- **개인정보** (RSK-019): 수집 최소화, 동의 필수/선택 분리, 항목별 보관 기간에 따른 자동 파기, **경고 기록·해피콜 메모는 비회원 조회·마이페이지에 표시하지 않는다**, 열람·삭제 요청 처리 수단(비회원 상담 신청 삭제 포함). 법률 판단과 문안 확정은 고객 몫
- **메일**: SPF·DKIM·DMARC 설정, 기존 회사 메일 SPF **병합 전 백업**, 발송 로그·실패 재시도, 운영 스모크에서 실제 수신 확인
- **백업·복구** (SC-6·RSK-020): 백업 스크립트 + 보관 회전 + 복구 스크립트 + 절차서 + **복구 리허설 1회 실행 기록**. 리허설 없이는 G7a·G7b를 통과시키지 않는다
- **콘텐츠**: 오픈 시점 `[TBD]` 0건, 이미지 전량 출처·라이선스 기록
- **검증 환경**: Safari·iOS 검증 수단을 G3a까지 확정(RSK-016). **스테이징에서 검증하고 운영 DB로 검증하지 않는다**(I-8)

> **이 교환에 대한 판단**: 월 3.5만 원을 아끼는 대신 3.25~5.75작업일을 더 쓴다. 제작비로 환산하면 손해지만 ① 그 작업의 상당 부분은 한 번 만들면 운영 내내 쓰는 자산이고 ② 요금제·약관·리전·사업자 종속 리스크가 영구히 제거되며 ③ 개인정보가 전부 자기 서버에 남는다. developer도 같은 판단이다. **단 "백업이 실제로 복구되는가"를 검증하지 않으면 이 이득은 전부 무효다** → SC-6·RSK-020.
