## 2. 요청 정리 (pmo)

> 기능 정의의 **단일 기준은 `interviews/2026-09-12_booking-rules.md` v1.2**(PM 지시 16건 정리본)와 위 §1 원문이다.
> `interviews/2026-09-12_customer-interview.md`는 **가상 인터뷰**이고, `interviews/2026-09-12_summary-and-options.md`는 **오케스트레이터 초안**이다. 두 문서의 고객 답변·수치는 사실로 인용하지 않고 **가정**으로만 다룬다. 특히 초안 §3의 공수 환산치는 developer가 중복·누락을 지적했으므로 이 절과 §3에서 쓰지 않는다.
> `interviews/2026-09-12_infra-constraints.md` v0.2(보유 호스팅·docker-compose·SMTP·운영자 확보)는 **PM 지시에 근거한 확정 전제**로 취급한다.

### 2.1 명시된 요구 (§1 원문 16건 → 기능 단위)

| # | 내용 | 원문 |
|---|---|---|
| M-01 | **회원가입·회원관리를 범위에 넣는다. 회원가입을 해야만 레슨 예약이 가능하다** | 1 |
| M-02 | 레슨 예약은 캘린더로 가능 여부를 표시하고, 가능할 때만 예약된다. 운영 06:00~20:00(조절 가능), 점심시간 제외(11:00~13:00 기본 닫힘, 관리자가 열 수 있음) | 2, 14(B-1·B-2) |
| M-03 | 레슨 길이는 60분 기준, 유형별 60~90분 | 3, 14(B-4) |
| M-04 | 슬롯은 관리자가 유연하게 열고 닫는다 | 4, 14(B-1) |
| M-05 | **"예약 후 관리자가 강사 배정" 방식은 취소한다.** 관리자가 **월별 스케줄을 편성·게시**하고 그 캘린더로 예약을 받는다. **월별 템플릿**을 제공한다 | 5, 6 |
| M-06 | 게시는 **전월에 관리자가 직접**(매월 1일 전). 일정 등록 시 **강사 배정 필수**. **공휴일도 운영**하며 관리자가 템플릿 적용 후 게시 전 수정 | 7(B-11·B-12·B-13) |
| M-07 | **강사 관리 기능 포함**(초기: 강사 정보 관리 수준). 강사 근무 기간·휴무 관리는 **다음 단계** | 7(B-14) |
| M-08 | **체험 후·신규 등록·임산부·기타 방문 상담은 캘린더와 별개의 별도 창구**로 일자·시간을 받아 접수한다 | 7 |
| M-09 | 상담 예약은 **비회원도 가능**, 레슨 캘린더와 **연계하지 않음**, **건강 정보 미수집**, 항목은 일자·시간·이름·연락처(회원 자동 기입), 접수 후 **해피콜로 확정** | 8(C-1~C-4) |
| M-10 | 해피콜 미응답 처리는 **담당자 재량**(자동 취소·재알림 없음). 중복 신청은 **일자+시간+연락처 동일 시 차단**, 연락처만 같으면 안내 후 접수 | 9(C-5·C-6) |
| M-11 | 중복 안내 문구 확정: **"이 연락처로 접수된 신청이 있습니다. 예약 확인 또는 전화로 문의주세요."** (신청 상세 미표시) | 10 |
| M-12 | **비회원 예약(상담 신청) 확인 창구를 둔다** | 11 |
| M-13 | **예약번호를 발급하고 번호로 취소**할 수 있게 한다 | 12 |
| M-14 | 예약 제한 없음, **하루 전까지 가능·당일 불가**. **레슨 예약에도 예약번호를 발급**한다 | 13(C-8·C-10), 15 |
| M-15 | 레슨 유형: 그룹·키즈·플라잉·로우플라잉·리포머(유형 조사 지시). **1:1 개인 레슨은 상담으로 처리**. 노쇼·반복 취소, 예약자 있는 슬롯 폐쇄는 **경고하고 기록** | 14(B-4·B-6·B-8) |
| M-16 | **슬롯당 최대 인원은 관리자가 정한다.** 수업 공간(룸)은 **1개**. **레슨 유형은 관리자 화면에서 관리** | 15, 16(B-15·B-16) |

**부수 전제(PM 지시, infra-constraints v0.2)**: 호스팅 보유(신규 선정 안 함) / 운영은 docker-compose 컨테이너 환경 / 로컬도 compose로 동일 구성 / 서버 리눅스 8코어 16GB / 오픈소스 DB / SMTP 발송 / 운영자 있음.

**pmo 권고**: **부분 수용**

**사유**

1. **기능 범위 자체는 수용을 권고한다.** ① PM이 §1 원문 16건으로 규칙을 직접 확정했고 ② booking-rules v1.2가 이미 구현 가능한 수준(레슨 유형·정원·게시 흐름·중복 규칙·조회 보안까지)으로 정리되어 있어 요구사항 도출이 막히지 않으며 ③ **회귀 시점으로는 지금이 가장 싸다** — P3 미착수라 디자인·소스 손실이 0이고, P2도 공통 영역 50~58건이 살아남는다. P4 착수 후였다면 목업·소스까지 폐기 대상이었다.
2. **그러나 "수용"만으로는 결정이 완결되지 않는다.** 이 CR은 기능 추가가 아니라 **계획 기준선(범위·일정·기술·비용)의 전환**이다. 오픈 방식과 오픈일을 함께 정하지 않으면 계획서 개정을 시작할 수 없고, 계획서가 확정되지 않으면 P2도 시작할 수 없다. 그래서 **"수용 + 조건"** 형태가 필요하다.
3. **거절·보류를 권고하지 않는 이유**: 거절하면 PM이 직접 지시한 16건이 무효가 된다. 보류는 비용만 만든다 — 현재 G2가 이미 보류 상태이고 P2 산출물 v0.4는 CR 결정 없이는 더 진행할 수 없어, 보류 기간이 그대로 유휴가 된다.
