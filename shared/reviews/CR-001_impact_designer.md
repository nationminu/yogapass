# CR-001 영향도 의견 — designer

> **이 문서는 리뷰(승인·수정 요청)가 아니라 영향도 의견이다.** 선택지와 영향만 제시하고 결정하지 않는다.
> **기능 정의 기준은 `interviews/2026-09-12_booking-rules.md` v1.2(PM 지시 정리본)와 CR-001 §1 원문 16건이다.**
> `interviews/2026-09-12_summary-and-options.md`는 **가상 인터뷰 기반 문서**이므로, 이 의견서에서는 **개발 공수 환산 구조와 단계 오픈 방안(방안 1~3)의 틀만 참조**하고 그 안의 고객 답변·수치를 사실로 인용하지 않는다.
> 아래의 SCR·CMP 번호는 **designer가 규모 산정을 위해 임시로 붙인 가칭**이다. 실제 ID 부여는 planner(SCR)·designer(CMP, P3)의 몫이며 이 문서로 확정되지 않는다.

- **가장 큰 위험은 화면 수가 아니라 "디자인 시스템의 성격이 바뀌는 것"이다.** 현재 8화면은 *읽는 사이트*(소개형)라 카드·Hero·폼 1개면 끝난다. CR-001이 들어오면 *쓰는 사이트*(입력·상태·목록·권한)가 되어, **상태(로딩·빈·오류·마감·비활성·권한없음) 정의량이 컴포넌트 수보다 빠르게 늘어난다.** 컴포넌트 34개 신규보다 **상태 조합 명세**가 공수의 절반 이상을 차지한다.
- **현행 P3 일정(컨셉 시안 09-28 착수, G3 10-07)은 CR-001 전체 범위로는 성립하지 않는다.** 단계 오픈(방안 1 틀)을 택하면 1차 P3는 09-28 착수를 유지할 수 있으나 **G3가 1~2작업일 초과**할 가능성이 있다(§5).
- **단계 오픈을 택할 경우 디자인의 최대 관심사는 "1차 컨셉이 2차 기능 화면까지 견디는가"다.** 소개형만 보고 감성형 컨셉을 고르면 2차에서 캘린더·표·관리자 화면이 컨셉과 따로 놀아 **재작업 3~5작업일**이 발생한다. 컨셉 시안 선택 기준에 **"기능 화면 확장성"** 을 넣는 것을 권한다(§6).

## 2. 가장 어려운 화면 — 난이도와 모바일 대응

### 2.1 관리자 월 편성 그리드 (A-03·A-04) — **최상 난이도. 이번 CR의 디자인 최대 난제**

**구조적 사실** (booking-rules v1.2 §2)
- 운영 06:00~20:00 = **14시간 = 30분 그리드 28행**
- 월 단위 전체를 한 화면에 = 28행 × 31열 = **868셀** → 1280px에서도 열 폭이 27px로 떨어져 **표시 불가**
- 다만 **B-15(수업 공간 1개)** 덕분에 한 시간대에 슬롯은 최대 1개다. **겹침이 구조적으로 불가능하므로 "겹친 블록 표현"(구글 캘린더식 열 분할)이 필요 없다.** 이것이 난이도를 한 단계 낮춘다.

**권고 뷰 분할 (3단 구조)**

| 뷰 | 용도 | 1280px 수치 | 모바일(360px) |
|---|---|---|---|
| 월 뷰 (A-03) | 현황 파악·게시 상태·미배정 경고. 날짜 셀에 `슬롯 n개 / 미배정 n` 요약만 | 7열 × 5~6행, 셀 140×96px | 읽기 전용으로 가능 (셀 45×56px, 요약 숫자만) |
| **주 뷰 (A-04)** | **실제 편성 작업의 주 무대** | 시간축 64px + 7열 × **127px**, 행 높이 28px(30분) → 60분 블록 56px, 세로 784px(sticky 시간축·날짜 헤더 필수) | **불가** — 열 폭 40px |
| 일 뷰 | 단건 수정·현장 확인 | 1열, 28행 | **가능** — 세로 타임라인 리스트 |

**슬롯 블록 안에 들어갈 정보**: 유형·강사·정원 3가지. 127×56px에 3정보를 넣으면 한 줄당 약 11~12px 폰트가 되어 **본문 최소 크기(14px) 기준을 깬다.**
→ 권고: 블록에는 **유형 축약 배지 + 강사 이름** 2줄(각 13px)만 두고, **정원·잔여는 포커스/hover 팝오버**와 **상세 패널(A-05)** 에서 보여준다. 13px은 본문이 아닌 **데이터 밀도 영역 전용 토큰**으로 별도 정의하고 대비 4.5:1을 확보한다.

**모바일 대응 의견 — 관리자 화면을 360px까지 대응할지**

| 안 | 내용 | 디자인 공수 | 위험 |
|---|---|---|---|
| **M-1 데스크톱 전용** | 1024px 미만 접근 시 "PC에서 이용해 주세요" 안내 1화면 | 기준(-0일) | 원장이 현장에서 오늘 예약자·신규 상담을 확인할 수 없다. 스마트폰만 쓰는 운영자면 실사용 불가 |
| **M-2 읽기 전용 모바일 (designer 권고 후보)** | 모바일에서는 **대시보드·오늘/이번 주 수업·슬롯별 예약자·상담 신청 목록/상태 변경**만. **편성·템플릿·게시·설정은 1024px 이상 전용** | +1~1.5일 | 운영자가 "왜 여기선 안 되냐"를 물을 수 있어 안내 문구 설계 필요 |
| **M-3 전 기능 모바일** | 편성 그리드까지 360px 대응 | +3~4일 | 30분 그리드 조작을 360px에서 정확히 하기 어렵다. 잘못 배치 → 게시 사고. 접근성(터치 44px)과 정보량이 충돌 |

> **의견**: 관리자 화면의 실사용자는 소수(계정 2개 수준)이고 편성은 책상에서 하는 작업이다. **M-2가 공수 대비 실익이 가장 크다.** 다만 **"모바일 미지원"은 REQ-N-001(360/768/1280 반응형)의 예외**가 되므로, 채택 시 **관리자 영역을 반응형 검증 대상에서 명시적으로 분리**하는 요구사항 개정이 필요하다(→ planner 확인 사항).

### 2.2 회원 월간 캘린더 (M-13) — 상 난이도, **모바일 대응 가능**

**360px 실측 계산**
- 컨테이너 패딩 16px × 2 → 콘텐츠 328px
- 7열, 열 간격 2px × 6 = 12px → **셀 폭 (328-12)/7 = 45.1px**
- 터치 타깃 44×44px(REQ-N-006)를 **1px 여유로 겨우 충족**한다. 패딩을 20px로 올리면 **43.4px로 기준 미달**이 되므로, **캘린더 영역만 좌우 패딩 12~16px로 고정**하는 예외 규칙이 필요하다.
- 셀 높이는 날짜 숫자(16px) + 상태 라벨(11px)을 담아 **56px** 권고 → 6행 = 336px + 요일 헤더 28px.

**날짜 셀 상태 5종** (booking-rules v1.2 §4)

| 상태 | 색 | **색 외 구분 수단(필수)** |
|---|---|---|
| 예약 가능 | 브랜드 강조 | 숫자 아래 **잔여 수 숫자** 또는 점 1개 + `aria-label`에 "예약 가능, 잔여 n자리" |
| 마감 | 중립 | **취소선 또는 사선 해치 패턴** + "마감" 라벨 |
| 휴무 | 연한 중립 | "휴무" 라벨 |
| 미게시 월 | — | 캘린더 대신 **빈 상태 블록** "다음 달 일정은 준비되면 공개됩니다" (※ "준비 중" 문구는 M-5 규칙상 금지 — 표현 대체 필요) |
| 지난 날짜 | 흐림 | `aria-disabled`, 라벨 "지난 날짜" |

→ 45×56px 셀에 11px 라벨을 넣으면 **대비 4.5:1 확보가 관건**이다. P3에서 5종 전부 측정값을 명세에 넣는다.

**768px**: 셀 폭 (720-24)/7 = 99px → 라벨을 12~13px로 키울 수 있다.
**1280px**: 캘린더(좌 560px) + 슬롯 목록(우) **2단 동시 표시**가 가능해 화면 전환이 사라진다. → **M-13·M-14를 1280px에서 한 화면, 360·768px에서 두 단계로 설계**하는 것이 자연스럽다(화면 정의 시 planner와 합의 필요).

### 2.3 슬롯 목록 (M-14) — 중상 난이도, 모바일 대응 가능

- 카드 1장 = 패딩 16×2 + 시간 24px + 유형·강사 20px + 잔여·버튼 44px + 간격 16px ≈ **128px**
- 하루 최대 13슬롯 → **1,664px + 오전/오후 헤더** = 360px에서 약 5화면분 스크롤
- 완화 수단 3가지: ① **오전/오후 분할**(v1.2 §4에 이미 규정) ② **유형 필터 칩**(그룹·키즈·플라잉·로우플라잉·리포머 — 관리자가 유형을 추가하므로 **칩이 6~8개로 늘어날 때의 줄바꿈·가로 스크롤 규칙** 필요) ③ 마감 슬롯 접기(기본 접힘 + "마감 n건 보기")
- **유형이 관리자 관리 대상(B-16-a)이라는 점이 디자인에 직접 영향**을 준다. 유형 배지는 **이름 길이 가변 + 색상 자동 배정**이 되어야 한다. → **유형별 고정 색 팔레트를 designer가 미리 지정할 수 없다.** 권고: **색은 1종(중립 배지)으로 고정하고 유형은 텍스트로만 구분**하거나, **관리자 유형 편집 화면에서 6~8색 팔레트 중 선택**하게 한다(각 색의 대비는 미리 검증된 값만 제공).

### 2.4 그 외 난도 있는 지점

| 화면·상황 | 문제 |
|---|---|
| 예약 확인(M-15) — 동시 예약 실패 | 마지막 한 자리를 놓쳤을 때의 복구 UI. "이미 마감되었습니다" + **같은 날 다른 슬롯 제안**까지 설계해야 이탈을 막는다 |
| 게시 전 검사 결과(A-08) | 미배정 슬롯 목록 → **해당 슬롯으로 바로 이동**하는 링크가 필요. 오류 요약 블록 패턴의 관리자판 |

### 3.3 상태 정의 규모 — **여기가 진짜 공수다**

- **컴포넌트 상태**: 인터랙티브 CMP 약 22개 × 평균 6상태(default/hover/focus/active/disabled/error) = **약 130개 상태 명세**
- **화면 상태**: 데이터가 있는 화면 약 28개 × 5상태(초기 로딩/정상/빈/오류/권한없음 또는 세션 만료) = **약 140개 화면 상태**
- 여기에 **뷰포트 3~4구간**이 곱해진다.
- 현재 8화면 소개형에서는 화면 상태가 화면당 1~2개였다(정적 + 폼 1개). **상태 명세량이 약 15배로 늘어난다.**

> **공수 절감 수단**: ① 상태를 **화면마다 쓰지 않고 "상태 패턴 5종"을 디자인 시스템에 한 번 정의**하고 페이지 디자인에서는 참조만 한다 ② 목업은 각 패턴의 **대표 1개만** 제작한다. 이 방식으로 §5의 추정에서 3~4작업일을 이미 절감한 상태로 계산했다.

## 6. 단계 오픈 시 디자인 전략 — 1차에서 어디까지 확정해야 하나

### 6.1 1차에서 반드시 확정 (안 하면 2차 재작업이 큼)

| # | 1차에서 할 것 | 1차 추가 비용 | 2차 절감 |
|---|---|---|---|
| 1 | **토큰 체계 전량 정의** — 1차에 안 쓰는 상태색 12개·중립 10단·compact 간격·z-index 6단·motion 6종·breakpoint 4구간까지 미리 정의 | +0.5~1일 | **2~3일** (2차에서 팔레트를 다시 짜면 1차 화면 전체 대비 재검증) |
| 2 | **폼 원자 컴포넌트 전량 명세** — 1차는 문의 폼 하나에 3종만 쓰지만 10종 전부 정의 | +1일 | **1.5~2일** |
| 3 | **상태 표현 3중 규칙 확정** (색 + 텍스트 라벨 + 아이콘/패턴) | +0.25일 | 1일 (2차 배지 20종 이상이 이 규칙을 그대로 따름) |
| 4 | **헤더에 "로그인·회원 메뉴" 자리 확보** — 1차는 비로그인 변형만 노출하되 레이아웃 폭·GNB 항목 수를 6~7개 전제로 설계 | +0.25~0.5일 | **0.5~1일** (안 하면 2차에서 헤더·GNB·고정 바를 3구간 전부 재설계) |
| 5 | **고정 바 정책을 "폼이 많은 사이트" 기준으로 재작성** — 현재 G-1~G-11은 8화면 전제다. 2차 화면 30여 개 중 폼·모달·sticky 표 헤더가 고정 바와 겹친다 | +0.25일 | 1~1.5일 |
| 6 | **페이지 셸 규격** (컨테이너 폭·12열 그리드·섹션 간격·1024px 구간) | +0.25일 | 0.5일 |
| 7 | **아이콘 세트 1회 선정** — 2차에 필요한 캘린더·시계·사용자·경고·체크·필터 등을 포함해 라이선스까지 한 번에 확정 | +0.25일 | 0.5일 (세트 교체는 전 화면 재작업) |
| 8 | **빈·로딩·오류 3패턴의 시각 규칙** | +0.25일 | 0.5일 |
| | **합계** | **+3~4일** | **7.5~10.5일** |

→ **1차에 3~4일을 더 쓰면 2차에서 7.5~10.5일을 아낀다.** 순이익 약 4~6.5작업일.

### 6.2 2차로 미뤄도 되는 것

캘린더·30분 그리드·데이터 테이블·모달·토스트·페이지네이션·관리자 셸의 **상세 시각 명세**, 데이터 밀도 스케일의 세부값, 관리자 전용 레이아웃.
(단, 이들이 **존재한다는 전제**는 1차 토큰·z-index·breakpoint에 이미 들어가 있어야 한다.)

### 6.3 가장 중요한 한 가지 — **컨셉 선택 기준**

- 1차만 보고 컨셉을 고르면 **"사진 크게·여백 많이·장식적 타이포"** 계열이 유리해 보인다. 그러나 2차의 캘린더·표·관리자 화면은 **정보 밀도가 높고 사진이 거의 없다.** 이 조합은 2차에서 컨셉 붕괴로 이어진다.
- **권고**: 컨셉 시안 3안 각각에 **"기능 화면 1장"(예약 캘린더 또는 마이페이지 예약 목록)을 포함**하고, 비교표에 **"기능 화면 확장성"** 항목을 넣어 PM이 그 축까지 보고 선택하게 한다. **컨셉 시안 단계 +0.5~1일로 2차 재작업 3~5일을 막는 조치**다.
- 부가 효과: 고객 회신 미확보(Q10 로고·브랜드 색상 / Q21 참고 사이트 / Q11 사진 조달)로 컨셉 시안이 "사진 0장 전제"인 현재 상황에서는, 사진 의존도가 낮은 기능 화면을 함께 보여주는 편이 **오히려 시안의 신뢰도를 높인다**(RSK-010 완화).

## 7. 관리자 화면 디자인 수준 — 선택지

| | **안 A — 공개 사이트 동급** | **안 B — 동일 토큰·기능 위주** | **안 C — 외부 관리자 UI 킷** |
|---|---|---|---|
| 내용 | 관리자도 브랜드 디자인 전면 적용, 일러스트·마이크로 인터랙션 포함 | 공개 사이트와 **같은 토큰**을 쓰되 장식 최소, 정보 밀도 상향, 관리자 전용 레이아웃 | MIT 등 상업 사용 가능한 관리자 컴포넌트 킷 채택, **브랜드 토큰만 덮어쓰기** |

| 접근성 | designer가 전량 책임 | designer가 전량 책임 | **킷 품질에 의존 → 별도 검증 필요**(캘린더·그리드는 킷으로 안 덮인다) |

| 목업 수 | 15~20 | 8~10 (대표 화면만) | 5~6 |

**어느 안을 고르든 공통으로 별도 상세 명세가 필요한 3화면** (킷·축소 스타일로 덮이지 않음):

2. **게시 전 검사 결과(A-08)** — 미배정 슬롯 → 해당 위치 이동

**공통 제안**: 관리자 영역도 **키보드 조작은 필수 기준으로 둔다.** 월 편성은 반복 입력 작업이라 키보드 효율이 실사용 만족도를 좌우하고, 이는 어느 안에서도 designer가 명세해야 한다.

## 9. 요약

- **화면**: 8 → **40~50**. 기존 3화면(SCR-004·005·007)은 수정이 아니라 **폐기·재작성**이다.
- **컴포넌트**: 18~22 → **48~56**(신규 28~34). 다만 실제 공수는 CMP 수보다 **상태 명세 약 270건**(컴포넌트 상태 130 + 화면 상태 140)이 좌우한다.
- **가장 어려운 화면**: **관리자 월 편성 30분 그리드(A-04)**. 다만 **B-15(공간 1개)로 겹침 표현이 불필요**해져 난이도가 한 단계 내려갔다. 월 전체를 한 그리드에 담는 것은 **불가능**하며 월(요약) / 주(편집) / 일(상세) **3단 뷰 분할**이 전제다.
- **관리자 모바일**: **M-2(읽기 전용 모바일 + 편집은 1024px 이상)** 를 권고 후보로 제시. 채택 시 REQ-N-001 예외 명시 필요.
- **P3 공수**: 컨셉 시안 2일 → **2.5~3일**, 상세 디자인 5~6일 → **20~26일**(관리자 안 B). **P3 총 7~8일 → 22~29일.** 현행 G3 10-07은 전체 범위로 성립하지 않는다.
- **단계 오픈 시**: 1차 P3 **9~11일**(G3 1~3일 초과 위험), 2차 P3 13~19일. **1차에 3~4일을 더 써서 토큰·폼 원자·상태 규칙·헤더 자리를 확정하면 2차에서 7.5~10.5일을 아낀다.**
- **관리자 디자인 수준**: 안 A +6~8일 / **안 B +3.5~4.5일** / 안 C +2~2.5일. 어느 안이든 편성 그리드·게시 검사·슬롯 닫기 3화면은 별도 상세 명세가 필요하다.
- **결정 사항 없음.** 위 선택지는 전부 PM 결정 대상이며, designer는 결정 후 P3 산출물에 반영한다.
