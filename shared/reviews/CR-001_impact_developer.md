# CR-001 영향도 의견 (기술) — developer

> **이 문서는 결정하지 않는다.** 스택 확정은 P4 기술 설계, 범위·오픈일 결정은 PM 몫이다. 여기에는 선택지와 근거만 적는다.

## 1. 아키텍처 변화 — 필요한 구성 요소

계획서 v1.0 §7의 "정보 페이지는 정적 사이트, 예약 영역만 서버 측 처리"는 CR-001 수용 시 **성립하지 않는다.** booking-rules v1.2는 로그인 상태에 따라 화면이 달라지고(캘린더·마이페이지·자동 기입), 관리자가 데이터를 상시 편집하며, 정원·겹침 같은 **서버 측 불변 조건**을 강제해야 한다.

| # | 구성 요소 | 왜 필요한가 (근거 규칙) | 새로 생기나 |
|---|---|---|---|
| 1 | **웹 프레임워크(서버 렌더링 또는 API 서버)** | 로그인 상태별 화면, 권한별 라우트, 서버 측 검증 | 신규 |
| 2 | **관계형 DB (Postgres 권장)** | 슬롯·정원·예약의 동시성 제어(§A-5 "한 명만 성공"), 겹침 검사(§A-2-4), 이력 보존(§A-1-1 "비활성만 되고 삭제되지 않는다") | 신규 |
| 3 | **DB 마이그레이션 도구** | 스키마 변경 이력·운영 반영 절차 | 신규 |
| 4 | **인증(비밀번호 저장·세션)** | "로그인한 회원이다"(§A-5-1), 회원 자동 기입(§B-7) | 신규 |
| 5 | **권한 분리(회원 / 관리자)** | 관리자 기능 12종(§C-9), 관리자 계정 2개 | 신규 |
| 6 | **메일 발송 서비스 + 발신 도메인 인증(SPF·DKIM·DMARC)** | 확정·취소·변경·상담·관리자 알림 등 **12종**(§3.3) | 신규(계획서 §7에 조건부로 있던 항목이 필수로 승격) |
| 7 | **파일 저장(객체 스토리지) + 이미지 처리** | 강사 관리의 "사진"(§C-9 강사 관리) | 신규 — **환산치에 없던 항목** |

| 9 | **빈도 제한용 공유 상태 저장소** | 비회원 조회 "10분 10회, 초과 시 10분 차단"(§8-1). 서버리스에서는 인스턴스 메모리로 셀 수 없다 | 신규 |
| 10 | **비밀 정보 관리(환경 변수)** | DB 접속 정보, 메일 API 키, 세션 서명 키 | 신규 |
| 11 | **백업·복구** | 회원·예약·상담 데이터 소실 시 복구 불가 | 신규 |
| 12 | **스테이징(검증) 환경** | 운영 DB에 테스트 데이터를 넣지 않기 위해 필요. 현재 계획서는 운영 스모크 테스트 데이터 삭제 절차만 있다 | 신규 |

**정적 사이트로 남는 부분**: 메인·강사 소개·오시는 길·개인정보 처리방침·404. 이들은 SEO가 필요하므로 **정적 생성(SSG)** 으로 두고, 예약·마이페이지·관리자는 인증이 필요하므로 `noindex`로 분리하는 구성이 가능하다(§2 후보 A·B 모두 지원).

## 2. 기술 스택 후보 비교

### 2.0 비교 전제
- 환율 **1 USD = 1,400원으로 가정**했다(2026-09 기준 **가정값**이며 검증하지 않았다). 카드 결제 수수료·부가세는 별도다.
- 요금제·약관은 **2026-09-12 확인 시점 기준**이며 언제든 바뀐다. **계약 전 재확인이 필요하다.**
- **Vercel Hobby(무료)는 개인·비상업 프로젝트 전용**이다. 상업 사이트이므로 후보에서 제외했다(P1 R1에서 이미 지적).
- 무료 요금제만으로 운영 데이터를 두는 구성은 **권하지 않는다** — 정책 변경·일시 중지·백업 부재 리스크가 고객에게 전가된다.

### 2.1 후보 A — 정적 호스팅(무료) + Supabase(서울) 풀스택  ★비용·리전 균형

| 구성 | 서비스 | 요금 | 리전 |
|---|---|---|---|
| 정적 호스팅·CDN | Cloudflare Pages **Free** (상업 사용 허용, 대역폭 무제한) | 0원 | 글로벌 CDN |
| DB + 인증 + 파일 저장 + 서버 함수 | **Supabase Pro** $25/월 (일시 중지 없음, 일 단위 백업, $10 컴퓨트 크레딧 포함) | 약 35,000원 | **서울 ap-northeast-2 선택 가능** |
| 메일 발송 | **Amazon SES** $0.10/1,000통 (서울 리전 제공) | 월 1,000통 기준 약 **140원** | **서울** |
| **합계** | | **약 35,000원/월** | **개인정보 전부 국내** |

- **장점**: 예산 내(여유 약 15,000원). 개인정보(회원·예약·상담·메일 본문)가 전부 서울에 머물러 **국외 이전 고지 쟁점을 피한다**. Postgres라 동시 예약 정원 처리(§4-1)를 표준 트랜잭션으로 해결할 수 있다. 인증·파일 저장이 포함돼 구현 공수가 줄어든다(-1~1.5작업일).
- **단점**: 서버 렌더링이 아니므로 예약·관리 화면은 클라이언트 렌더링(SPA)이 된다. 데이터 보호를 **RLS(행 수준 보안)** 로 설계해야 하고, 정책을 하나 빠뜨리면 타인 데이터 노출로 이어진다(설계·검토 비용 +0.5작업일, qa 점검 항목 추가). Supabase는 단일 사업자 종속이다.
- 대안: 메일을 Resend Free(3,000통/월, **일 100통 상한**)로 쓰면 비용 0원이지만 발송처가 미국이다. 메일 본문에 이름·예약 일시가 들어가므로 국외 이전 검토 대상이 된다 → SES 서울 권고.

### 2.2 후보 B — Vercel Pro(서울 함수) + Supabase(서울)  ★개발 속도 우선

| 구성 | 서비스 | 요금 | 리전 |
|---|---|---|---|
| 앱(SSR·API) | **Vercel Pro** $20/시트·월 (상업 사용 허용, $20 사용 크레딧 포함, 함수 리전 **icn1 = 서울** 지정 가능) | 약 28,000원 | 서울 |
| DB + 인증 + 파일 저장 | Supabase Pro $25/월 | 약 35,000원 | 서울 |
| 메일 | Amazon SES 서울 | 약 140원 | 서울 |
| **합계** | | **약 63,000원/월 — 예산 5만 원 초과(+13,000원)** | 개인정보 전부 국내 |

- **장점**: 서버 렌더링·서버 액션·미들웨어 권한 분리가 기본 제공되어 **구현 공수가 가장 적다(후보 A 대비 -1~2작업일)**. 인증 상태에 따른 SEO·화면 분기가 단순하다. 배포·프리뷰·롤백이 성숙하다.
- **단점**: **예산 초과.** 시트를 늘리면 월 $20씩 더 든다. 사용량 초과 시 크레딧 소진 후 종량 과금이 붙는다.
- **축소안**: Supabase를 **Free**(서울, 0원)로 내리면 합계 약 28,000원으로 예산 안에 들어오지만, Free는 **7일 무활동 시 프로젝트 일시 중지**되고 **자동 백업이 없으며** DB 500MB 상한이다. 회원 개인정보를 담는 운영 DB에 백업이 없는 구성은 **권하지 않는다.**

### 2.3 후보 C — Cloudflare Workers + D1 (최저 비용)

| 구성 | 요금 | 리전 |
|---|---|---|
| Workers Paid(D1 포함, 무료 요금제도 상업 사용 허용) | $5/월 ≈ **7,000원** | — |
| D1 데이터 위치 | — | **위치 힌트는 `apac`까지만. 서울·한국 지정 불가** |

- **장점**: 압도적으로 싸다. 무료 요금제도 상업 사용을 허용한다.
- **단점(중요)**: ① **개인정보가 국외에 저장된다** → 처리방침에 국외 이전 고지가 필요하다(법률 판단은 고객 몫). 인터뷰의 "서울 리전 선호" 전제와 충돌한다. ② D1은 SQLite 기반이라 **상호작용형 트랜잭션에 제약**이 있어 §4-1(동시 예약 정원)의 설계 난이도가 올라간다. ③ 인증·파일 저장을 직접 구현해야 한다(**+1~1.5작업일**).
- 판단: 비용만 보면 최적이나 **고객 조건(서울 리전) 미충족**이다. 리전 제약을 PM이 완화할 때만 후보로 남는다.

### 2.4 후보 D — 서울 리전 단일 VPS (AWS Lightsail 서울 / NCP / 국내 호스팅)

- 월 $3.5~$10 ≈ **약 5,000~14,000원**. 데이터 완전 국내, 완전 통제.
- **단점**: OS 보안 패치, TLS 인증서 갱신, DB 백업 스크립트, 모니터링, 장애 복구를 **전부 직접 운영**해야 한다. 초기 구축 **+1~2작업일**, 이후 **월 단위 유지보수 인력 필요**.
- 판단: 인터뷰 전제 "고객이 직접 운영"과 정면으로 충돌한다. **유지보수 계약이 전제될 때만** 후보다.

### 2.5 비교 요약

| 기준 | A (CF Pages+Supabase) | B (Vercel Pro+Supabase) | C (CF Workers+D1) | D (서울 VPS) |
|---|---|---|---|---|
| 월 비용 | **약 35,000원** | 약 63,000원 ❌ | 약 7,000원 | 약 5,000~14,000원 |
| 예산 5만 원 | ✅ | ❌ | ✅ | ✅ |
| 개인정보 서울 | ✅ | ✅ | ❌ | ✅ |
| 상업 사용 허용 | ✅ | ✅ | ✅ | ✅ |
| 고객 명의 계정 | ✅ | ✅ | ✅ | ✅ |
| 동시성 처리 난이도 | 낮음(Postgres) | 낮음(Postgres) | **높음(SQLite)** | 낮음 |

## 4. 기술 난이도·리스크 (항목별)

### 4-1. 동시 예약 정원 처리 — 난이도 **높음**, 결함 심각도 Critical 가능
- 규칙: "마지막 한 자리를 두 사람이 동시에 누르면 한 명만 성공해야 한다"(§A-5).
- 애플리케이션 코드에서 `현재 예약 수 조회 → 판단 → INSERT` 로 짜면 **거의 반드시 초과 예약이 난다.** 서버리스는 인스턴스가 동시에 여러 개 뜨므로 프로세스 내 잠금은 무의미하다.
- 권고 설계(P4 확정 대상): ① 단일 트랜잭션 안에서 슬롯 행을 잠그고(`SELECT … FOR UPDATE`) 정원을 검사하거나, ② `INSERT … SELECT … WHERE (SELECT count(*) …) < capacity` 로 원자화하고, ③ `(slot_id, member_id)` **부분 유니크 인덱스**로 중복 예약을 DB 차원에서 막는다. 취소된 행은 유니크 대상에서 제외해야 재예약이 가능하다.
- **DB 선택에 직결된다.** Postgres(후보 A·B·D)는 위 방식이 표준이다. **D1/SQLite(후보 C)는 상호작용형 트랜잭션에 제약**이 있어 설계를 다시 짜야 한다.
- 검증: 동시 요청 N개를 쏘는 부하 스크립트가 필요하다. **qa와 검증 수단을 합의해야 한다**(현재 테스트 계획에 이런 케이스가 없다).

### 4-2. 예약번호·신청번호 무작위성 — 난이도 **낮음**, 이미 설계 합의됨
- P2 R1 부록 A에서 확정한 방침 유지: **CSPRNG + 40비트 이상(Base32 8자)**, Crockford 치환(O→0, I/L→1), 충돌 시 재시도.
- **추가 의견**: 레슨(§A-5)과 상담(§B-7)이 **같은 발급 로직을 쓰되 접두어를 분리**할 것을 권고한다(예: `YL-…` / `YC-…`). 접두어가 같으면 비회원 조회 창구에 레슨 예약번호를 넣는 오조회가 생기고, 응답 동일화 규칙(§8-1)과 얽혀 사용자 안내가 어려워진다. **0.1작업일 이내.**
- URL 쿼리스트링·서버 로그·분석 도구에 번호를 남기지 않는 규칙(REQ-N-R-010)은 그대로 유지한다.

### 4-3. 비회원 조회 빈도 제한 — 난이도 **중간**, **구성 의존**
- "10분 10회, 초과 시 10분 차단"(§8-1)은 **요청 간 공유되는 상태 저장소**가 있어야 성립한다. 서버리스 인스턴스 메모리로는 셀 수 없다(P2 R2 #5에서 지적한 것과 같은 유형).
- 선택지: (a) DB 테이블(가장 단순, 쓰기 부하 발생) (b) Redis/KV 등 별도 저장소(비용·구성 추가). 후보 A·B는 (a)가 현실적이다.
- **제한 키를 무엇으로 잡을지 결정이 필요하다.** IP만 쓰면 공용망(스튜디오 와이파이·회사망) 이용자가 함께 차단되고, 신청번호만 쓰면 번호를 바꿔 가며 시도하는 공격을 못 막는다. **IP와 신청번호 양쪽에 각각 건다**는 안을 권고한다.
- 응답 **시간** 동일화는 "같은 문구·같은 응답 시간"(§8-1) 규칙의 핵심인데 DB 조회 유무에 따라 시간이 갈린다. 고정 최소 지연(예: 300ms)을 두는 방식이 가장 단순하다. **측정 절차를 qa와 합의해야 한다**(P2 R1·R2에서 이미 올린 항목).

### 4-4. 비밀번호·세션 보안 — 난이도 **중간**, 누락 시 Critical
- 비밀번호: **bcrypt(cost ≥ 12) 또는 argon2id**. 직접 해싱을 구현하지 않고 검증된 라이브러리를 쓴다.
- **계정 열거 방지**: 가입·로그인·비밀번호 재설정 세 곳 모두 "그 이메일이 존재하는지" 알 수 없게 응답을 동일화해야 한다. 상담 조회 동일화(§8-1)와 같은 원리인데 규칙 문서에는 회원 쪽 언급이 없다 → **기획 보강 필요**.
- 세션: HttpOnly·Secure·`SameSite=Lax` 쿠키, **로그인 성공 시 세션 ID 재발급**(세션 고정 방지), 절대 만료 + 유휴 만료, 비밀번호 변경·탈퇴 시 전 세션 무효화.
- 비밀번호 재설정 토큰: 1회용·짧은 만료(예: 30분)·해시 저장.
- 로그인 시도 제한: 계정 단위 + IP 단위(§4-3과 같은 저장소 사용).
- CSRF: 상태 변경 요청 전부에 토큰 또는 `SameSite` + Origin 검증.

### 4-5. 권한 분리(회원/관리자) — 난이도 **중간**, 누락 시 Critical
- 라우트 가드만으로는 **부족하다.** 데이터 접근 지점마다 **소유자 검사**가 필요하다(IDOR 방지). 예: 마이페이지에서 예약 ID만 바꿔 남의 예약을 취소할 수 있으면 안 된다.
- 후보 A(Supabase RLS)를 고르면 이 검사를 **DB 정책으로 일괄 강제**할 수 있어 누락 위험이 준다. 대신 정책 설계·검토 비용이 붙고, 정책 자체를 빠뜨리면 반대로 전면 노출이 된다.
- 관리자 계정 2개의 **권한 차등 여부가 미정**이다(ITV-002 §7에 이미 올라 있음). 동일 권한이면 설계가 단순하고, 차등이면 역할 테이블이 필요하다(+0.25~0.5작업일).
- 관리자 경로는 `noindex` + 별도 경로로 두되, **robots.txt에 관리자 경로를 나열하면 오히려 위치를 알려 주므로** `Disallow`로 적지 않는다(P2 R1 #3과 같은 논지).

### 4-6. 개인정보 보관·파기 — 난이도 **중간**, **기획·법률 의존**
- 새로 보관하는 항목: 회원(이름·연락처·이메일·비밀번호 해시), 레슨 예약 이력, 상담 신청(비회원 포함), 경고 기록, 접근 로그.
- **항목별 보관 기간 표가 없으면 파기 배치를 만들 수 없다.** planner·고객 법률 판단이 필요하다.
- **탈퇴 시 예약 이력 처리(즉시 삭제 vs 익명화 후 보존)가 미정**이다(ITV-002 §7). 즉시 삭제면 슬롯별 예약자 수 집계가 깨지고, 익명화면 익명화 로직이 필요하다.
- 건강 정보를 받지 않기로 한 결정(C-3)은 **민감정보 처리 부담을 실제로 크게 줄인다**. 기술적으로도 유리한 결정이다.
- 위탁(호스팅·DB·메일 사업자)·국외 이전 고지가 처리방침에 반영되어야 한다 → **후보 선택과 처리방침 문안이 연동된다.**

### 4-7. 메일 발신 인증 — 난이도 **중간**, **DNS 리스크**
- SPF·DKIM·DMARC가 없으면 12종 메일이 스팸함으로 간다. 예약 확정 메일이 닿지 않으면 기능 자체가 무의미해진다.
- **기존 회사 메일 레코드가 있으면 SPF를 병합**해야 하며, 잘못 쓰면 **기존 회사 메일 수·발신이 끊긴다**(RSK-012). 기존 레코드 백업 → PM 승인 → 적용 → 수발신 확인 순서를 지킨다.
- **적용 시점을 오픈 직전에 몰지 않는다**(계획서 §4.1의 10-22 운영 환경 준비 단계 유지). DNS 전파 지연이 있다.
- DMARC는 `p=none`으로 시작해 보고를 보고 조정한다.

### 4-8. 월 편성 화면 UI — 난이도 **높음**, **단일 화면 중 최대**
- 한 화면에 동시에 얹히는 규칙: 06:00~20:00 **30분 그리드 28행**, 유형별 가변 길이(60·90분), 종료 시각 자동 계산, 운영 종료 초과 금지, **시간 겹침 금지(공간 1개)**, **같은 강사 동시간 중복 금지**, 정원 지정, 11:00~13:00 기본 비움, 템플릿 적용, 공휴일 수동 수정, 미배정 검사, 게시 전 미리보기.
- **드래그 앤 드롭 편집은 권하지 않는다.** 구현·검증 비용이 크고(+0.75~1.5작업일) **키보드만으로 조작할 수 없어 접근성 기준(WCAG 2.1 AA)을 맞추기 어렵다.** 대안은 **폼·목록 기반 편집 + 그리드는 읽기 전용 시각화**다.
- 겹침 검사는 **화면(즉시 피드백)과 서버(최종 강제) 양쪽**에 있어야 한다. 화면에만 두면 API 직접 호출로 겹치는 슬롯이 생긴다.
- 이 화면은 **디자인 명세 의존도가 가장 높아** 병렬 선착수가 어렵다(§6.2).
- **designer에게 전달할 사항**: 28행 그리드의 1280px·768px 레이아웃, 슬롯 블록의 60분/90분 높이 차이, 충돌 상태 표시, 미배정 경고 표시가 디자인 명세에 필요하다. 없으면 P4에서 추측하게 된다.

## 5. 단계 오픈 시 기술 구성과 전환 비용

### 5.1 방안 1 — 1차 정적(10월 말) → 2차 서버 구성

전환 비용은 **1차를 무엇으로 만드느냐에 따라 약 2~3배 차이가 난다.**

| 1차 구현 방식 | 2차 전환 작업 | 전환 비용 |
|---|---|---|
| **(가) 2차와 같은 프레임워크로 만들고 정적 출력만 한다** (권고) | 빌드 모드 전환·호스팅 설정, 헤더에 로그인/마이페이지 진입점 추가, 정적 콘텐츠(수업 안내·운영 시간)를 DB로 이관, 2차 배포 후 1차 페이지 회귀 확인 | **0.75 ~ 1.75작업일** |
| (나) 1차를 별도 SSG(순수 HTML 또는 다른 도구)로 만든다 | 위 + **레이아웃·컴포넌트 재작성**, 디자인 토큰 재적용, SEO 메타 재구성 | **1.5 ~ 3작업일** |

세부 내역 ((가) 기준):

| 항목 | 작업일 |
|---|---|
| 빌드·호스팅 전환, 환경 변수 구성 | 0.25 |
| 헤더·모바일 메뉴·하단 고정 바에 로그인/마이페이지 진입점 추가 (**디자인 변경 동반** — designer 몫 별도) | 0.25~0.5 |
| 정적 콘텐츠 파일 → DB 테이블 이관(수업 안내·운영 시간·강사) | 0.25~0.5 |
| 2차 배포 시 1차 페이지 회귀 확인 | 0.25~0.5 |
| (qa 몫 별도) 1차 범위 회귀 테스트 | +1 |

> 오케스트레이터가 ITV-002 §4에 적은 **"전환 작업 0.5~1일"은 (가) 방식 전제에서만 성립**한다. 1차를 다른 스택으로 만들면 값이 커진다. 방안 1을 고르면 **1차 착수 전에 2차 스택을 먼저 정해야 한다** — 이것이 방안 1의 가장 중요한 기술 조건이다.

부수 효과:
- 1차에서 디자인·도메인·DNS·배포 파이프라인을 확정해 2차 위험이 준다(오케스트레이터 서술에 동의).
- 1차 문의 폼을 폼 전송 서비스로 두면 2차에 DB 저장으로 바뀌면서 **개인정보 저장처가 바뀐다 → 처리방침 개정과 1차 접수 건 이관 문제**가 생긴다(계획서 S-3에 이미 적힌 논점). 1차부터 (가) 방식 + 최소 DB를 쓰면 이 문제가 없어지지만 그러면 사실상 §5.2가 된다.
- **유료 요금제 과금이 2차 시점부터 시작**되어 약 1.5~2개월치(월 3.5~5만 원 기준 약 5~10만 원)를 아낀다.

### 5.2 방안 2 — 처음부터 서버 구성으로 1차를 만든다

| 항목 | 영향 |
|---|---|
| 전환 비용 | **0** |
| 1차 공수 | 공통 정적 4.5~5.5 + **기반·인프라 2~2.5** = **6.5~8작업일** |
| 현행 WBS P4 구현 배정(3.5~4일) 대비 | **-3 ~ -4작업일 부족** → 1차 오픈이 최소 **3~4작업일 순연** |
| 비용 | 유료 요금제가 1차 시점부터 과금(약 1.5~2개월 조기, 약 5~10만 원) |
| 개인정보 | 1차부터 DB에 문의 내역이 쌓임 → **처리방침·보관·파기·백업 책임이 1차부터 발생** |
| 외부 계정 | 계정 생성 PM 승인·고객 명의 준비가 1차 일정의 주요 경로로 들어옴(계획서 S-1 전제 조건 2와 같은 구조) |

### 5.3 비교

| 기준 | 방안 1 (가) | 방안 2 |
|---|---|---|
| 1차 오픈일 | 빠름 (다만 공통 정적만으로도 4.5~5.5일 필요 — 현행 배정 3.5~4일보다 이미 부족) | 3~4작업일 더 늦음 |

## 6. P4 일정에 미치는 영향

### 6.1 현행 WBS 대비

| 항목 | 계획서 v1.0 WBS | CR-001 수용 시 필요 | 배수 |
|---|---|---|---|
| P4 기술 설계 (10-08~10-12) | 약 2작업일 | 2.5~3.5 | ×1.3~1.8 |
| P4 구현 (10-12~10-15) | 실질 3.5~4작업일 | **35.5~51.25** | **×9~14** |
| P5 검증·수정 (10-19~10-21) | 3작업일 | 4~6 | ×1.3~2 |
| **P4+P5 developer 총계** | **약 9작업일** | **42~60.75** | **×4.7~6.8** |

- 1인 기준 달력 환산(주 4.7작업일, 공휴일 반영): **약 9~13주**.
- 전체 일괄 오픈 시 P4 착수(10-08 가정) 기준으로 **12월 중순 ~ 2027년 1월 상순**에 오픈된다. ITV-002 §3의 "12월 15일 ~ 2027년 1월 6일"과 **대체로 일치**하며, 내 재추정은 그 범위의 **후반부**를 가리킨다.

### 6.2 병렬(선착수) 가능 구간

단일 에이전트 구조에서는 **총량이 줄지 않는다.** "병렬"은 디자인 확정(G3)을 기다리지 않고 먼저 착수할 수 있는 구간을 뜻한다(계획서 O-6의 확장).

| 구간 | 디자인 의존 | 선착수 가능 시점 | 분량 |
|---|---|---|---|
| 기반·인프라(#0), 회원·인증 서버 측(#2 일부), 보안·파기 배치(#10), 메일(#9), 통합·환경(#11) | **낮음** | 요구사항 확정(G2 재승인) 직후 | **약 9 ~ 12.5작업일** |
| 동시 예약 정원 로직, 겹침·중복 검사, 예약 성립 조건(#3·#4의 서버 측) | 낮음 | 같음 | 약 3 ~ 4.5작업일 |
| 캘린더 UI, 마이페이지, 월 편성 그리드, 관리자 화면 전반(#3·#4·#5·#6·#7의 화면) | **높음** | G3 이후 | 약 20 ~ 30작업일 |
| 상담 신청 폼·조회 창구 화면 | 중간 | G3 이후(폼 구조가 단순해 일부 선행 가능) | 약 2 ~ 3작업일 |

- **선착수 효과의 상한은 약 12~17작업일**이다. 이를 모두 살려도 전체 일정이 절반으로 줄지는 않는다.
- **디자인 의존을 줄이는 유일한 실질 수단**: **관리자 화면(#4·#6·#7, 약 11~17작업일)의 디자인 명세를 "기능 우선·최소 스타일 + 데스크톱 1280px 전용"으로 합의**하는 것이다. 관리자 화면은 고객 내부 전용이라 대외 이미지 영향이 없다. 이 합의가 되면 선착수 가능 구간이 크게 늘고 designer 작업량도 준다. **designer·planner·PM 협의 사항**이며 내가 결정할 수 없다.
- qa의 테스트 계획·케이스 선작성은 이미 계획된 병렬 구간이다(계획서 §4.1). 단, **동시성·권한·개인정보 파기 검증 수단**은 기술 설계가 나와야 구체화되므로 기술 설계 완료 후로 잡아야 한다.

## 7. 운영 비용·유지보수 (고객이 직접 운영할 때)

### 7.1 월 고정 비용

| 후보 | 월 비용 | 예산(5만 원) |
|---|---|---|
| A | 약 35,000원 | 여유 약 15,000원 |
| B | 약 63,000원 | **초과 13,000원** |
| C | 약 7,000원 | 여유 크나 리전 조건 미충족 |
| D | 약 5,000~14,000원 | 여유 크나 운영 부담 큼 |

- 도메인 갱신비(연 1~2만 원대)는 별도다.
- **사용량이 늘면 비용이 오른다.** 특히 후보 B는 크레딧 소진 후 종량 과금이 붙는다. 요가 스튜디오 1곳 규모에서는 한도 내에 머물 가능성이 높지만 **예측이 아니라 모니터링으로 확인해야 한다.**

| 작업 | 고객 직접 | 비고 |

## 11. 정리

1. CR-001은 **범위 변경이 아니라 프로젝트 성격의 변경**이다. 정적 소개 사이트 제작이 회원제 웹 애플리케이션 개발이 된다.
2. 구현 공수는 **35.5~51.25작업일(±30%)** 로, 오케스트레이터 환산치(32.5~45.5)보다 **3~5.75일 크다.** 다만 환산치는 단순히 작은 것이 아니라 **중복 4.5~6일과 누락 9.25~14일이 섞여** 있다(§3.2).
3. 고객 조건 네 가지(예산 5만 원·서울 리전·상업 사용·직접 운영)를 **모두 만족하는 스택은 후보 A(약 월 35,000원)** 뿐이다. 개발 속도를 사면 후보 B(월 63,000원, 예산 초과)다. **확정은 P4 기술 설계에서 한다.**
4. 단계 오픈의 전환 비용은 **1차·2차를 같은 프레임워크로 만들면 0.75~1.75작업일**로 작다. 방안 1을 고른다면 **1차 착수 전에 2차 스택을 먼저 정해야 한다.**
5. 어느 방안이든 **현행 WBS의 P4 구현 배정(3.5~4작업일)은 1차 범위만으로도 부족**하다. 이는 CR-001과 무관하게 이미 존재하는 격차다(P2 R2 부록 A).
6. **결정은 하지 않았다.** 스택·범위·오픈일 결정은 PM과 P4 기술 설계의 몫이다.
