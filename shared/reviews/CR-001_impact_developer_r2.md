# CR-001 영향도 의견 R2 (기술) — developer

> **이 문서는 결정하지 않는다.** 스택 확정은 P4 기술 설계, 범위·오픈일 결정은 PM 몫이다. 선택지·근거·공수만 적는다.
> **웹 검색을 하지 않았다** (PM 지시: 호스팅은 이미 보유). 일반 기술 지식과 기존 문서만으로 판단했다.
> **명령 실행·의존성 설치·코드 작성을 하지 않았다.** 아래 공수는 문서 분석에 의한 추정이며 **±30%** 불확실하다.
> 이전 의견서(`CR-001_impact_developer.md` v0.1)는 **수정하지 않았다.** 이 문서가 무효 구간을 표기하고 나머지를 이어받는다.

**핵심 판단 3줄**

1. 공수는 **줄지 않고 늘었다**. 관리형 서비스가 대신 해 주던 것(DB 운영·인증·백업·프록시·인증서·스케줄러)을 전부 우리가 만들어야 하기 때문이다. 줄어든 것은 **비용과 일정 차단 요인(계정 준비)** 이지 작업량이 아니다.
2. 반대로 **비용·리전·약관·사업자 종속 리스크가 통째로 사라졌다.** R1에서 "네 조건을 모두 만족하는 스택은 후보 A뿐"이라고 좁혔던 제약이 없어져 **스택 선택 자유도가 크게 올라갔다.** 이것이 이 전제의 가장 큰 이득이다.
3. **PostgreSQL 권고는 타당하다.** 다만 infra 문서에 적힌 두 가지(슬롯 겹침·중복 접수) 외에 **"같은 강사 동시간 중복 배정 금지"도 같은 제약 하나로 해결된다** — 권고 근거가 문서보다 하나 더 강하다 (§2.2).

## 2. DB 권고 검토 (I-3)

### 2.1 결론 — **PostgreSQL 권고에 동의한다**

infra-constraints §4의 논거(슬롯 겹침 배제 제약, 취소 건 제외 조건부 유니크 인덱스)는 **정확하고 타당하다.** 내가 R1 §4-1에서 독립적으로 도출한 설계 방향(부분 유니크 인덱스 + 트랜잭션 내 원자적 정원 검사)과 일치한다.

### 2.2 권고 근거 보강 — infra 문서에 없는 이점 2가지

| # | 이점 | 설명 |
|---|---|---|
| **①** | **"같은 강사 동시간 중복 배정 금지"(booking-rules §3.3)도 같은 제약 하나로 해결된다** | 배제 제약을 `(instructor_id WITH =, 시간범위 WITH &&)` 로 걸면 끝난다. infra 문서는 슬롯 겹침만 들었지만 booking-rules에는 **강사 중복 금지라는 두 번째 겹침 규칙**이 있다. 배제 제약이 **두 규칙을 같은 방식으로** 막는다 |
| **②** | **공간이 늘어나도 설계가 안 깨진다** | 지금은 "공간 1개"(B-15)지만 스튜디오가 방을 늘리면 제약 키에 `room_id WITH =` 만 추가하면 된다. 애플리케이션 검사 방식이면 잠금 범위 설계를 다시 짜야 한다 |

### 2.3 PostgreSQL 선택 시 주의점 (P4 설계에 반드시 반영)

| # | 주의점 | 대응 |
|---|---|---|
| 1 | 배제 제약에는 **`btree_gist` 확장이 필요**하다 | 공식 postgres 이미지에 포함돼 있으나 확장 생성 마이그레이션이 별도로 필요 |
| 2 | **취소 건 제외**를 하려면 제약·인덱스에 상태 조건이 붙는다 (부분 배제 제약·부분 유니크 인덱스) | 예약·상담의 **상태 값 정의가 먼저 확정**돼야 한다 |
| 3 | **ORM(Prisma·Drizzle 등)은 배제 제약과 부분 인덱스를 표현하지 못한다** | 해당 마이그레이션만 **raw SQL로 손으로 작성**해야 한다. 스키마 드리프트 관리 절차 필요 (+0.25) |
| 4 | 제약 위반은 **DB 예외**로 올라온다 | 사용자에게 "이미 예약된 시간입니다"로 번역하는 오류 매핑이 필요하다 (+0.1~0.25) |
| 5 | **DB 제약이 애플리케이션 검사를 대체하지 않는다** | 편성 화면은 "저장 전 즉시 피드백"이 필요하므로 애플리케이션 검사가 여전히 있어야 한다. DB 제약은 **최종 안전망**이다. 이 때문에 PostgreSQL 선택으로 줄어드는 공수는 **-0.25~0.5로 작다** |
| 6 | 운영자의 숙련도 | **PostgreSQL 백업·복구를 운영자가 못 다루면 백업이 안 돌아간다.** 이것이 마지막 판단 기준이다 → I-7-a와 묶어 확인 필요 |

### 2.4 MariaDB(MySQL)를 고를 경우 추가 공수

infra 문서는 **+0.5~1작업일**로 봤다. 나는 **+1.0 ~ +2.0작업일**로 본다. 내역은 아래와 같다.

| # | 추가 작업 | 공수 |
|---|---|---|
| 1 | **슬롯 겹침 검사를 애플리케이션에서 구현** + 동시 편성 대비 잠금 설계 (날짜 단위 행 잠금 또는 잠금 테이블) | +0.5 ~ 0.75 |
| 2 | **강사 중복 배정 검사**를 같은 방식으로 한 번 더 구현 (§2.2 ①) | +0.25 |
| 3 | **취소 건 제외 유니크** 우회 — 생성 컬럼(취소 시 NULL이 되도록 만들고 NULL 중복 허용을 이용) + 유니크 인덱스. 상담 중복(C-6)과 슬롯 내 회원 중복 예약 **두 곳** | +0.25 ~ 0.5 |
| 4 | **동시 요청 테스트 케이스 설계·자체 확인** (동시 예약 정원, 동시 편성 겹침) — developer 몫. qa 몫은 별도 | +0.25 ~ 0.5 |
| 5 | 편성 일괄 편집 시 **잠금 경합·데드락 대응**(재시도 로직) | +0 ~ 0.25 |
| | **합계** | **+1.0 ~ +2.0** |

> infra 문서와의 차이는 ②(강사 중복)와 ⑤(데드락)를 세지 않았기 때문이다. 큰 차이는 아니며 **MariaDB가 불가능하다는 뜻이 아니다.** 1~2작업일을 내고 운영자에게 익숙한 DB를 쓰는 것도 합리적 선택이다. PM·운영자가 판단할 사항이다.

## 4. 스택 구성안 (확정하지 않음 — P4 기술 설계 입력)

공통 전제: 리눅스 8코어 16GB 단일 서버, docker-compose, PostgreSQL, SMTP, 운영자 있음.
**8코어 16GB는 이 규모(요가 스튜디오 1곳)에 충분하며, 운영 + 스테이징을 같은 서버에 올려도 여유가 있다**고 본다 (I-8 관련).

### 4.1 구성 ① — Node.js 풀스택 SSR 단일 앱 (기준선)

| 계층 | 선택 | 비고 |
|---|---|---|
| 앱 | **SSR 프레임워크 1개** (Next.js / Remix / SvelteKit 중 택1) — 소개 페이지는 정적 생성, 예약·마이페이지·관리자는 서버 렌더링 | 컨테이너 1개. 언어 하나로 끝난다 |
| DB | **PostgreSQL** 컨테이너 + 명명 볼륨 | 배제 제약·부분 유니크 인덱스 사용 |
| 마이그레이션 | Prisma / Drizzle + **raw SQL 마이그레이션 병용** | §2.3 ③ |
| 리버스 프록시 | **기존 프록시 재사용이 1순위** (I-2). 없으면 Caddy(인증서 자동) 또는 Nginx + certbot | #0c 하한/상한을 가르는 항목 |
| 세션·빈도 제한 | 앱 인스턴스 1개면 **DB 테이블**로 충분. 복제하거나 성능이 문제되면 Redis 컨테이너 추가 | 처음부터 Redis를 넣지 않는 쪽을 권한다 (운영 요소 최소화) |
| 메일 | **SMTP 직접 발송.** 로컬은 Mailpit/MailHog 컨테이너 | 발송 로그 테이블 + 실패 재시도는 직접 |
| 배치 | **별도 스케줄러 컨테이너**(cron 이미지 → 앱 CLI 호출) 또는 호스트 crontab → compose 명령. **앱 내 인메모리 스케줄러는 비권고**(재시작 시 실행 누락) | 미게시 알림·자동 파기 |
| 파일 저장 | **호스트 바인드 볼륨** + 프록시가 직접 서빙 | 백업 대상에 포함 |
| 컨테이너 수 | 앱 · DB · [프록시] · [스케줄러] = **2~4개** | 최소 구성 |

- 장점: 단일 언어·단일 앱. SSR로 "로그인 상태 분기 + SEO"를 동시에 해결. 컨테이너 수가 적어 운영이 단순하다.
- 단점: 관리자 기능 12종의 화면을 **전부 직접 만든다**(#7 3.75~5.5 그대로). ORM이 DB 제약을 표현 못 해 마이그레이션 일부 수작업.

### 4.3 선택 기준 (P4에서 판단할 것)

| # | 기준 | 설명 |
|---|---|---|
| 1 | **I-2 — 기존 compose에 이미 있는 런타임** | 이미 Node 또는 Python 스택이 돌고 있으면 그쪽으로 맞추는 것이 운영 부담이 적다. **이 항목이 먼저 확인돼야 한다** |

## 5. 단계 오픈 전환 비용 재산정

R1 §5는 "1차를 2차와 같은 프레임워크로 만드느냐"만 따졌다. compose 전제에서는 **"1차에 인프라를 어디까지 세우느냐"** 가 새 변수다. 세 가지를 비교한다.

### 5.1 세 방식 비교

| 방식 | 1차(소개형) 공수 | 2차 전환 비용 | 1차 오픈 시점 | 총량 |
|---|---|---|---|---|
| **(가) 2차와 동일한 full compose** (앱·DB·프록시·백업까지) | #1 4.5~5.5 + #0 일부 1~1.25 + #0b 1.25~2 + #0c 0.5~1 + #11 일부 0.75~1.25 = **8.0 ~ 11.0** | 헤더 진입점 0.25~0.5 + 정적 콘텐츠→DB 이관 0.25~0.5 + 회귀 확인 0.25~0.5 = **0.75 ~ 1.5** | 가장 늦음 | 기준 |
| **(나) 같은 compose, DB 없이** (앱·프록시만) ★절충 | #1 4.5~5.5 + 스캐폴딩 0.75~1 + compose(앱·프록시) 1.0~1.5 + 배포 절차 0.5~1 = **6.75 ~ 9.0** | DB·세션·백업 추가 0.75~1.25 + 헤더·콘텐츠 이관·회귀 0.75~1.5 = **1.5 ~ 2.75** | 중간 ((가) 대비 **-1.25 ~ -2.0**) | +0.75 ~ +1.25 |
| **(다) 순수 정적** (HTML/SSG 산출물을 기존 웹 서버에 얹음) | #1 4.5~5.5 + 정적 빌드·배포 0.5~0.75 = **5.0 ~ 6.25** | 레이아웃·토큰·SEO 재적용 1.0~2.0 + 회귀 0.25~0.5 = **1.25 ~ 2.5** <br>※ compose·DB·백업 구축 4.25~7은 전환 비용이 아니라 **2차로 이월** | 가장 빠름 ((가) 대비 **-3.0 ~ -4.75**) | +1.25 ~ +2.5 |

### 5.2 판단

- **일정만 보면 (다)가 가장 빠르다** — 1차를 (가) 대비 **3.0~4.75작업일** 앞당긴다.
- **그러나 (다)의 진짜 비용은 작업일이 아니라 리스크다.** compose 구성·프록시·HTTPS·배포·백업을 **한 번도 검증하지 않은 채 2차로 넘긴다.** 미확인 인프라 항목(I-2·I-4·I-6·I-8)이 **전부 2차 오픈 직전에 터지게 된다.**
- **(나)가 절충으로 가장 합리적으로 보인다.** 1차에 compose·프록시·HTTPS·배포 절차를 **실제로 한 번 돌려 보면서**(= I-2·I-4·I-6을 실물로 검증하면서) DB·백업이라는 가장 무거운 부분만 2차로 미룬다. (가) 대비 1.25~2.0작업일 빠르고 (다) 대비 인프라 리스크가 크게 낮다.
- **1차에 문의 폼을 넣으면 (나)는 성립하지 않는다.** 문의 내역을 저장해야 하므로 DB가 1차부터 필요하다(또는 메일 발송만 하고 저장하지 않는 방식). 이 결정은 planner·PM 몫이다 (R1 §5.1 부수 효과와 같은 논점).
- **R1 대비 변화**: 호스팅 이관이 없어져 "1차를 다른 스택으로 만들 때의 전환 비용"이 R1의 1.5~3에서 **1.25~2.5로 소폭 감소**했다. 그러나 **인프라 구축분(4.25~7)이 2차로 이월**되므로 총량 부담은 오히려 커졌다.
- **결정하지 않는다.** PM 선택지로 제시한다.

## 9. 정리

1. **공수는 늘었다.** P4 구현 **39.0~57.25작업일**(R1 35.5~51.25 대비 **+3.5~6.0**), P4+P5 총계 **46.0~67.25작업일**(R1 42~60.75 대비 **+4.0~6.5**), 1인 약 **10~15주**. 증가분은 compose 구성(+1.25~2), 백업·배포·복구·스테이징(+1.5~2.5), 인증 직접 구성(+0.5~1), 프록시·HTTPS(+0.5~1)에서 나온다.
2. **대신 신규 월 고정비가 사실상 0이 됐고 요금제·리전·약관·사업자 종속 리스크가 통째로 사라졌다.** 개인정보가 전부 자기 서버에 남는 것도 명확한 이득이다. **이 교환은 이 프로젝트에 유리하다고 본다.**
3. **PostgreSQL 권고에 동의한다.** 근거는 infra 문서보다 하나 더 있다 — **강사 동시간 중복 배정도 같은 배제 제약으로 막힌다.** MariaDB를 고르면 **+1.0~2.0작업일**(infra 문서의 +0.5~1보다 크다. 근거 §2.4). 마지막 판단 기준은 **운영자가 어느 DB의 백업·복구에 익숙한가**다.
4. **스택 구성안 2개를 제시했다** — ① Node.js SSR 단일 앱(기준선) ② Django 계열 + 내장 관리자 활용(**-2.0~3.25작업일**, 관리자 화면 디자인 의존도까지 낮아짐). **확정하지 않았다.** I-2 답변과 운영자 언어 숙련도로 P4에서 판단한다.
5. **단계 오픈은 (나) "같은 compose, DB 없이"가 절충으로 가장 합리적**으로 보인다. 1차에 인프라를 실제로 한 번 돌려 보면서 I-2·I-4·I-6을 실물로 검증하고 가장 무거운 DB·백업만 2차로 미룬다. (다) 순수 정적은 3.0~4.75작업일 빠르지만 **인프라 리스크가 전부 2차 오픈 직전으로 몰린다.**
6. **P4 착수를 실제로 막는 것은 I-2(현재 compose 구성)와 I-4(도메인·HTTPS 처리 방식) 둘뿐이다.** I-8은 테스트 계획 전, **I-5-a(SPF·DKIM 가능 여부)는 비차단이지만 늦게 밝혀지면 메일 기능 설계 자체가 뒤집히므로 조기 확인을 강하게 권고한다.**
7. **결정은 하지 않았다.** 스택·DB·범위·오픈일·1차 인프라 범위는 PM과 P4 기술 설계의 몫이다. **티켓은 발행하지 않았다** — CR-001이 아직 분석 단계이고 planner와 항목이 겹친다. PM 결정 후 남는 것만 올린다.
