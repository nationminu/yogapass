# CR-001 영향도 의견 — 기획 관점

## 0. 이 문서의 성격과 전제

- **결정 문서가 아니다.** 범위 수용 여부·오픈일·단계 오픈 방안은 PM이 정한다. 이 문서는 선택지와 그 영향만 제시한다.
- **기능 정의의 기준은 `interviews/2026-09-12_booking-rules.md` v1.2** 하나다. 같은 폴더의 `2026-09-12_customer-interview.md`·`2026-09-12_summary-and-options.md`는 **가상 인터뷰·오케스트레이터 초안**이며, 이 문서는 그 안의 고객 답변을 사실 값으로 인용하지 않고 "가정"으로만 다룬다. 공수·일정 수치도 developer 검토 전 1차 환산치로 취급한다.
- **기획 산출물(`planning/02_*.md`)은 이번 작업에서 수정하지 않았다.** 세 문서는 v0.4 · in-review 상태 그대로다.
- **추정의 불확실성**: 아래 건수·작업일은 현재 116건·8화면 산출물의 밀도(화면당 기능 REQ 약 5~7건, 문서 총 1,500여 줄)를 기준선으로 한 환산이며, 별도 표기가 없으면 **±25~30%** 로 읽는다. PM 결정과 고객 확인(§6 R-2)에 따라 범위가 더 움직인다.

## 1. 영향 받는 기존 요구사항

### 1.1 전체 판정 요약 (현행 116건)

| 판정 | 건수 (추정) | 비중 | 뜻 |
|---|---|---|---|
| **유지** — 문구 손대지 않음 | **50~58** | 43~50% | 소개형 공통 영역(메인·강사·오시는 길·처리방침·404·대부분의 SEO/접근성) |
| **변경** — 요구사항은 살아 있고 전제·대상·수용 기준이 바뀜 | **57~64** | 49~55% | 예약 영역 27건 + 공통 영역 30~37건 |
| **폐기** — 전제 자체가 사라짐 | **1~2** | 1~2% | REQ-F-R-022 (+ 조건부로 REQ-F-R-009) |
| 합계 | 116 | 100% | |

> 여기에 더해 **§4.5 선택지별 차이표 전체(표 (1)(2)(3))와 결정 대기 REQ 10건(REQ-F-R-090~096, REQ-N-R-007~009)이 통째로 삭제**된다. 이들은 116건 집계에 들어 있지 않은 "조건부 항목"이라 위 표에는 없지만, 문서 분량으로는 요구사항 §4.5 한 절(약 50줄)이 사라진다.
> 부수 효과: **G1 조건 C-3(예약 영역 병기 금지)과 G2 보류 사유가 CR-001 승인과 동시에 해소된다.** B안 확정은 곧 ADR-001 결정이므로 병기할 선택지가 없어진다. 이것은 CR-001의 **긍정적 영향**이며 pmo 종합 시 함께 반영할 것을 요청한다.

### 1.2 예약 영역 28건 (§4, `REQ-*-R-*`) — 전건 영향

요구사항 §4 머리말이 이미 못박아 두었다: **"B(자체 예약 시스템)로 결정되면 이 절 전체를 다시 쓴다."** CR-001은 B안이므로 **28건 전부가 재작성 대상**이다. 다만 "전부 폐기"는 아니며, 상당수가 이름만 바꿔 그대로 살아난다.

| 분류 | 건수 | ID | 판단 근거 |
|---|---|---|---|
| **승계** — 규칙·기준값을 그대로 쓰고 적용 대상만 넓힘 | **15** | REQ-F-R-002(수집 최소화), 003(입력 검증), 004(동의), **006(번호 발급 규칙)**, 008(운영자 알림), 010(악용 방지), 011(전송 결과·중복 제출) / REQ-N-R-001(타인 정보 조회 0건), **002(번호 강도)**, 003(보관·파기), 004(외부 사업자·리전), 005(저장·알림 실패 구분), 006(응답 3초), 010(식별 정보 노출 차단) / REQ-C-R-002(보관기간·위탁 문구) | 규칙 본문이 구현 방식과 독립적으로 쓰여 있다 |
| **대상 전환·대폭 재작성** | **12** | REQ-F-R-001(신청 폼), 005(저장), 007(완료 화면), 009(접수 안내) / REQ-F-R-020·021·023·024·025·026·027(예약조회 7건) / REQ-C-R-001(수집 항목·희망 수업) | 아래 1.3 참조 |
| **폐기** | **1 (~2)** | REQ-F-R-022 (조회 결과 안내 문구 "접수 완료는 예약 확정이 아닙니다") | 레슨 예약이 **즉시 확정**이 되어 문구의 전제가 사라진다. 상담 예약에는 "해피콜로 확정" 취지의 **다른** 문구가 필요하므로, 폐기 후 신규로 세는 것이 맞다. REQ-F-R-009(접수 안내)도 레슨에서는 성립하지 않아 폐기로 볼 여지가 있다(상담에서는 남음) → **판정 폭 1~2건** |

### 1.3 예약번호 관련 항목 — 폐기가 아니라 **승계·확장**이다

`interviews/2026-09-12_summary-and-options.md` §2 표는 "예약번호 체계 → 폐기"로 적었으나, **기획 관점에서는 사실과 다르다.** 근거는 booking-rules v1.2 두 곳이다.

- §5 (C-10 확정): "레슨 예약이 확정되면 **예약번호**를 발급한다. **상담 신청번호와 같은 방식**(추측 불가한 무작위 값)"
- §7 (C-9 확정): 상담 신청번호 "형식: 추측할 수 없는 무작위 값 (예: `YP-A7KD-M2XF`). **순번처럼 남의 번호를 유추할 수 있는 방식은 쓰지 않는다**"

이는 현행 **REQ-F-R-006**(CSPRNG·엔트로피 40비트 이상·Crockford Base32 8자·`YP-XXXX-XXXX` 표기·입력 정규화 3규칙)과 **REQ-N-R-002**(강도 기준값·1,000건 중복 0건·연속 20건 규칙성 0건)를 **글자 그대로 만족하는 요구다.** 두 건은 R1~R3 세 라운드에서 다듬어졌고(치환 시험 표본 `YP-0A7K-1M2X` 교체까지 v0.4에서 끝났다), 폐기하면 그 결론을 다시 도출해야 한다.

**권고(기획 관점)**: REQ-F-R-006·REQ-N-R-002는 **ID를 유지한 채 적용 대상을 "레슨 예약번호 + 상담 신청번호 2종"으로 확장**하는 개정으로 처리한다. 함께 확장되는 것:

| 현행 | CR-001 후 |
|---|---|
| 발급 대상 1종(예약 신청) | **2종** — 레슨 예약번호, 상담 신청번호 |
| 번호로 조회하는 창구 1개(SCR-005) | **1개** — 상담 신청 조회(비회원). **레슨은 번호 조회 창구를 두지 않는다**(booking-rules §5: 회원 전용이라 마이페이지에서 본다) |
| 조회 보안 규칙(응답 동일화·빈도 제한·마스킹) | **그대로 상담 조회에 적용** (booking-rules §8-1이 같은 내용을 요구) |

→ 따라서 예약조회 7건(REQ-F-R-020·021·023·024·025·026·027)도 "폐기"가 아니라 **"레슨 → 상담으로 대상 전환 후 재작성"** 이다. 수용 기준 중 특히 REQ-F-R-023(응답 본문·상태 코드·헤더·시간 동일화, 웜업 5회 폐기 + 인터리브 50회 + p90 계산 규칙)은 그대로 재사용 가능하며, 이 항목 하나가 R2~R3 두 라운드를 소비한 것이므로 재사용 가치가 크다.

### 2.1 개정 후 전체 규모

| | 현행 | CR-001 후 (추정) | 배수 |
|---|---|---|---|
| 요구사항 총건수 | 116 | **200~250 (중앙 ~225)** | 1.7~2.2배 |
| 기능 REQ | 58 | 105~140 | 1.8~2.4배 |
| 비기능 REQ | 37 | 55~65 | 1.5~1.8배 |
| Must 건수 | 79 | **155~195** | 2.0~2.5배 |

> **신규 항목의 Must 비중이 높다(75~85% 추정).** booking-rules v1.2가 규칙을 이미 확정해 두어 "있으면 좋은 것"이 거의 없기 때문이다. 이는 **P5 검증 부담이 건수 비례 이상으로 늘어난다**는 뜻이다(Must는 미충족 시 게이트 차단).
> **고객 요청에 없어 `Could`로만 제안할 항목**: 공지 공개 화면(관리자 "공지 관리"는 지시에 있으나 회원이 보는 공지 목록·상세 화면은 지시에 없다), 예약 리마인더 알림, 캘린더 파일(.ics) 내려받기, 강사별 프로필 연결. → 이들은 Could로 제안만 하고 PM이 고르지 않으면 넣지 않는다.

### 2.2 추정의 불확실성 요인

| 요인 | 영향 폭 |
|---|---|
| 회원 가입 항목 확정(이메일 필수 여부, 생년월일·성별 수집 여부) | ±3~5건 |

| **α (원칙안)** | P1 확정 → P2 착수 | 범위·일정이 확정된 상태에서 기획하므로 재작업 0 | 계획서 개정·G1 재승인 기간(2~4일 추정) 동안 기획이 멈춘다 |
| **β (압축안)** | P1 개정과 P2 개정을 **병렬** 착수 | 2~4일 단축 | 계획 미확정 상태에서 기획이 진행됨. **다만 기능 정의는 booking-rules v1.2로 사실상 확정**되어 있어 "무엇을 만드는가"는 흔들리지 않는다. 흔들리는 것은 **차수 분할·오픈일**이며, 이는 §7의 차수 표시 방식으로 흡수 가능 |

기획 관점에서는 **β가 실행 가능**하다고 본다(단 PM이 §7의 단계 오픈 방안을 먼저 정해 주면 β의 리스크가 거의 사라진다). 선택은 PM·pmo 몫이다.

### 5.2 폐기되는 기존 작업

| P2 산출물 | in-review(v0.4). 공통 영역 50~58건과 §3.0·§5.0·§5.3·§9 기준 장치는 **그대로 살아남는다** |

## 7. 단계 오픈(1차 소개형 10월 말 / 2차 회원·예약)을 택할 경우의 문서 구성

> PM이 방안 1(단계 오픈)을 고른다는 **가정** 아래의 기획 관점 제안이다. 방안 선택 자체는 PM 결정이다.

### 7.1 원칙 — 문서는 1세트, 차수는 "열"로 표시한다

**차수별로 문서를 쪼개지 않을 것을 권고한다.**

근거:
1. **공통 영역이 두 차수에 걸쳐 있다.** 헤더·푸터·접근성·SEO·개인정보·브랜드는 1차에 만들고 2차에 확장된다. 문서를 쪼개면 같은 규칙이 두 곳에 생기고, **이 프로젝트는 정확히 그 문제(같은 규칙이 세 문서에 다르게 적힘)로 R1~R3를 소비했다**(§3.0·§9 단일 기준이 그 해법이었다). 차수별 분리는 해결한 문제를 되살린다.
2. **추적 ID는 프로젝트 단위 연속이다**(`CLAUDE.md` §4). 차수별 문서는 ID 충돌·재사용 위험을 만든다.
3. 2차 착수 시 "1차 문서에서 무엇이 바뀌는가"를 다시 대조하는 비용이 든다.

### 7.2 구체 표기 방식 (5가지)

| # | 방식 | 내용 |
|---|---|---|
| **1** | **REQ 표에 `차수` 열 추가** | 값은 **`1차` / `2차` / `공통`** 3종만. `공통` = 1차에 구현하고 2차에 확장되는 항목(예: REQ-F-001 헤더 → 2차에 로그인·마이페이지 메뉴 추가). `공통` 항목은 상세 설명에 **"2차 확장:"** 단락을 두고, **수용 기준도 1차용·2차용을 나눠 쓴다**(qa가 1차 게이트에서 2차 기준으로 판정하지 않도록) |
| **2** | **SCR 번호대로 차수와 영역을 동시에 표현** | §3.3 제안과 결합 — `SCR-001~099`(공개=1차) / `SCR-100~199`(회원·예약=2차) / `SCR-900~999`(관리자=2차). **번호만 보고 차수와 적용 규칙을 알 수 있다.** 화면 목록·§9 매핑에도 같은 `차수` 열을 둔다 |
| **3** | **§7 우선순위 집계를 `차수 × MoSCoW` 교차표로** | "1차 Must 전건 충족"을 게이트에서 바로 판정할 수 있게 한다. 현행 §7.1~7.3(영역별 집계)을 차수 축으로 한 번 더 낸다 |
| **4** | **§10 "차수 전환 항목" 절 신설** | 1차에서 임시로 만들고 2차에 교체되는 것을 **전부 목록화**하고 각각에 전환 수용 기준을 붙인다. 예: 강사 정보(1차 데이터 파일 → 2차 관리자 DB), 수업 유형(1차 정적 → 2차 유형 관리), 헤더 메뉴(1차 5개 → 2차 로그인·마이페이지 추가), 문의 폼(1차 단독 → 2차 상담 창구와 역할 분리). **이 절이 없으면 2차에서 "왜 이걸 다시 만드나"가 반복되고 전환 공수가 일정에서 누락된다**(ITV-002가 지적한 0.5~1일이 여기에 해당) |
| **5** | **§"2차 확장 예고" 절을 1차 문서에 둔다** | 1차 디자인(P3)이 2차에 깨지지 않도록 designer에게 미리 알릴 항목 — 헤더에 메뉴 2개 추가, 캘린더·표 형태 컴포넌트 필요, 관리자용 고밀도 UI 토큰 필요, 폼 컴포넌트 재사용 범위. 이게 없으면 2차에서 디자인 시스템을 다시 만든다 |

### 7.3 1차 범위 구성에 대한 기획 의견

| 항목 | 의견 |
|---|---|
| **1차에 그대로 쓸 수 있는 분량** | 현행 공통 영역 88건 중 **50~58건이 v0.4 수준으로 이미 완성**돼 있다. 1차 기획 개정은 **예약 영역 분리 + 차수 표시 + §3.0 화면 목록 조정** 정도라 **1.0~2.0작업일**이면 끝난다(전체 개정 11~16.5일 중) |
| **1차에 시간표를 정적으로 넣을 것인가** | **넣지 않는 안을 제안한다.** 이유: ① 시간표 자료 자체가 미회신(T-18/Q13) ② 2차에서 관리자 입력으로 전환하는 작업(0.5~1일)이 생긴다 ③ 잘못된 시간표가 오픈 기간 중 노출되면 신뢰 손상. **대안**: 1차에는 "수업 유형 소개"(그룹·키즈·플라잉·로우 플라잉·리포머의 설명)만 정적으로 두고, 시간표 자리에는 "월 시간표는 준비 중입니다 · 전화 문의" 안내를 둔다 |
| **1차 상담 예약** | 상담 예약은 **회원 기능에 의존하지 않는다**(비회원 가능, 캘린더 비연계). 1차에 넣을 수 있고, 넣으면 10월 말 오픈 시점부터 실제 전환(체험·등록 상담 접수)이 발생한다 — **사이트 목적(예약 문의 증가, CR-000)에 직접 기여**. 다만 관리자 상담 목록·해피콜 기록이 함께 필요해 **+3~5작업일**(기획 0.5~1 + 구현)이 1차로 넘어온다. **PM 선택지로 제시한다** |

### 7.4 게이트 운영 — 두 방식과 기획 권고

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **α** | 1·2차 기획을 **한 번에** 완성 → G2 1회 | 전체 그림이 일관되고 디자인 시스템을 한 번에 잡는다. 2차 재작업 위험 최소 | 기획 11~16.5일이 통째로 1차 오픈 앞에 놓인다 → **10월 말 오픈이 사실상 불가** |
| **β** | **1차 범위로 G2a 먼저 승인** → 1차 P3~P7 진행, **그동안 2차 기획 병행** → G2b | 1차 오픈일(10-27~30)을 지킬 수 있다. 1차 기획 개정이 1~2일이면 끝나므로 즉시 착수 가능 | 2차 설계 시 1차 결정(헤더·GNB·디자인 토큰)을 바꿔야 할 수 있다 → §7.2 방식 5("2차 확장 예고")로 완화 |

**기획 관점 권고: β.** 근거는 §7.3 첫 행(1차 기획 개정 1~2일) 하나다 — 1차에 필요한 기획은 이미 v0.4에 거의 다 있다. 다만 β는 **게이트가 G2a/G2b 둘로 늘어 관리 부담이 생기고, 게이트 번호 체계(`G{n}`)를 어떻게 표기할지는 `CLAUDE.md` §9 태그 규칙과 연관되므로 pmo·PM이 정해야 한다.**
