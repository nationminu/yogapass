# CR-002 디자인 고도화 — 구현 영향도 의견 (developer)

> **이 문서의 성격**: CR-002가 designer에게 제시한 5개 트렌드 요소가 현행 구현 제약(번들러·npm·외부 CDN 없음 / Lighthouse 4지표 90+ / 로딩 2.5초 / WCAG 2.1 AA)에서 **실제로 가능한지**를 판정한다.
> 판정은 추측이 아니라 **① 현행 사이트의 Lighthouse 실측 증거(`qa/evidence/cycle3/`) ② 이번에 직접 돌린 렌더링 비용 실험 ③ 가변 폰트 용량 실측 ④ MDN browser-compat-data 8.1.1 조회** 에 근거한다.
> designer 개정본은 작업 중이므로 **현행 v1.x 기준**으로 판단했다.

---

## 1. 총평

1. **5개 요소 중 4개는 "조건부 가능"이고, 1개(키네틱 타이포의 글자 단위·가변축 애니메이션)는 범위를 좁히지 않으면 불가다.** 전 제목에 음절 단위 가변축(wght) 애니메이션을 걸면 스크롤 중 **프레임의 25.2%가 떨어졌다**(실측). 히어로 제목 1개로 한정하면 **드롭 0%**다. 이 선만 지키면 나머지 트렌드 요소는 순수 CSS/JS로 구현 가능하다.
2. **최대 리스크는 모션이 아니라 폰트 바이트다.** 현행 메인 화면 전송량 198KB 중 **폰트가 160KB(81%)** 다. 한글 가변 폰트로 바꾸면 메인 +13.5%, 강사 소개 +43.6%가 되고 **LCP가 1.06초 → 1.20초로 +144ms** 늘어난다(실측). 2.5초 기준에는 여유가 있으나, **디자인이 굵기를 3단 이상 쓰기 시작하면 정적 폰트 유지가 오히려 더 비싸진다**(3단이면 가변이 17~26% 저렴). 즉 **"굵기를 몇 단 쓸 것인가"가 폰트 전략을 결정하는 유일한 변수**이며, 이것은 designer가 지금 정해야 한다(§4.4).
3. **Firefox 155는 CSS 스크롤 구동 애니메이션(`animation-timeline`)을 아직 지원하지 않는다**(MDN BCD 8.1.1 기준 preview 단계). 우리 지원 범위가 "Chrome/Edge/Safari/Firefox 최신"이므로 **폴백이 필수**다. 다행히 `animation-timeline`을 무시하는 엔진에서는 애니메이션이 **종료 상태로 고정**되므로(실측 확인), **"종료 상태가 그 자체로 정상 화면"** 이기만 하면 폴백 비용이 0이다. 패럴랙스처럼 종료 상태가 어긋나는 연출만 `@supports`로 감싸면 된다.
4. **한 가지 착시를 미리 경고한다. Lighthouse 성능 점수는 "로딩"만 측정하므로 스크롤 애니메이션을 아무리 무겁게 만들어도 점수는 100을 유지한다.** 이번 실험에서 프레임을 25% 떨어뜨린 구성도 Lighthouse로는 잡히지 않는다. 따라서 "Lighthouse 90+ 유지"만으로 모션 품질을 지킬 수 없고, §6의 금지선을 디자인 명세 단계에서 지켜야 한다.
5. 판정은 **조건부 승인**이다. §6의 금지선 14개가 디자인 명세에 반영되면 CR-002의 시각 언어 고도화는 현행 스택에서 구현 가능하고, 성능·접근성 기준을 완화할 필요가 없다.

### 3.1 요소 1 — 키네틱 타이포그래피 : 조건부 가능

**질문**: 번들러·CDN 없이 순수 CSS/JS로 어디까지 가능한가. Lighthouse 99~100을 깎지 않는가.

**실측** (CPU 4배, 4000px 스크롤, 3회 중앙값. `frameAvg` 16.7ms = 60fps 유지)

| 시나리오 | frameAvg | p95 | **드롭%** | Script | Style | **Layout** | Task | 판정 |
|---|---|---|---|---|---|---|---|---|
| 기준선(효과 없음) | 16.7 | 17.0 | 0 | 2.0 | 0 | 0 | 225 | — |
| 요소 단위 진입 전환 | 16.7 | 17.9 | **0** | 2.4 | 102 | 0 | 701 | 무료 |
| **어절 단위** transform 키네틱(전 제목) | 16.7 | 17.3 | **0** | 3.2 | 101 | 0 | 865 | 허용 |
| **음절 단위** transform 키네틱(전 제목) | 21.6 | 31.7 | **3.5** | 3.0 | 317 | 0 | 2542 | 제한 |
| **음절 단위 + 가변축(wght)** (전 제목) | 27.2 | 41.8 | **25.2** | 9.9 | 212 | **1127** | 3282 | **불가** |
| 음절 단위 + 가변축 (**히어로 1개만**) | 16.7 | 17.1 | **0** | 3.4 | 7.6 | **0** | 300 | 허용 |
| 커서 반응(포인터 이동 150회) | 16.7 | 17.9 | **0** | 67.5 | 306 | 0 | 731 | 허용(데스크톱 한정) |

**해석**
- **가변축(`font-variation-settings: 'wght'`) 애니메이션이 비싼 이유는 레이아웃이다.** 굵기가 바뀌면 글리프 폭이 바뀌므로 매 프레임 줄바꿈을 다시 계산한다 — Layout 0ms → **1127ms**. 다른 시나리오는 모두 Layout 0ms다. 이게 25% 드롭의 정체다.
- 반면 **같은 효과를 히어로 제목 1개(14자)로 한정하면 Layout 0ms, 드롭 0%, 기준선 대비 Task +75ms**에 그친다. 즉 금지해야 할 것은 기법이 아니라 **적용 범위**다.
- 음절 단위 transform(가변축 없음)도 전 제목에 걸면 Style 317ms·Task 2542ms로 기준선의 11배다. p95 31.7ms로 60fps가 무너지기 직전이다. **어절(語節) 단위로 내리면 Task 865ms·드롭 0%** 로 안전해진다. **한글은 어절 단위가 자연스러운 조판 단위이기도 하다.**
- **Lighthouse 점수는 이 중 어느 것도 잡지 못한다.** Lighthouse의 TBT·성능 점수는 로딩 구간만 측정한다. 스크롤 애니메이션은 로딩 후 발생하므로 25% 드롭 구성도 성능 100이 나온다. **"Lighthouse 90+ 유지"는 이 요소의 안전장치가 아니다.**

**구현 방식 (번들러 없이)**
- 글자·어절 분할은 **JS가 아니라 Django 템플릿 필터(서버 렌더링)** 로 한다. ⓐ JS 없이도 동작(REQ-N-028) ⓑ 분할 시점의 리플로우·FOUC 없음 ⓒ 추가 JS 0바이트.
- 접근성: 분할된 `<span>`은 일부 스크린리더에서 한 글자씩 읽힌다. 부모에 `aria-label="원문"`, 자식 `<span>`은 `aria-hidden` 처리가 필요하다 — 이건 **접근성 비용이 있는 연출**이므로 히어로 1곳으로 제한하는 또 하나의 이유다.
- 커서 반응은 `pointermove` → `requestAnimationFrame` 1회 throttle → **루트의 CSS 변수 1개만 갱신** → `transform`으로 소비하는 구조면 드롭 0%다. 다만 **`@media (hover: hover) and (pointer: fine)` 안에만** 둬서 모바일이 비용을 0으로 내게 한다.
- CSP 제약: 현행 CSP는 `script-src 'self'; style-src 'self'` 다(`apps/core/middleware.py`). **인라인 `style=` 속성은 브라우저가 차단한다** — 실제로 DEF-003이 이 문제였다. JS에서 `el.style.setProperty()`(CSSOM)로 값을 쓰는 것은 차단되지 않는다(현행 `viewport.js`가 이미 그렇게 동작한다). **디자인 명세에 인라인 스타일을 전제한 연출을 넣으면 안 된다.**

### 3.2 요소 2 — 가변 폰트 self-host : 조건부 가능 (§4에서 상세)

요약만 적는다. 실측 근거와 판단 기준은 **§4 전체**에 있다.

- Pretendard Variable(45–920) 전체 woff2 = **2,057,688바이트(2.06MB)**. 그대로 쓰면 불가.
- 현행과 동일한 `unicode-range` 분할본을 쓰면 **페이지당 +13.5% ~ +43.6%**, **LCP +144ms**(실측). 2.5초 기준 내에서 수용 가능하다.
- **굵기를 3단 이상 쓰는 순간 가변이 정적보다 17~26% 저렴해진다.** 결정 변수는 굵기 단 수 하나다.
- FOUT는 현행과 동일하게 `font-display: swap` + 메트릭 오버라이드 폴백으로 처리한다. 실측 **CLS는 전환 전후 모두 0**이었다.

### 3.3 요소 3 — 스크롤 트리거 · 패럴랙스 · 진입 전환 : 조건부 가능

**브라우저 지원** (MDN BCD 8.1.1, 현재 정식 버전 기준)

| 기능 | Chrome 153 | Edge 152 | Safari 26.6 | **Firefox 155** | iOS Safari 26.6 |
|---|---|---|---|---|---|
| `animation-timeline` / `scroll()` / `view()` / `animation-range` | 115+ ✅ | 115+ ✅ | 26+ ✅ | **미지원 (preview)** | 26+ ✅ |
| `timeline-scope` | 116+ ✅ | ✅ | 26+ ✅ | **미지원** | ✅ |
| `IntersectionObserver` | 51+ ✅ | 15+ ✅ | 12.1+ ✅ | **55+ ✅** | ✅ |
| `@property` / `CSS.registerProperty` | 85+ ✅ | ✅ | 16.4+ ✅ | **128+ ✅** | ✅ |
| 동일 문서 View Transition API | 111+ ✅ | ✅ | 18+ ✅ | **144+ ✅** | ✅ |
| **교차 문서** `@view-transition` | 126+ ✅ | ✅ | 18.2+ ✅ | **지원 안 함(NO)** | ✅ |
| `transition-behavior: allow-discrete` | 117+ ✅ | ✅ | 17.4+ ✅ | 129+ ✅ | ✅ |
| `content-visibility` | 85+ ✅ | ✅ | 18+ ✅ | 125+ ✅ | ✅ |

**판정 근거**
1. **CSS 스크롤 구동 애니메이션은 Firefox 155에서 동작하지 않는다.** 우리 지원 범위에 "Firefox 최신"이 있으므로 폴백 없이 쓰면 요구사항 위반이다.
2. 다만 **폴백 비용이 거의 0이라는 것을 실험으로 확인했다.** `animation: rise linear both`는 `animation-duration` 초기값이 `0s`이고 `fill-mode: both`이므로, `animation-timeline`을 무시하는 엔진에서는 **애니메이션이 즉시 종료 상태로 고정**된다. Chrome에서 `animation-timeline` 선언을 뺀 등가 구성·해석 불가능한 타임라인 이름을 준 구성 모두 `opacity: 1`(=종료 상태)로 계산되는 것을 확인했다(§5.3).
   → **진입 전환(fade-in / rise)은 Firefox에서 "처음부터 보이는 상태"로 자연스럽게 열화된다. 콘텐츠 손실이 없으므로 폴백 코드가 필요 없다.**
3. **패럴랙스는 다르다.** 배경을 `-15%` 이동시키는 애니메이션의 종료 상태는 "어긋난 배경"이다. Firefox에서 그 상태로 고정되면 여백이 비거나 잘린다. → **패럴랙스는 `@supports (animation-timeline: scroll())` 로 감싸야 하고, 그러면 Firefox에는 연출이 아예 없다.** 즉 **패럴랙스는 "없어도 되는 장식"으로만 설계해야 한다.**
4. **성능 비교**: 패럴랙스를 CSS로 하면 `Script 2.7ms`, JS 스크롤 리스너로 하면 `Script 37.6ms`(14배)다. 둘 다 드롭 0%지만 **CSS 방식이 명확히 우월**하다. 단 Firefox 대응까지 고려하면 조합은 이렇게 된다.

| 연출 | 1순위 구현 | Firefox 155 결과 | 비고 |
|---|---|---|---|
| 진입 전환(등장) | `animation-timeline: view()` | 처음부터 보임(정상) | 폴백 코드 불필요 |
| 진입 전환(1회성·정밀 제어 필요) | `IntersectionObserver` + 클래스 토글 | **동일하게 동작** | 전 브라우저 균일. Style 80.5ms / 드롭 0% |
| 패럴랙스 | `animation-timeline: scroll()` + `@supports` | 연출 없음(정상 배경) | 필수 조건 |
| 스크롤 진행 표시기 | `animation-timeline: scroll(root)` + `@supports` | 표시기 없음 | 정보 전달 수단으로 쓰지 말 것 |
| 페이지 간 전환 | `@view-transition` | 전환 없음(일반 이동) | 순수 점진적 향상, JS 0바이트 |

5. `IntersectionObserver`는 모든 대상 브라우저에서 동작하고 실측 드롭 0%다. **브라우저 균일성이 필요한 연출은 IO를 쓰면 된다** — 추가 JS는 10줄 수준이고 번들러가 필요 없다.

### 3.4 요소 4 — 그라데이션 면 · 결(texture)/노이즈 : 가능

**실측** (동일 조건)

| 시나리오 | frameAvg | 드롭% | Script | Style | Layout | Task | 기준선 대비 |
|---|---|---|---|---|---|---|---|
| 기준선 | 16.7 | 0 | 2.0 | 0 | 0 | 225 | — |
| 다층 방사형 그라데이션(mesh) 고정 배경 | 16.7 | 0 | 1.7 | 0 | 0 | **219** | 사실상 0 |
| mesh + **SVG `feTurbulence` 노이즈**(data-URI, 160px 타일 반복, `mix-blend-mode: multiply`) + 카드 `backdrop-filter: blur(12px)` | 16.7 | 0 | 1.6 | 0 | 0 | **272** | +47ms |
| 전 카드 `backdrop-filter: blur(16px) saturate(1.2)` + 고정 배경 | 16.7 | 0 | 2.1 | 0 | 0 | **263** | +38ms |

**해석**
- **이미지 없이 CSS만으로 내는 그라데이션 면은 비용이 사실상 0이다.** 스크롤 중 Style·Layout이 모두 0이고 Task는 기준선과 구분되지 않는다. 배경 한 장이 한 번 래스터화된 뒤 합성 레이어로만 소비되기 때문이다.
- 노이즈는 **SVG `feTurbulence`를 data-URI로 넣고 작은 타일(160px)로 반복**하는 방식이 안전하다. 필터가 **로드 시 한 번만** 실행되고 이후는 타일 반복이다. 전송량은 **약 0.3KB**로, 노이즈 PNG/WebP(같은 품질이면 수십 KB)보다 압도적으로 싸다. **REQ-C-013(사진 없음 → 그래픽·타이포 중심 구성) 방침과도 맞는다.**
- CSP: CSS 안의 `url("data:image/svg+xml,…")`는 `img-src 'self' data:` 에 걸리므로 **현행 CSP에서 허용된다.** 별도 헤더 변경이 필요 없다.
- **다만 이 숫자를 과신하면 안 된다.** headless shell 측정은 **GPU 래스터·합성 비용을 반영하지 못한다.** `backdrop-filter`와 `mix-blend-mode`는 비용이 GPU 쪽에 있으므로, 위 표의 "+38ms / +47ms"는 **하한선**이다. 저사양 모바일 GPU에서의 실제 비용은 이보다 크다. 그래서 §6-10·11에서 **면적·개수·움직임을 보수적으로 제한**한다.

### 3.5 요소 5 — 모션 전반 / `prefers-reduced-motion` : 가능 (이미 있음)

**현행 구조를 확인했다** — `static/css/tokens.css` L96–100, L184–191.

```
--motion-fast: 120ms;  --motion-base: 160ms;  --motion-slow: 220ms;
--ease-standard: cubic-bezier(.2,0,0,1);  --ease-out: cubic-bezier(0,0,.2,1);
--motion-distance: 8px;

@media (prefers-reduced-motion: reduce) {
  :root { --motion-fast/-base/-slow: 0.01ms; --motion-distance: 0px; }
  *, *::before, *::after { animation-duration/iteration-count/transition-duration 강제 · scroll-behavior: auto }
}
```

**이미 요구된 구조가 있다.** 토큰 차원 스위치(`--motion-*`)와 전역 안전망(`* { ... !important }`)이 함께 있다. 이번 고도화에 필요한 확장은 **토큰 3개 추가 + 규칙 1개** 뿐이다.

| 추가 항목 | 내용 | 이유 |
|---|---|---|
| `--motion-scroll: 1` / `reduce`일 때 `0` | 스크롤 구동 애니메이션의 진폭 배율 | 지속시간이 아니라 **진폭**으로 끄는 축이 필요하다. 스크롤 구동 애니메이션은 duration이 없어서 기존 `--motion-*`로 꺼지지 않는다 |
| `--motion-parallax-distance` | 패럴랙스 이동량(기본 15%, reduce 시 0%) | 위와 동일 |
| `--motion-kinetic: 1 / 0` | 키네틱 타이포 on/off | 히어로 연출만 따로 끄기 |
| `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-timeline: none !important } }` | 스크롤 구동 애니메이션 자체를 무력화 | 위 `*` 블록의 `animation-duration: 0.01ms`는 **스크롤 타임라인 애니메이션을 멈추지 못한다**(진행률이 시간이 아니라 스크롤 위치로 결정되므로). 반드시 `animation-timeline: none`을 함께 넣어야 실제로 꺼진다 |

**마지막 항목이 이번 고도화에서 새로 생기는 진짜 위험이다.** 현행 `reduce` 블록만 믿고 스크롤 구동 애니메이션을 추가하면 **모션 민감 사용자에게 그대로 노출된다.** 디자인 시스템 §1.6 CSS 변수 블록에 이 규칙을 명시해야 한다.

또한 `prefers-reduced-motion`은 대상 전 브라우저에서 지원된다(Chrome 74+/Edge 79+/Safari 10.1+/Firefox 63+).

각 화면이 **실제로 내려받은 덩어리 번호**를 Lighthouse 네트워크 기록에서 추출해, 같은 덩어리의 가변본 크기로 치환해 계산했다.

| 화면 | 현행(정적 2단) | 요청수 | **가변(45–920)** | 요청수 | 델타 | 증가율 |

| 메인 | 159,684 | 13 | **181,224** | 7 | +21,540 | **+13.5%** |
| 강사 소개 | 126,216 | 10 | **181,224** | 7 | +55,008 | **+43.6%** |
| 오시는 길 | 160,112 | 13 | **206,328** | 8 | +46,216 | **+28.9%** |
| 처리방침 | 207,976 | 17 | **260,952** | 10 | +52,976 | **+25.5%** |

**덩어리 단가로 보면 구조가 보인다.** 예를 들어 91번 덩어리는 정적 Regular 20,200 + Bold 20,396 = 40,596바이트인데, 가변본은 **37,996바이트로 오히려 작다.** 반대로 **한 덩어리를 한 가지 굵기로만 쓰는 화면**(강사 소개가 그렇다)에서는 가변본이 정적 1벌의 약 2배가 된다. 그래서 증가율이 화면마다 13.5%~43.6%로 크게 갈린다.

### 4.4 결정 변수는 하나다 — "굵기를 몇 단 쓸 것인가"

3번째 굵기(예: SemiBold 600)를 정적으로 추가했을 때와 가변을 비교했다(3번째 굵기는 해당 화면의 Bold 덩어리 평균 단가 × 사용 덩어리 수로 추정).

| 화면 | 정적 2단(현행) | 정적 3단(추정) | **가변** | 가변 vs 정적 3단 |
|---|---|---|---|---|
| 메인 | 159,684 | 245,398 | **181,224** | **−64,174 (−26.2%)** |
| 강사 소개 | 126,216 | 220,319 | **181,224** | **−39,095 (−17.7%)** |
| 오시는 길 | 160,112 | 261,197 | **206,328** | **−54,869 (−21.0%)** |
| 처리방침 | 207,976 | 330,425 | **260,952** | **−69,473 (−21.0%)** |

**결론 — designer가 지금 답해야 하는 질문은 이것 하나다.**

| designer의 선택 | 권고 |
|---|---|
| 굵기 **2단**(400/700)을 유지한다 | **현행 정적 구성 유지.** 가변으로 바꿀 이유가 없다. 바이트만 13~44% 늘어난다 |
| 굵기 **3단 이상**을 쓴다 (예: 300·400·600·700, 또는 제목 800) | **가변으로 전환.** 정적 3단보다 18~26% 싸고, 그 뒤로는 굵기를 몇 단 더 써도 **바이트가 늘지 않는다** |
| 굵기를 **연속적으로** 쓴다(스크롤·호버에 따라 200→800 변화 등) | **가변 필수.** 단 §6-2의 적용 범위 제한을 반드시 지켜야 한다 |

### 4.5 LCP 영향 — 실측

같은 메인 화면 HTML·CSS·JS에서 `@font-face`만 바꿔 Slow 4G + CPU 4배로 5회 측정했다(중앙값).

| 구성 | FCP | **LCP** | load | CLS | 총 전송 | 폰트 요청 |
|---|---|---|---|---|---|---|
| 정적 400/700 (현행) | 1,060ms | **1,060ms** | 1,938ms | **0** | 182,441 | 13 |
| 가변 45–920 | 1,204ms | **1,204ms** | 1,902ms | **0** | 206,886 | 7 |
| **델타** | +144ms | **+144ms (+13.6%)** | **−36ms** | 0 | +24,445 (+13.4%) | **−6** |

**해석**
- **LCP +144ms.** 목표 2,500ms 대비 여유가 1,440ms → 1,296ms로 줄지만 **기준을 깨지 않는다.**
- `load`는 오히려 36ms 빨라졌다 — **요청이 13개 → 7개로 줄어** RTT 150ms의 연결·대기 비용이 상쇄하기 때문이다. 바이트는 늘지만 왕복은 준다.
- **CLS는 전환 전후 모두 0.** 기존 메트릭 오버라이드 폴백이 그대로 작동한다. 단 **중간 굵기(500·600)를 새로 쓰면 그 굵기용 `Pretendard Fallback` 페이스를 추가해야 한다** — 지금은 400·700 두 개뿐이다. 빠뜨리면 굵기별 폴백 매칭이 어긋나 FOUT 구간에서 줄바꿈이 흔들린다.
- **preload 2개의 바이트가 30,087 → 58,848로 +28,761 늘어난다.** 이게 +144ms의 대부분이다. 전환한다면 preload는 **2개를 넘기지 말 것**(3개로 늘리면 여유가 더 줄어든다).
- 여기서 **이번 사이트 구성의 전송 바이트 ↔ LCP 환산 계수**가 나온다: **24.4KB → 144ms, 즉 임계 경로 1KB당 약 5.9ms**(Slow 4G). §7의 예산 계산에 쓴다.

### 4.6 한글 가변 폰트의 현실적 선택지

| 후보 | 라이선스 | 분할 배포 | 판정 |
|---|---|---|---|
| **Pretendard Variable** (45–920, weight 축) | SIL OFL 1.1 | **공식 `unicode-range` 92분할 배포본 있음** | **유일한 현실적 선택.** 현행과 같은 서체라 디자인·자간·메트릭 연속성이 유지되고, 폴백 오버라이드 값도 재사용된다 |
| 그 외 한글 가변 서체 | 서체별 상이 | 분할본을 **직접 만들어야 함** | 분할 도구(fonttools 등)를 도입하고 92개 `unicode-range`를 맞춰 재생성해야 한다. **공수 +2~3일 + 검증 부담**. 시각적 이득이 그만한지 의문 |
| 제목 전용 한글 서체 **추가** | — | — | **권장하지 않음.** 서체를 한 벌 더 얹으면 화면당 **+100KB 이상**(현행 1벌 단가 기준). LCP +0.6초급 |
| 라틴 전용 디스플레이 서체 추가 | 서체별 | 라틴 글리프만 | **조건부 가능.** 라틴 서브셋만 쓰면 5~15KB. 단 한글과 섞이면 베이스라인·x-height 불일치가 눈에 띈다 |

**축은 weight 하나만 쓴다.** optical size·width 등 다축 서체는 한글에서 사실상 선택지가 없고, 축이 늘면 용량도 늘어난다.

### 4.7 `font-display` 와 FOUT

- 현행 `font-display: swap` **유지 권고.** `optional`로 바꾸면 느린 회선에서 웹폰트가 아예 적용되지 않아 디자인 고도화의 의미가 사라진다. `block`은 최대 3초 텍스트 공백이라 LCP를 직접 악화시킨다.
- swap의 FOUT는 메트릭 오버라이드 폴백이 흡수한다(실측 CLS 0).
- **가변으로 가면 FOUT 단계가 오히려 줄어든다.** 지금은 Regular·Bold 덩어리가 따로 도착해 교체가 여러 번 일어나지만, 가변은 덩어리당 1회다(요청 13 → 7).
- `format('woff2-variations')`(upstream CSS 표기)는 Chrome 66+/Firefox 62+/Safari 11+ 모두 지원하므로 그대로 써도 되지만, **`format('woff2')` 로 통일하는 편이 단순하다**(가변 여부와 무관하게 전 대상 브라우저에서 동작).

### 5.3 `animation-timeline` 폴백 확인 결과

| 구성 | 계산된 `opacity` |
|---|---|
| `animation: rise linear both` (타임라인 선언 없음 = Firefox가 무시한 상태와 등가) | **1** (= 종료 상태) |
| `animation: rise linear both; animation-timeline: view()` | 1 |
| `animation: rise linear both; animation-timeline: --없는이름` (해석 불가 타임라인) | **1** |

→ **타임라인이 없거나 해석되지 않으면 종료 상태로 고정된다.** 진입 전환이 Firefox에서 "이미 보이는 상태"가 되는 근거이고, 동시에 **패럴랙스처럼 종료 상태가 비정상인 연출은 반드시 `@supports`로 감싸야 하는 근거**다.

## 10. 요약

- **Must: 5건 · Should: 5건 · Could: 2건**
- **판정: 조건부 승인** — §6 금지선(특히 Must 5건)이 디자인 명세에 반영되면 CR-002의 시각 언어 고도화는 **현행 스택(번들러·npm·CDN 없음, 서버 렌더링 + self-host + 순수 CSS/JS)에서 구현 가능**하고, **Lighthouse 4지표 90+·로딩 2.5초·WCAG 2.1 AA·터치 44px·기능 요구사항 241건을 하나도 완화하지 않아도 된다.**
- 요소별 판정: **키네틱 타이포 = 조건부(범위 한정) · 가변 폰트 = 조건부(굵기 3단 이상일 때 채택) · 스크롤 연출 = 조건부(Firefox 폴백) · 그라데이션·노이즈 = 가능 · 모션 토큰 = 가능(이미 구축)**
- **PM 결정이 필요한 사항은 없다.** designer의 결정 1건(**사용 굵기 단 수** — §4.4)과 진행 방식 선택 1건(§7.1 단계 A/B/C)만 정해지면 착수할 수 있다.
