# 리뷰: P2 기획 CR-001 반영본 — developer (R1 · 기술 영역 분담)

## 1. 총평

- **URL·식별자 설계는 구현·보안상 타당하다.** 예약·신청번호를 URL에서 분리하고 `{ref}`·`{slotRef}` 비연번 식별자 + 소유자 검사를 짝지은 구조, robots Disallow를 쓰지 않고 `noindex`로 가는 판단, 완료 화면 고정 경로 + 1회용 쿠키 방침은 모두 그대로 구현한다. 남은 것은 **후보 값 하나(ULID)와 재설정 토큰 전달 경로** 두 지점뿐이다(#2·#3).
- **관리자 18화면은 DB 제약·트랜잭션으로 구현 가능한 형태로 정의됐다.** REQ-N-035의 3가지(슬롯 겹침·강사 중복·상담 중복)는 PostgreSQL 배제 제약 2개 + 부분 유니크 인덱스 1개로 **명세 그대로** 옮겨진다. 경계값 "10:00 맞닿음 허용 / 09:59 거부"는 반개구간 `[)` 시간 범위와 정확히 일치해 별도 해석이 필요 없다. PostgreSQL 배제 제약과 어긋나는 곳은 **발견하지 못했다.**
- **다만 Must 1건이 있다. REQ-F-A-008(강사 배정 필수)과 REQ-F-A-013(게시 전 미배정 검사)이 서로를 성립 불가로 만든다** — 배정이 저장 단계 필수면 미배정 슬롯이 구조적으로 존재할 수 없고, 미배정 요약(SCR-902)·미배정 필터(SCR-903)·게시 차단 목록(SCR-907)이 전부 재현 불가능한 UI가 된다. 이 판단이 `slot.instructor_id`의 NULL 허용 여부를 가르므로 **P4 스키마를 확정할 수 없다.** 문장 두 곳 수정으로 해소된다(#1).
- 공수 관점: **§5.3 환경 요건 ⑦·⑧(검증 전용 로그인 세션 · 표준 시드 400/200/100 + 동시 요청 20건 부하 스크립트)은 P4 산출물로 새로 요구된 항목이며, 내 R2 §3.1 영역별 표에 해당 행이 없다.** 시각 고정 수단(#5)까지 묶어 별도 항목으로 잡아야 한다. 그 밖에 목록 모드·템플릿 미리보기·세션 만료 경고는 기존 항목 범위 안이다.

## 5. 분담 항목별 결론

**① URL·식별자 설계 — 타당하다.** `{ref}`/`{slotRef}` 비연번 + 소유자 검사 + 번호의 URL 배제 + 완료 화면 고정 경로는 그대로 구현한다. 번호를 URL에서 빼는 판단은 특히 옳다 — 액세스 로그·리퍼러·히스토리 세 경로가 한 번에 닫힌다. 보완할 곳은 **ULID 후보(#2)**, **재설정 토큰의 로그 유입(#3)**, **날짜 세그먼트 형식 제약(#4)** 세 곳이며 모두 한 줄 수정이다.

**② 관리자 18화면 — DB 제약으로 구현 가능한 형태다. PostgreSQL 배제 제약 전제와 어긋나는 곳은 없다.**
- 슬롯 겹침(REQ-F-A-006): `EXCLUDE USING gist (날짜/공간 WITH =, 시간범위 WITH &&)` + 반개구간 `[)` → "10:00 맞닿음 허용 / 09:59 거부"가 제약 정의만으로 성립한다.
- 강사 중복(REQ-F-A-007): 같은 제약에 `instructor_id WITH =` 키만 추가. 단 #1이 ⓐ로 결정되면 `WHERE instructor_id IS NOT NULL` 부분 제약이 된다.
- 상담 중복(REQ-F-S-005): `(희망일자, 희망시간, 연락처)` 부분 유니크 인덱스 + 취소·완료 제외 조건.
- 운영 시간 초과(REQ-F-A-010)는 설정값이 나중에 바뀔 수 있어 **DB 제약이 아니라 쓰기 시점 검증**이 맞고, SCR-916이 "운영 시간 축소 시 기존 슬롯 유지 + 경고"로 이미 그렇게 정의했다 — 일관된다.
- 30분 그리드·유형별 가변 길이(종료 시각 자동 계산)·강사 배정 필수·정원 지정은 전부 단일 폼(SCR-905) 안에서 처리되고 URL도 분리돼 있어 구현이 단순하다. **드래그 편집 제외와 목록 모드 대안 경로는 내 R2 §4-8 권고와 일치하며, 목록 모드는 SCR-905를 재사용하므로 추가 비용이 작다.**
- 남은 차단 요인은 **#1 하나**다.

**③ 권한·렌더 분기 — 구현 부담이 작다.** REQ-N-036의 "기본 거부 + 공개 허용 경로 명시 등록" 구조에 `/booking` 정확 일치 1건을 공개 허용으로 등록하면 끝난다(+0.1~0.2작업일). 관리자 인증 경로 분리(REQ-F-A-001)는 세션 쿠키·스코프를 둘로 나누는 정도이며 역시 범위 안이다. **문서 수정이 필요한 것은 구현이 아니라 판정 근거(#6)다.**

**④ 수용 기준의 구현·검증 가능성 — 신규 126건 중 판정 불가로 남는 것은 시각 의존 항목뿐이다.** REQ-F-R-023(웜업 폐기·인터리브 50회·p90 nearest-rank), REQ-F-R-006(1,000건 중복·문자 분포 ±50%·치환 시험 표본), REQ-N-L-001(동시 20건 → 성공 1·실패 19), REQ-N-036(미등록 엔드포인트 기본 거부), REQ-F-A-030(작업 기록 7종 + 수정 API 거부)은 모두 **그대로 자동화 가능한 수준으로 적혀 있다** — 이 정도로 판정 절차까지 못박은 수용 기준은 드물다. 반대로 **#5의 시각 의존 기준군과 REQ-F-A-022의 "24시간 방치"** 는 수단 없이는 판정할 수 없다. (참고: REQ-N-036의 "신규 엔드포인트를 권한 등록 없이 추가한 시험 케이스"는 운영 빌드에 시험 코드를 넣어야 하므로 검증 전용 빌드 + 제거 확인 절차를 P4 기술 설계에 함께 적겠다.)

**⑤ 차수 분리 — 기술적으로 성립한다.** 1차 = 공개 5화면(SCR-001·002·003·006·008) + Could 1(SCR-009) + `/location#contact` 문의 폼 + full compose. 조건은 두 가지다.
- **1차를 정적 산출물(SSG 파일)로 만들지 않는다.** REQ-F-A-029·REQ-F-064의 2차 기준("관리자에서 전화번호를 바꾸면 **재빌드 없이** 헤더·푸터·오시는 길 3곳에 반영")과 TR-03(공개 유형 소개가 관리자 활성 유형과 일치)은 소개 화면이 2차에 DB를 읽어야 함을 뜻한다. 1차에 정적 파일로 만들면 2차에 전면 재작성이 된다. **CR-001 D-2로 1차부터 앱+DB가 서므로 1차부터 SSR 앱으로 만들면 이 전환이 사라진다** — 내 R2 §5의 (가) 방식과 일치하며 PM 결정(full compose)이 이미 그 방향이다.
- **I-2(현재 compose 구성)·I-4(도메인·HTTPS 처리 방식)가 P4 착수를 여전히 막는다**(§8.5 D-30). 1차 오픈이 11-06이고 오늘이 09-12이므로, 이 두 항목의 회신 지연이 곧 1차 일정 리스크다. 기획 문서에는 정확히 반영돼 있으며 이 리뷰의 지적은 아니다.
- 1차 게이트 판정 모수 74건(Must 63)에는 REQ-N-031~034·040(헬스체크·백업/복구 리허설·배포/롤백·동일 compose·스테이징)이 포함된다. **1차는 "소개 페이지 6장"이 아니라 "운영 인프라 1식 + 소개 페이지"** 이며, 기획이 이를 1차로 명시한 것은 정확하다.

## 6. 요약

- **Must: 1건 · Should: 8건 · Could: 6건**
- **판정: 수정 요청**
- Must는 **#1 하나**이며, REQ-F-A-008 한 문장과 REQ-F-A-024 한 줄 추가로 해소된다. 다른 지적은 모두 게이트를 막지 않는다(PM 방침 "최대한 빨리" 반영 — 판단이 갈릴 여지가 있는 항목도 게이트 차단 사유가 아니면 Should 이하로 뒀다).
- **Should 중 #5·#6은 P5 판정 충돌을 막기 위한 것**이라 반영을 권한다. #3은 미반영 시 P4 기술 설계에서 구현으로 해결하겠으나 P5 검사 근거가 남지 않는다.
- 공수 관점에서 **R2 추정(P4 구현 39.0~57.25작업일)을 벗어나게 만드는 항목은 §5.3 환경 요건 ⑦·⑧ + 시각 고정 수단(#5) 하나**다. 그 밖의 신규 항목(목록 모드·템플릿 적용 미리보기·세션 만료 경고·관리자 렌더 분기)은 기존 영역별 항목의 ±30% 범위 안이다. 재산정은 P4 기술 설계에서 한다.
- **티켓은 발행하지 않았다** — 지적 전량이 이 리뷰의 수정 요청으로 처리 가능하고, 발행 대상이 planner 단일이라 티켓이 중복 경로가 된다.
