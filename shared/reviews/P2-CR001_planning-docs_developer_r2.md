# 리뷰: P2 기획 CR-001 반영본 — developer (R2 · 범위 축소 확인 검토)

> **이 라운드의 범위**: R1 지적 15건의 반영 확인 + 그 반영으로 새로 생긴 기술 문제만. 문서 전체 재검토·공수 재산정은 하지 않았다.

## 1. 총평

- **Must #1(강사 배정 규칙 모순)은 해소됐다. P4 스키마를 확정할 수 있다.** planner는 내가 권고한 ⓐ·ⓑ가 아닌 제3안을 택했는데 — PM 지시("일정 등록 시 강사 배정 필수")를 지키기 위해 `REQ-F-A-008`의 **저장 시 필수**를 그대로 두고, `REQ-F-A-024`에 **"강사 비활성 → 미래 슬롯 미배정 전환"** 상태 전이를 신설해 미배정이 발생하는 경로를 하나 만들었다 — **기술적으로 ⓐ보다 낫다.** 미배정이 "작성 중 상태의 정상 값"이 아니라 **한 가지 시스템 동작의 결과**로만 존재하므로, 생성·수정 API의 NULL 거부가 예외 없는 단일 규칙이 되고 `IS NOT NULL` 부분 배제 제약도 의미가 분명해진다. 상태 전이는 **지난/미래 경계(시작 시각 > 현재)·예약 유지·회원 화면 비노출·메일 0건·재배정 시 안내**까지 판정 가능한 형태로 적혔다.
- **미배정 UI 3곳의 도달 경로가 실제로 이어졌다.** `SCR-911 §3 섹션 4(비활성 2단계 확인)` → `SCR-902 월 요약` → `SCR-903 §4 경고·필터` → `SCR-907 §2 게시 차단` → `SCR-905 재배정`. 회원 쪽(`SCR-110·111` 미노출 + URL 직접 접근 거부, `SCR-101·102` "강사 조정 중")도 같은 값으로 맞춰졌고, `REQ-F-L-007` 조건 ③이 이미 서버 거부 근거를 갖고 있어 추가 REQ 없이 성립한다. **R1 §4 #1이 요구한 "재현 가능한 게시 전 검사"가 확보됐다.**
- **Should 8건·Could 6건 전량 반영됐다.** ULID 제외·재설정 토큰 로그 유입 차단·날짜 세그먼트 형식 제약·`REQ-F-M-018` 예외·환경 요건 ⑦~⑩ 모두 제안 문장 또는 그 이상으로 들어갔고, 미반영 항목은 0건이다.
- **새로 생긴 문제는 2건(Should)뿐이며 둘 다 같은 뿌리다** — 배정 해제를 **NULL 덮어쓰기**로 정의하면서 ⓐ `SCR-907`이 요구하는 **"이전 강사" 열의 데이터 출처가 사라졌고**(#1), ⓑ **비활성을 되돌리는 경로(재활성)가 문서 어디에도 없다**(#2). 둘 다 게이트를 막지 않는다 — #1은 P4에서 컬럼 1개로 흡수할 수 있고 #2는 규칙 한 줄로 결정된다. **판정은 조건부 승인.**

## 3. 방향을 달리 처리한 3건 — 타당성 판단

**① Must #1을 제3안으로 해소한 것 — 타당하며, 내 권고 ⓐ보다 낫다.**
- ⓐ(작성 중 미배정 허용)는 "정상 입력으로 만들어진 미배정"과 "시스템이 해제한 미배정"이 같은 값으로 섞여, 게시 검사·회원 화면 비노출·재배정 안내 메일의 대상을 **상태만으로 구분할 수 없게** 된다. 제3안은 미배정의 발생 원인이 하나뿐이라 그 구분이 필요 없다.
- API 계약도 단순해진다 — 생성·수정 엔드포인트는 **예외 없이 강사 NULL 거부**, 배정 해제는 **비활성 처리 경로에서만** 일어나는 내부 전이다. 검증 로직에 "작성 중이면 허용" 같은 상태 분기가 생기지 않는다.
- 스키마 귀결이 REQ 본문에 그대로 적혀 있어 P4에서 해석할 것이 없다: 슬롯의 강사 컬럼 **NULL 허용**(전이 상태 표현) / 생성·수정 **API 거부**(애플리케이션 계층) / 강사 중복 배제는 **`강사 IS NOT NULL` 부분 배제 제약**. 공간 겹침 제약(`REQ-F-A-006`)은 강사와 무관하므로 **제약을 두 개로 분리**해 건다 — R1 §5-②에서 "같은 제약에 강사 키를 추가"로 적었던 것을 여기서 정정한다(술어가 다르므로 분리가 맞다).
- 상태 전이의 경계가 `시작 시각 > 현재`로 `REQ-F-A-018`(지난 슬롯 불변)과 같은 기준을 쓴다 — 두 규칙이 충돌하지 않는다.
- 재현 절차가 `REQ-F-A-013` 수용 기준 머리에 들어갔고, 관리자 화면정의서 자체 점검표에도 "미배정 슬롯의 발생 경로가 재현 가능한가 → 예"로 경로가 명시됐다. qa가 그대로 TC를 쓸 수 있다.

**② G-5 "회원 영역 · 비로그인" 칸을 2분할로 채운 것 — 타당하다. 내 권고(전폭 1버튼)가 틀렸다.**
- 내가 "자기 참조"로 본 것은 **고정 바 구성이 영역으로 정해진다**는 전제 위에서였다. planner의 규칙("구성은 로그인 상태로 정해진다")을 따르면 비로그인 상태의 우측 목적지는 `/consult`이고 현재 URL `/booking`과 다르므로 G-6 ① 자기 참조가 아니다. **구현 관점에서도 이쪽이 단순하다** — 고정 바 컴포넌트는 인증 상태 하나만 읽고, 자기 참조 판정은 G-7의 URL 비교 한 곳에서만 한다. 영역 판정이 들어갔다면 분기가 둘로 늘었다.
- `SCR-110 상태별 차이`(비로그인 = 2분할 / 로그인 = 자기 참조 → 전폭 1버튼)와 `REQ-F-M-017`(비로그인 공개 화면 우측 "상담 예약")까지 세 곳이 같은 값이다. **표만 읽어도 한 해석만 나온다** — R1 #6의 부수 지적도 함께 해소됐다.

**③ `REQ-F-A-022`를 정의 검사(역검증)로 교체한 것 — 타당하다.** "24시간 방치 후 관찰"은 P5 기간 안에 실행할 수 없고, 자동 전이가 **없음**을 증명하는 데는 실행 관찰보다 정의 전수 확인이 강한 증거다. ⑩ 확보 시 보조 확인을 덧붙이게 한 것도 맞다. 다만 검사 대상 범위에 대한 확인 1건이 §4 #4다.

**④ (부수) Could #13을 "추가"로 처리한 것 — 동의한다.** WCAG 2.2.1 적용 근거와 IA §2.4 기존 기술과의 일치 회복이라는 이유가 맞다. 세션 만료 경고·연장은 공통 레이어 1회 구현이라 관리자 확대로 늘어나는 것은 **폼 입력값 보존 부분뿐**이며 기존 영역별 공수 항목의 ±30% 안이다. 관련 확인 1건은 §4 #5.

## 5. P4 스키마 확정 가능 여부 — **가능하다**

R1 #1에서 "이것이 스키마를 가른다"고 지목한 지점이 v0.6에 모두 값으로 적혔다.

| 결정 항목 | v0.6의 값 | P4 반영 |
|---|---|---|
| 슬롯의 강사 컬럼 NULL 허용 여부 | **허용** (비활성 해제 상태 표현 — `REQ-F-A-008`) | `instructor_id` nullable |
| 미배정 생성 경로 차단 | **생성·수정 API가 NULL 거부**, 미배정은 비활성 전이로만 발생 | 애플리케이션 계층 검증 + `REQ-F-A-008` 수용 기준 ②의 생성 경로 전수 확인 |
| 강사 중복 배정 배제 제약 | **`강사 IS NOT NULL` 부분 배제 제약** (`REQ-F-A-008`·`REQ-N-035` 2곳 동일) | 공간 겹침 제약과 **분리한 두 개의 배제 제약**으로 건다(술어가 다르다) |
| 정원 불변 조건 | 트랜잭션 + 행 잠금 **또는** 선언적 `CHECK` **둘 다 허용** (`REQ-N-035` 비고) | P4에서 선택 |

- 남은 것은 §4 #1(이전 강사 보존 컬럼) 하나이며 **컬럼 1개 추가**라 제약·인덱스·쿼리 계획에 영향이 없다. 미반영이어도 스키마 확정을 막지 않는다.
- 배제 제약 3종(공간 겹침 · 강사 중복 · 상담 중복)과 반개구간 `[)` 경계값("10:00 맞닿음 허용 / 09:59 거부")은 R1에서 확인한 그대로 유효하며, v0.6에서 어긋난 곳은 **발견하지 못했다.**
- 공수: 이번 개정으로 R2 추정(P4 구현 39.0~57.25작업일)을 벗어나게 만드는 신규 항목은 없다. **§5.3 환경 요건 ⑦~⑩(검증 지원 도구)은 R1과 동일하게 P4 기술 설계에서 별도 항목으로 재산정**하며, §7.4·TR-12에 그 취지가 기록돼 있다. 비활성 상태 전이 구현(일괄 UPDATE + 영향 건수 조회 + 2단계 확인)은 기존 "관리자 강사 관리" 항목의 ±30% 안이다.

## 6. 요약

- **Must: 0건 · Should: 2건 · Could: 3건**
- **판정: 조건부 승인**
- **R1 지적 15건 전량 해결**(Must 1 · Should 8 · Could 6). 미반영 0건.
- 신규 지적 2건(Should)은 모두 **배정 해제를 NULL 덮어쓰기로 정의한 데서 파생**했고 각각 **요구사항 한 줄**로 닫힌다. 게이트를 막지 않는다 — #1은 미반영 시 P4에서 컬럼으로 구현하겠고, #2는 어느 쪽으로 정하든(재활성 허용 / 미도입 명시) 구현 부담이 같다.
- **P4 스키마를 확정할 수 있다.** 기술 설계 착수를 막는 기획 항목은 남아 있지 않으며, 남은 착수 차단 요인은 R1과 동일하게 **I-2(현재 compose 구성)·I-4(도메인·HTTPS 처리)의 고객 회신**(§8.5 D-30)이다 — 이 리뷰의 지적이 아니다.
- **티켓은 발행하지 않았다** — 지적 2건 모두 이 리뷰로 처리 가능하고 수신 대상이 planner 단일이다.
