# 리뷰: P2 기획 산출물 4종 v0.5 (CR-001 회귀) — qa (R1)

## 1. 총평

CR-001로 116 → 241건, 8 → 45화면이 된 것에 비해 **검증 가능성은 오히려 좋아졌다.** §5.0 측정 조건, §5.3 화면 밖 검증 27건 + 환경 요건 8항목, §8.3 미확보 시 Block/N/A 표, 화면정의서의 "예외·상태" 표는 그대로 테스트 케이스로 옮길 수 있는 수준이다. **SCR 45개의 번호·이름·차수는 요구사항 §9 · IA §3 · 화면정의서 2종에서 전수 일치했고, §9가 각 화면에 할당한 REQ가 해당 화면 블록에 빠짐없이 나타나는 것도 전수 확인했다(누락 0건).**

그러나 **반대 방향 대조에서 §9 자체의 선언이 반증됐다.** §9는 "전체 REQ 241건의 완전 분할이며 누락 0건"이라고 명시하는데, 실제로는 **REQ 11건(Must 10 · Should 1)이 §9.1~§9.5 어디에도 없다.** 그중 5건은 §5.3(화면 밖 검증)에도 없어 **P5에서 검증 위치 자체가 지정되지 않은 Must**다. §9를 기준선으로 추적 매트릭스를 만들라고 문서가 지시하고 있으므로, 지금 상태로 P5에 들어가면 Must 10건이 TC 없이 빠진다 — P2 게이트 기준("모든 Must REQ가 화면/비기능 항목과 연결")과 P5 기준("요구사항 추적 100%")을 함께 깬다.

또한 **게이트 판정 모수(§7.3)가 각 REQ 행의 `차수` 열과 재현되지 않고**(실측 1차 35 / 공통 60 / 2차 146 vs 표기 54 / 39 / 148), **REQ-N-039(개인정보 접근 통제·백업 파일 권한)가 `2차`로 분류되어 M-7 규칙상 1차 게이트에서 판정 대상에서 빠진다.** 1차부터 DB에 개인정보를 저장하고 백업을 운영하므로(D-2 · REQ-N-032는 1차) 이 분류는 1차 오픈 판정에 공백을 만든다. Must 3건은 모두 표·셀 수정 수준이라 반영 공수는 작다.

## 2. 이전 라운드 지적 확인

v0.4까지의 qa R1~R3 지적은 모두 종결됐고 본 리뷰는 **CR-001 개정본에 대한 새 R1**이다. 다만 이전 사이클에서 신설된 장치가 v0.5에서 유지·확장됐는지만 확인했다.

|---|---|---|
| 빈 값 (빈 상태) | `REQ-C-L-001`, SCR-101·103·110 빈 상태 문구. **"준비 중" 표현 금지**(M-5)로 자동 검색 오탐까지 차단 | 가능 |
| 입력 오류 | `REQ-F-041`(blur 이후 검증), `REQ-F-R-003`(서버 동일 규칙) | 가능 |
| 전송 실패 | SCR-112 "서버 오류 → 예약이 저장되지 않았음을 분명히 안내", `REQ-N-037` SMTP 실패 주입 | 가능 (단 주입 수단은 지적 #6) |
| 권한 없음 | `REQ-F-A-002`(전 경로 거부), `REQ-N-M-003`(IDOR), `REQ-N-036`(기본값 거부) | 가능 |
| 마감 | `REQ-F-L-002` 날짜 상태 5종, SCR-112 "정원 마감(동시 요청 패배)" + 같은 날 다른 슬롯 제안 | 가능 |
| 미게시 | `REQ-F-L-003`, `REQ-F-A-014`(상태 3종), SCR-112 "미게시 월 슬롯 → 서버 조건 ②로 거부" | 가능 |
| 중복 신청 | `REQ-F-S-005`(차단) / `REQ-F-S-006`(안내만) 분리, SCR-112 "같은 슬롯 중복 요청 → 1건만 성립" | 가능 |
| 차단 (빈도 제한) | §5.0 M-3에 5종 기준값, `REQ-N-019`가 단일 정의처 | 가능 |
| 세션 만료 | SCR-112 "SCR-032 이동 후 복귀, 예약 미성립", `REQ-N-M-002`, `REQ-N-A-004` | 가능 |
| 존재하지 않는 식별자 | SCR-112 "존재하지 않는 `{slotRef}` → 404" | 가능 |
| 강사 미배정 슬롯 URL 직접 접근 | SCR-112 "화면에 노출되지 않아야 하지만 URL 직접 접근 시 거부" | 가능 |

특히 **`REQ-F-L-011`의 "어떤 화면에도 '승인 대기'·'확정 대기' 상태가 존재하지 않는다"** 와 **`REQ-F-A-031`(Won't)의 "근무 기간·휴무 입력 항목 0건 확인"** 처럼 **미구현을 역검증하는 기준**이 들어 있는 점은 P5에서 범위 이탈을 잡는 데 유용하다.

### 5.4 차수 분리 (M-7) — 규칙 방향은 옳고, 분류 1건이 틀렸다

M-7의 설계 자체는 타당하다. 1차 게이트에서 2차 REQ를 미충족으로 세지 않게 하는 장치가 없으면 1차 게이트가 자동 불합격하므로 반드시 필요하다. 검증 결과:

- **"2차로 분류돼 1차에서 빠지지만 실제로는 1차에 필요한 REQ"**: `REQ-N-039` 1건 → **지적 #3**. 나머지 3건(`REQ-N-035`·`036`·`041`)은 1차에 대상이 없어 타당하다.
- **"1차로 분류됐으나 2차에도 이어지는 REQ"**(`REQ-F-004`·`REQ-C-001`·`REQ-C-009` 등): M-7상 2차 게이트는 **전건을 판정**하므로 **검증에서 누락되지 않는다.** 다만 §7.3 집계와 계획서 공수 산정에는 영향이 있어 지적 #2 ②에 함께 적었다.
- **판정 모수 재현 불가**: 지적 #2.
- 1차 게이트에서 실제로 판정할 화면은 **6화면**(SCR-001·002·003·006·008·009 — IA §3.4)이고 이는 §9.2의 차수 표기와 일치한다.

### 5.5 검증 환경 — docker-compose 전제에서 성립한다

| 요건 | compose 전제 성립 여부 |
|---|---|
| ① 스테이징 DB + qa 조회 수단, 운영 DB 권한 미부여 | **성립** (별도 compose 스택). 단 스테이징 자체가 I-8 미회신 — 지적 #5 |
| ② 테스트 수신 메일 + 발송 로그 조회 | 성립. **실패 주입 수단만 누락** — 지적 #6 |
| ③ 로컬 HTTPS 또는 localhost | **성립** (리버스 프록시가 compose에 포함 — `REQ-N-034`) |
| ④ 항목별 독립 검증 전용 설정 (`RETENTION_MINUTES=10` + `RATE_LIMIT=off` 조합) | 성립. 환경 변수로 구현 가능하며 v0.4에서 "단일 모드 스위치 금지"까지 못박혀 있어 그대로 쓸 수 있다 |
| ⑤ 테스트 데이터 삭제 규칙 | 성립 |
| ⑥ 가상 키보드 (Android 실기기·에뮬레이터) | **compose 밖 항목.** 미확보 시 `REQ-F-003` ⑤-2만 "미검증", Block 아님이 명시돼 있어 처리 방침이 이미 서 있다 |
| ⑦ 검증 전용 로그인 세션 | 성립 (목적 문구만 지적 #10) |
| ⑧ 표준 시드 400/200/100 + 동시 요청 20건 부하 스크립트 | 성립. 동시 요청 20건은 단일 앱 컨테이너에서 발생 가능 |

**Safari·iOS 등 검증 불가 항목의 처리는 이미 충분하다.** `REQ-N-003`이 "Safari·iOS Safari는 Windows 로컬에서 검증 수단이 없다 → 미확보 시 Safari 항목만 '미검증'으로 명시하고 **이 REQ 전체를 Block으로 두지 않는다**"로 적었고, §8.5 D-1이 수단 선택을 PM 결정(1차 G3까지)으로 올려 뒀으며, **G-9가 ⓐ(WebKit 폴백 구현)로 확정되어 "구현 대상"과 "검증 수단"이 분리**돼 있다. qa가 P5에서 임의 판단할 여지가 없다 — 이 구조를 그대로 테스트 계획의 "검증 한계" 절에 옮기겠다.

## 6. P5 테스트 계획으로 이월할 입력 (지적 아님)

반영 여부와 무관하게 qa가 테스트 계획에 담을 항목을 남긴다.

1. **추적 매트릭스 기준선** = §9 (지적 #1 반영본). 분모는 지적 #2 ③의 결론을 따른다.
2. **화면 밖 검증** = §5.3의 27건 + 지적 #1 ②로 추가될 6건.
3. **측정 조건·도구** = §5.0 M-1~M-7 + M-5 검색 스크립트·제외 규칙(qa가 확정해 기록할 의무가 명시돼 있다).
4. **검증 한계·Block 예상** = §8.1(노출 값 8묶음) + §8.3(미확보 시 영향) + `REQ-N-003` Safari 단서 + 환경 요건 ⑥ 미확보 시 처리.
5. **표준 시드 정의**(슬롯 400 / 예약 200 / 상담 100)와 **동시 요청 판정 절차**는 qa가 기록하도록 §5.0 M-2 ④·`REQ-N-L-001`이 지정했다 — P4 착수 시 developer에게 시드·부하 스크립트를 티켓으로 요청한다(`TKT-QA-001` 예정, 환경 요건 8항목 + 지적 #6의 실패 주입 수단 포함).
6. **차수 전환 항목 TR-01~TR-12**(§10)는 2차 게이트에서 "전환 완료"를 별도 판정하므로 **2차 테스트 계획에 독립 절**로 둔다. 특히 TR-12가 환경 요건 ⑦⑧을 2차 착수 조건으로 걸어 둔 점을 반영한다.
7. **게이트 조건 확인**: `REQ-N-032` ②의 "복구 리허설 1회"가 §7.4에서 P5 또는 P7 게이트 통과 조건으로 신설 요청됐다 — pmo 게이트 문서에 반영되는지 확인이 필요하다.

## 7. 요약

- **Must: 3건 · Should: 5건 · Could: 4건** (총 12건)
- **판정: 수정 요청**

**Must 3건은 모두 표·셀 수정 수준이며 기획 내용 자체를 바꾸지 않는다** — ① §9에 REQ 11건 추가(5건은 화면정의서에 이미 있는 내용을 기준선에 옮기는 것) ② §7.3 차수 집계 재산정 + 분모 단위 통일 ③ `REQ-N-039` 차수 1셀 변경. PM 방침("최대한 빨리")을 고려해 **게이트를 실제로 막는 사안에만 Must를 부여**했고, 나머지는 Should·Could로 내렸다.

반영 확인은 **지적 #1·#2의 대조를 다시 돌리는 것만으로 끝난다**(§9 참조 REQ와 정의 REQ의 차집합 0건, §7.3 집계와 `차수` 열 일치). 이 두 가지가 맞으면 승인으로 전환한다.
