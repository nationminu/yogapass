# 리뷰: P2 기획 산출물 3종 v0.1 — designer (R1)

## 1. 총평

- 화면 구성·콘텐츠 양은 **360px에서 무리 없이 성립한다.** 메인 7섹션, 오시는 길 5섹션, 예약 폼 7항목은 모바일 1열 기준으로 과하지 않고, 빈 상태(강사 0명·수업 비공개·지도 실패·조회 결과 없음)와 오류 상태가 화면정의서 "예외 · 상태" 표에 화면마다 정의되어 있어 디자인이 추측할 구간이 적다. 문구 초안도 그대로 목업에 넣을 수 있는 수준이다.
- 다만 **공통 요소인 "모바일 하단 고정 바"의 규칙이 확정되지 않았고 문서 간에도 어긋난다.** 겹침 처리가 ①숨김/②여백 두 가지로 병기되어 있고(IA §2.3, SCR-003·004), SCR-005에는 겹침 처리 자체가 없으며, SCR-006·007·008 와이어프레임에는 고정 바가 그려져 있지 않다. 전 페이지 공통 요소라서 이 하나가 8개 화면 전부의 하단 레이아웃과 폼 조작 가능성에 영향을 준다(#1).
- 그 밖에 게이트를 막아야 할 항목은 **예약 페이지에서 예약 CTA가 자기 자신을 가리키는 예외 미정의**(#2), **지도 정적 미리보기의 라이선스 근거 부재**(#3), **description 초안 6건이 REQ-N-010 기준값 70자에 전부 미달**(#4)이다. 네 건 모두 수정 분량은 크지 않다.
- planner가 확인 요청한 3건(고정 바 충돌, 지도 지연 로딩, 문의 폼 위치)에는 **§5에서 수치까지 포함해 회신**했다. 그대로 기획에 반영하면 #1과 #3은 해소된다.

- [x] 로딩/빈 상태/오류 상태 — 빈 상태·오류 상태는 잘 정의됨. **로딩(조회 중) 1건 누락, 결과 상태의 포커스 이동 미정의**(#8)

- [x] 이미지 요구 개수·비율 정의 — **부분 정의.** `[IMG: …]` 5곳에 비율은 있으나 총량표·OG·파비콘 규격·고객 제출 규격이 없음(#9)
- [x] 접근성을 디자인에서 충족할 때 기획의 걸림돌 — 큰 걸림돌 없음. 대비 4.5:1·키보드·포커스·색상 단독 전달 금지·폼 오류 프로그램적 연결이 REQ-N-006·008에 있고 Hero 오버레이까지 지시되어 있다. **터치 타깃 최소 크기만 REQ 누락**(#7)

## 5. planner 확인 요청에 대한 designer 회신

### (1) 하단 고정 바와 폼 제출 버튼 충돌 → **"고정 바 유지 + 하단 여백 확보"(②)로 확정 권고**

| 항목 | 확정안 |
|---|---|
| 고정 바 높이 | **56px** + 하단 안전 영역(`env(safe-area-inset-bottom)`) |
| 폼 화면 본문 하단 여백 | **`56px + safe-area + 16px`(최소 72px)** — SCR-003 `#contact`, SCR-004, SCR-005에 적용 |
| 제출 버튼과 고정 바 사이 최소 간격 | **16px** (터치 오조작 방지) |
| 적용 뷰포트 | 360px·768px (고정 바가 노출되는 전 구간) |
| 고정 바 내부 | 2분할 버튼 각각 최소 44×44px, 사이 구분선 1px, 버튼 라벨은 아이콘 + 텍스트 병기(색·아이콘 단독 전달 금지) |

**"폼 영역 진입 시 숨김"(①)을 채택하지 않는 사유**
1. 스크롤 위치에 따라 나타났다 사라지면 **레이아웃 이동(CLS)** 이 생기고, 사용자가 방금 본 버튼이 사라져 조작 예측이 깨진다.
2. 폼 화면에서 고정 바가 사라지면 **전송 실패 시 대체 연락 수단(REQ-F-046, REQ-F-R-011)이 화면에서 함께 사라진다.** 실패 안내 안의 전화 링크 하나만 남아 회복 경로가 좁아진다.
3. "폼 영역 진입"의 판정 기준(어느 요소가 몇 % 보일 때)을 기획·디자인·구현이 각각 정하게 되어 명세가 흔들린다. 여백 방식은 판정 로직이 없다.

**단, SCR-004에서는 고정 바 구성을 바꾼다** — 지적 #2와 연결. 예약 페이지에서는 "예약 신청" 버튼이 자기 자신을 가리키므로 **"전화 문의" 1개 버튼(전폭)** 으로 대체한다. SCR-005도 같은 이유로 "예약조회" 메뉴만 활성 표시하고 고정 바는 기본 2분할을 유지한다(예약 신청 버튼이 유효한 이동 경로이므로).

### (2) 지도 지연 로딩 → **"클릭 투 로드"(명시적 버튼) 채택 권고**

| 방식 | 판단 |
|---|---|
| 뷰포트 진입 시 로드(IntersectionObserver) | **미채택.** 오시는 길은 h1 바로 다음이 지도라서 360px에서 **진입 직후 지도가 뷰포트에 들어온다.** 사실상 즉시 로드와 같아 REQ-N-004(Lighthouse 모바일 90점)·REQ-N-005 달성에 거의 기여하지 않는다 |
| **정적 대체 + 클릭 시 임베드 로드** | **채택 권고.** 초기 로드에서 지도 리소스가 완전히 빠져 성능 기준 달성이 확실하고, 지도를 로드하지 않아도 주소·교통·길찾기로 화면이 완결되어 REQ-F-035(지도 접근성 대체)와도 일치한다 |

**구현·접근성 기준 (designer가 P3 페이지 디자인에 수치로 넣는다)**
- 대체 영역: 브랜드 그래픽(또는 정적 지도 API 이미지) + 중앙에 **"지도 불러오기" 버튼**(최소 44×44px, 텍스트 라벨 포함). 높이는 로드 후 지도와 **동일한 240~280px(360px 기준)** 로 고정해 레이아웃 이동 0.
- 로드 후: 버튼을 제거하고 지도 `iframe`에 `title="요가패스 위치 지도"`를 유지. **포커스는 `iframe`이 아니라 지도 섹션 제목으로 이동**시킨다(iframe 안으로 들어가면 키보드 사용자가 빠져나오기 어렵다).
- "지도 불러오기"는 외부 서비스로 개인정보(IP 등)가 전달되는 시점이므로, 버튼 아래 한 줄 고지("지도를 불러오면 {지도 서비스}로 연결됩니다")를 두면 REQ-F-052 위탁 고지와도 정합적이다.
- **지적 #3과 연결**: 대체 이미지에 지도 화면 캡처를 쓰지 않는다. 메인(SCR-001 섹션5)은 **지도 이미지 없이 주소·교통 텍스트 + "지도·길찾기 보기" 버튼**만 두기를 권고한다(라이선스 리스크 제거 + 메인 LCP 부담 감소, 대신 브랜드 그래픽 1장으로 시각 밀도 보완).

### (3) 문의 폼 위치(오시는 길 하단 `#contact`) → **기준안에 동의**

- **디자인상 실현 가능하다.** 360px 기준 오시는 길 전체 예상 스크롤은 약 2,800~3,300px(지도 280 + 정보 7행 약 560 + 안내 120 + 폼 약 1,200 + 헤더·푸터·여백)로, 단일 페이지가 감당하는 범위다. 페이지를 늘리지 않는다는 계획서 §2.1 원칙과도 맞는다.
- **다만 planner가 지적한 "메뉴명에서 문의 폼을 떠올리기 어렵다"는 단점은 보완책이 실제로 IA에 들어가야 해소된다** → 지적 #13(푸터 링크 누락).
- designer가 추가로 제안하는 보완 3가지:
  1. 오시는 길 h1 아래에 **페이지 내 이동 칩 2개**("지도·오시는 길" / "문의하기")를 두어 진입 즉시 폼의 존재를 알린다.
  2. 앵커 진입 시 섹션 제목이 고정 헤더에 가리지 않도록 `scroll-margin-top = 헤더 높이 + 16px`를 적용한다(지적 #6의 헤더 sticky 확정이 선행 조건).
  3. `#contact`로 진입해도 **입력 필드에 자동 포커스하지 않는다.** 모바일 키보드가 즉시 올라와 맥락을 잃게 되므로, 섹션 제목(`tabindex="-1"`)에만 포커스를 준다.
- Q4에서 "별도 문의 페이지 희망"으로 회신되어도 **디자인 영향은 크지 않다.** 폼 컴포넌트(CMP)와 페이지 템플릿을 그대로 재사용하므로 추가되는 디자인 산출물은 페이지 디자인 1건과 목업 1건이다. 다만 GNB 항목이 6개로 늘어나면 데스크톱 헤더의 예약 강조 버튼과 경쟁하므로, 그 경우 **문의는 GNB가 아니라 푸터·본문 CTA로만 노출**하는 구성을 권고한다.

### (4) designer가 P3에서 책임지고 정의할 항목 (기획에서 정하지 않아도 되는 것)

토큰(컬러·타이포·간격·radius·shadow·motion·breakpoint), 컴포넌트 상태(기본·hover·focus·active·disabled·오류), 대비 검증 결과, 이미지 크롭 기준·세이프 영역, 오버레이 불투명도, 고정 바·헤더 높이 수치, 아이콘 세트 라이선스, 에셋 총량표, prefers-reduced-motion 대응, 400% 확대 시 고정 바 처리.

> 참고: **화이트·블루 톤(REQ-N-025)에서 대비 기준(REQ-N-006)을 지키려면 밝은 파랑을 본문·라벨 색으로 쓸 수 없다.** 흰 배경 위 밝은 파랑(#3B82F6 계열)은 대비가 약 3:1로 본문 기준 미달이고, 4.5:1을 넘기려면 상당히 어두운 파랑이 필요하다. 이 제약은 기획 수정 사항이 아니라 P3 팔레트 설계에서 흡수하며, 컨셉 시안에 대비 측정값을 함께 제시하겠다. 다만 **로고 원본·브랜드 색상(REQ-C-001, Q10, 기한 09-18)이 미수령 상태에서 컨셉 시안을 만들면 팔레트가 확정되지 않는다.** 미수령 시 designer는 임시 워드마크와 잠정 팔레트로 컨셉을 진행하고 로고 수령 후 팔레트를 보정하는 방식으로 대응하겠다(RSK-010).

## 6. 요약

- Must: 4건 · Should: 9건 · Could: 5건 (총 18건)
- 판정: **수정 요청**
- Must 4건은 모두 **문서 간 불일치·예외 미정의·라이선스 근거 부재** 유형이며, §5 회신을 그대로 반영하면 #1·#3은 별도 판단 없이 해소된다. #2는 REQ-F-003에 예외 1줄과 수용 기준 한정, #4는 REQ-N-010 기준값과 §6.3 초안 중 한쪽 정리로 끝난다. 새로운 조사나 고객 회신이 필요한 항목은 없다.
- **화면 구성·콘텐츠 양·빈 상태·오류 상태 정의는 P3 착수에 충분하다.** Must 4건 반영 후에는 컨셉 시안(2~3안) 작업에 들어가는 데 기획 측 차단 요소가 없다.
- P3 착수에 실제로 걸리는 것은 기획이 아니라 **고객 회신**이다: Q10(로고·브랜드 색상, T-15), Q11(사진 조달 방침, T-16), Q21(참고 사이트·피하고 싶은 스타일, T-26). 셋 다 미회신이면 컨셉 시안은 "사진 0장 전제 + 잠정 팔레트"로만 만들 수 있고, 회신 후 팔레트·이미지 방향 재작업이 생긴다. 최소 **Q10·Q21을 컨셉 시안 착수 전까지** 확보하도록 PMO·PM에 요청한다.
