# 리뷰: P2 기획 산출물 v0.1 (요구사항·IA·화면정의서) — developer (R1)

## 1. 총평
- 구현 관점에서 완성도가 높다. 예약 영역을 `REQ-*-R-*`로 분리하고 선택지별 차이표를 붙인 C-3 대응, 화면별 예외·상태 표(전송 중·실패·honeypot·시도 초과·파기 후 조회), 조회 결과 URL 금지·no-store, 데이터 파일 분리(REQ-F-021·064)는 P1에서 내가 지적한 기술 요건이 그대로 요구사항으로 내려온 결과다. 우선순위 집계(기능 57 · 비기능 33 · 콘텐츠 21 = 111, Must 76)도 ID를 하나씩 대조해 검산했고 불일치가 없다.
- **Must 3건을 지적한다.** ① §4.5 선택지별 차이표의 A안·C안 열에 기술적으로 잘못된 "삭제" 표기가 있다. 이 표는 ADR-001(09-16) 결정 자료로 쓰이므로 틀린 채로 결정되면 요구사항이 실제로 사라진다. ② 수용 기준 5건이 구현·검증 불가능하거나 서로 판정이 겹친다(P5에서 합격·불합격을 가릴 수 없다). ③ 예약번호를 완료 화면에 전달하는 방법이 어디에도 정의되지 않았고, 분석 도구(REQ-F-062)를 설치하면 예약번호가 URL로 외부 사업자에게 넘어갈 수 있는데 이를 막는 요구사항이 없다.
- 규모는 **건수보다 서버 측 항목이 기간을 좌우한다.** 111건 자체는 과다하지 않지만, P2에서 확정된 공통 영역만 다시 추정하면 계획서 부록 A의 "공통 정적 영역 3~4작업일"이 **4~5작업일**로 늘어난다(부록 B). ADR-001 일정 대응안 판단에 쓰이는 값이므로 pmo에 전달이 필요하다 → #13.
- planner가 확인 요청한 4건(예약번호 무작위성, 조회 실패 응답 동일화, JS 비활성 범위, 지도 지연 로딩과 성능 양립)은 **부록 A**에 구현 방법·공수·검증 방법까지 적어 답한다.

  - #1(선택지 차이표의 기술 오류)은 **ADR-001 결정(09-16) 전에** 고쳐야 결정이 틀린 자료 위에서 이뤄지지 않는다. 가장 급하다.
  - #2(검증 불가 수용 기준)와 #3(예약번호 노출 경로)은 G2 통과 기준("모든 요구사항에 수용 기준 존재", Must REQ의 화면·비기능 연결)과 직결된다.
  - Should 10건은 대부분 비고·수용 기준 한두 줄 추가로 해결되며 문서 구조를 바꾸지 않는다.
  - #13(공수 재추정)은 planner가 아니라 **pmo에게 전달되어야 할 사항**이다. 오케스트레이터가 ADR-001 자료·계획서 1.1 개정에 반영되도록 전달해 주기 바란다.

## 부록 A. planner 확인 요청 4건에 대한 developer 답변

### A-1. 예약번호 무작위성 구현 (REQ-F-R-006, REQ-N-R-002, SCR-005·007 `YP-XXXXXX`)
| 항목 | 답변 |
|---|---|
| 생성 방식 | 암호학적 난수 생성기(`crypto.getRandomValues` / `crypto.randomUUID`)로 만든다. 순번, 시각(타임스탬프), 입력값(이름·휴대폰)에서 유도한 값이나 단순 해시는 쓰지 않는다. 시각 기반 값은 신청 시각을 알면 탐색 공간이 급격히 줄어든다 |
| 길이·엔트로피 | **40비트 이상**을 권고한다. 예: Crockford Base32(0-9, A-Z에서 I·L·O·U 제외) **8자 = 40비트 ≈ 1.1조 가지**. 접두어 `YP-`는 사람이 알아보기 쉬우므로 유지해도 되지만 엔트로피에 포함하지 않는다 |
| 화면정의서 예시 문제 | 현재 `YP-XXXXXX`(6자)를 문자 그대로 구현하면 대문자+숫자 기준 36^6 ≈ 22억이다. 조회 시도 제한(REQ-F-R-024)이 있으면 실사용 공격은 막히지만, 제한이 우회되거나 로그가 유출되는 상황까지 고려하면 여유가 적다. **`YP-XXXXXXXX`(8자)로 고치기를 권고한다.** 사용자 입력 부담은 2자 차이로 크지 않다 |
| 입력 편의 | 대소문자를 구분하지 않고(입력값을 대문자로 정규화), 하이픈·공백을 제거한 뒤 비교한다. 혼동 문자를 뺐으므로 전화로 불러주기도 쉽다 |
| 충돌 처리 | 저장소에 예약번호 고유 제약을 걸고, 충돌이 나면 재생성한다(최대 3회) |
| 검증 방법 (수용 기준 대체안) | ① 생성 함수 코드 확인 — 난수원·문자 집합·길이 ② 1,000건 생성 스크립트로 중복 0건, 문자 분포 편향 없음 확인 ③ 연속 발급 20건에서 앞뒤 번호 간 상관 없음. "20건 육안 비교"만으로는 판정 근거가 되지 않는다 |
| 공수 | 0.1작업일 (기존 추정 안에 포함) |

### A-2. 조회 실패 응답 동일화 구현 (REQ-F-R-023, SCR-005 예외 표)
| 항목 | 답변 |
|---|---|
| 동일화 대상 | **본문 · HTTP 상태 코드 · 응답 헤더 · 응답 시간** 네 가지를 모두 같게 해야 한다. 문서는 본문과 상태 코드까지만 요구하고 있는데, 응답 시간 차이만으로도 "그 예약번호는 존재한다"는 사실이 드러난다(존재하면 휴대폰 비교까지 수행해 응답이 느려진다) |
| 구현 | ① 예약번호로 조회한다. 없으면 **더미 레코드로 같은 비교 절차를 수행**해 실행 경로 길이를 맞춘다. ② 휴대폰 번호 비교는 조기 반환하지 않고 상수 시간 비교를 쓴다. ③ 성공·실패 모두 같은 상태 코드(200 권고)와 같은 형태의 본문을 반환하고, 실패 본문에는 존재 여부를 암시하는 어떤 값도 넣지 않는다. ④ 응답 지연 편차를 더 줄이려면 최소 응답 시간(예: 300ms)을 두고 그보다 빨리 끝나면 대기한다 |
| 로그 | 서버 로그에도 "예약번호 없음 / 휴대폰 불일치"를 구분해 남기면 로그 유출 시 단서가 된다. 실패는 한 종류(`lookup_failed`)로만 기록하고, 운영 진단이 필요하면 별도 보호된 지표로 집계한다 |
| 보관 기간 경과분 | SCR-005 예외 표의 "파기된 신청도 같은 문구" 판단이 정확하다. 구현상으로도 파기 후에는 레코드가 없으므로 자연히 같은 경로를 탄다 |
| 검증 방법 | 두 경우(존재하지 않는 번호 / 존재하는 번호 + 틀린 휴대폰)를 각 50회 호출해 상태 코드·본문 바이트·응답 시간 분포를 비교한다. 수용 기준에 "응답 시간 분포에 유의한 차이가 없다"를 추가하기를 권고한다 |
| 공수 | 0.2~0.25작업일 (기존 추정 안에 포함) |

### A-3. JavaScript 비활성 시 폼 동작 범위 (지적 #6의 근거)
| 구간 | 권고 | 근거·공수 |
|---|---|---|
| 정보 제공 콘텐츠 (SCR-001·002·003의 지도 외 영역·006·008) | **JS 없이 100% 표시·동작** (Must) | 정적 사이트 생성 방식이면 이미 HTML로 출력된다. 추가 공수 0. 검색 크롤러·저사양 환경에도 유리하다 |
| 공통 헤더·모바일 메뉴 | 메뉴 열고 닫기는 JS가 필요하다. **JS 없을 때는 메뉴 항목이 펼쳐진 상태로 보이게** 하거나(CSS `:target`·`details` 활용) 푸터 링크로 전 페이지 도달이 가능하면 충족된다(REQ-F-006) | 추가 공수 0~0.1일 |
| 지도 (SCR-003) | `<noscript>`에 주소 텍스트 + 외부 지도 링크를 노출한다. REQ-F-035(지도 접근성 대체)와 같은 내용이므로 사실상 이미 요구되어 있다 | 추가 공수 0.1일 |
| 폼 3종 (문의·예약 신청·예약조회) | **JS 없이 제출까지 지원하는 것은 권하지 않는다.** `<noscript>`로 전화 문의 안내와 대표 번호를 노출하는 선까지가 적정하다 | JS 없는 제출을 지원하려면 서버가 HTML 응답(303 리다이렉트)을 돌려주는 경로를 따로 만들어야 한다. 그러면 ① 예약번호를 완료 화면에 넘기는 수단이 JS 경로와 다르게 필요하고(#3) ② 중복 제출 방지·오류 시 입력값 유지·no-store 처리를 두 경로에 각각 구현해야 하며 ③ 조회 결과는 URL에 식별 정보를 담을 수 없어 POST 후 서버 렌더가 강제된다. 합계 **+0.5~1작업일**이고 검증 대상도 두 배가 된다 |
| 공통 | JS 유무와 무관하게 폼 마크업은 `<form action method>`와 라벨을 갖춘 네이티브 구조로 만든다. 자동완성·엔터 제출·스크린리더 동작이 여기에 달려 있다(REQ-N-008) | 추가 공수 0 |

### A-4. 지도 지연 로딩과 성능 점수의 양립 (REQ-F-032, REQ-N-004·005)
- **충돌하지 않는다. 오히려 지연 로딩이 90점 달성의 전제다.** Lighthouse는 페이지 로드 시점을 기준으로 측정하므로, 사용자가 조작하기 전까지 지도 스크립트·타일을 요청하지 않으면 점수에 거의 영향을 주지 않는다. 지도 임베드를 초기에 로드하면 스크립트 수백 KB와 타일 이미지가 주요 지표를 직접 끌어내린다.
- 다만 아래 3가지를 지키지 않으면 지연 로딩을 해도 점수가 떨어진다.
  1. **미리보기 이미지가 LCP 요소가 된다.** 적정 크기로 잘라 WebP 등으로 제공하고, 화면 밖이면 `loading="lazy"`를 쓴다. 이미지 조달 방법은 지적 #4.
  2. **클릭 후 임베드가 들어오면서 레이아웃이 밀린다(CLS).** 지도 컨테이너의 높이·비율을 미리 고정한다(화면정의서 SCR-003 "지도 높이 240~280px" 표기가 이미 이 역할을 한다).
  3. **측정 시나리오를 고정한다.** "초기 로드 상태(지도 미로드)"에서 측정한다는 조건이 없으면, 지도를 로드한 뒤 측정한 값으로 결함이 등록될 수 있다 → 지적 #10.
- 결론: REQ-F-032의 수용 기준을 점수가 아니라 **네트워크 관찰**로 바꾸면(지적 #2(a)) 두 요구사항이 각자 독립적으로 검증된다.
