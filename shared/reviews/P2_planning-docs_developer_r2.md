# 리뷰: P2 기획 산출물 v0.2 (요구사항·IA·화면정의서) — developer (R2)

## 1. 총평
- **R1 지적 17건 중 16건이 해결됐다.** Must 3건은 모두 해결됐다 — ①§4.5 차이표 A열 3건·C열 1건의 "삭제" 표기가 정정됐고 표기 정의("삭제/변경/해당 없음")까지 추가됐다 ②판정 불가 수용 기준 5건이 관찰·수치 기준으로 다시 쓰였다(예약번호는 CSPRNG·40비트·Base32 8자·1,000건 중복 0건, 화면정의서 예시도 `YP-A7KD-M2XF`로 교정) ③예약번호 쿼리스트링 금지 제약과 REQ-N-R-010(신설)이 들어가고 `/reservation/complete`의 robots Disallow가 제거됐다. 남은 1건(#13 공수 재추정)은 planner 범위에서는 처리됐고 **pmo 조치가 미완**이다.
- **신규 Must는 1건이다.** §4.5의 표 **(1)과 표 (2)가 C안에서 서로 반대되는 판정**을 하고 있다 — 표 (1)은 REQ-F-R-001·007·009·011을 "삭제", 표 (2)는 같은 4건을 "변경(남음)"으로 적었다. v0.2에서 표 (2)만 새 정의에 맞춰 재작성되고 표 (1)의 해당 칸이 남은 결과다. R1 #1과 같은 자리·같은 성격의 문제이고, ADR-001(09-16) 결정 자료이자 "결정 후 §4를 정리하는 근거"라서 그대로 두면 C안 결정 시 요구사항 4건의 존폐가 두 갈래로 갈린다. **표 (1) 4칸 수정으로 끝나는 사안이다.**
- 새로 추가된 §3.0·§5.0·§5.3·§9는 구현·검증 관점에서 큰 개선이다. 특히 §5.0 M-1~M-6(측정 조건·기준값·검사 도구)과 §5.3(화면 밖 Must 13건의 검증 시점·수단·증거)은 P4 기술 설계와 P5 테스트 계획이 같은 값을 보게 만든다. §9를 단일 기준선으로 선언한 판단도 옳다 — 다만 그 기준선에서 **REQ 5건이 빠져** 있어 선언한 효과가 반감된다(#3).
- **규모(116건·Must 79)는 여전히 과다하지 않고, 낮춰야 할 Must는 실질적으로 없다.** v0.2 신규 Must 3건(REQ-N-028·029·REQ-N-R-010)의 추가 공수는 합쳐 약 0.2작업일이다. 다만 §3.0 G-9(가상 키보드 시 고정 바 숨김)는 신규 항목 중 유일하게 공수(+0.25일)와 검증 리스크(iOS Safari 수단 미확보 — D-1)를 함께 가지며, 수용 기준도 없다(#4). 공통 정적 영역 재추정치는 **4.5~5.5작업일**로, 계획서 WBS의 P4 구현 배정(3.5~4작업일)을 넘어선다(부록 A, #8).
