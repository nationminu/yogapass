# 리뷰: 기술 설계서 v0.1 — devops (R1)

## 1. 총평

배포·운영 관점에서 **이 설계로 운영에 올릴 수 있다**. 특히 ⓐ 우리 compose에 nginx를 넣지 않고 `proxy_pass` + 헤더 전달로 요청을 최소화한 선택, ⓑ 정적 서빙을 WhiteNoise로 앱 안에 가둬 **남의 nginx와의 결합을 끊은 것**, ⓒ 스케줄러를 호스트 crontab이 아닌 컨테이너로 둔 것, ⓓ 되돌릴 수 없는 마이그레이션 식별 방침(`# IRREVERSIBLE`)과 배포 직전 백업을 절차에 박아 넣은 것은 **운영자 1명이 감당할 수 있는 구조**를 만든 판단이다. §13(로컬/운영 차이 10건)과 §10.6(QA 도구 안전장치)은 devops가 따로 요구했어야 할 항목을 먼저 적어 둔 것이라 P7 계획서 작성이 그만큼 빨라진다.

막아야 할 문제는 2건이다. **① 백업의 "실행 주체·실패 알림 경로"가 설계에 없다** — REQ-N-032는 Must이고 복구 리허설은 G7a 통과 조건(SC-6)인데, `backup` 컨테이너가 무엇으로 일 1회 실행되고 실패를 **누구에게 어떻게 알리는지**가 §3.2~§3.4·§12.5 어디에도 없다(`backup`은 Django 앱이 아니라 아웃박스에 기록할 경로가 자명하지 않다). 검증 요건 ⑨ⓑ(백업 강제 실패)의 확인 경로도 함께 비어 있다. **② 스테이징에 접근 제어가 설계되지 않았다** — REQ-N-040 수용 기준은 `noindex + 인증`인데 설계는 `X-Robots-Tag`만 있고, 같은 환경에서 `QA_TOOLS_ENABLED`·`qa_session`(세션 발급)이 켜진다. 개인정보 형태의 검증 데이터가 든 무인증 공개 URL은 §10.6이 스스로 "Critical"이라고 적은 상태와 같다.

그 밖에 **HTML 응답 압축 주체가 빠져 있고**(§12.3의 "재압축 불필요"는 정적 자산에만 맞다), **앱이 죽은 상태의 점검 화면(503)을 Django 템플릿으로 둘 수 없으며**, **스테이징 HTTPS가 도메인 확정(10-16)에 묶여 §13의 스테이징 판정 5건이 배포 주간으로 밀릴 수 있다.** 모두 설계 문구 몇 줄과 devops 작업으로 해결되므로 Should로 둔다. §16 devops 질의 4건은 §6에 답했다.

## 3. 검토 관점 체크리스트

- [x] **compose 3환경 성립성** — 공통 `compose.yaml` + override 1개 + 프로젝트명 분리는 성립한다. 볼륨(명명 볼륨/바인드), DB 포트 비게시, 헬스체크, `unless-stopped`, 로그 회전 모두 정의돼 있다. 단 **서비스 집합이 환경별로 다르다**(로컬 `mail` / 운영 `backup`) → #3
- [x] **기존 nginx 연결** — compose에 nginx를 넣지 않는 선택은 타당하다(권한·공유 리스크 회피). 요청 항목은 전부 `server`/`location` 레벨이라 **다른 서비스와 충돌하지 않는다** → §6 Q-5. 누락 항목 3건(#4·#5·#8)
- [x] **I-2-a 분기 처리** — 기본안(호스트 nginx + `127.0.0.1:${APP_PORT}`)이 옳다. 컨테이너 판명 시 전환 비용 0.25일 평가에 동의 → §6 Q-1
- [x] **배포 절차·롤백** — 6단계 절차는 운영자가 따라 할 수 있는 수준이다. 단 마이그레이션 중 scheduler 동시 실행(#6), 롤백용 이전 이미지 보존 보장(#7)이 빠졌다. 무중단 아님(TR-9)은 수용 — 다운타임 목표치만 명시 필요(#8)
- [x] **백업·복구** — 방식(`pg_dump -Fc`)·주기·회전·무결성 확인·`restore.sh`·리허설 계획까지 설계돼 있으나 **실행 주체·실패 알림이 비었다(#1)**. 오프사이트 부재 위험도 평가는 §6 Q-6
- [x] **운영 부담** — 운영자 1명 기준 감당 가능. 다만 **장애 인지 수단이 없다**(#9). 패치·인증서·로그는 P8 운영 가이드 항목으로 식별했다(§5)
- [x] **환경 변수·비밀 정보** — 이름만 표기, 런타임 주입, `.env` 제외, `production`에서 `QA_*` 기동 거부까지 적절. `.env` 자체의 보관·재구축 절차가 비었다(#10)
- [x] **도메인·SMTP 미정 상태의 1차 배포 가능성** — `SITE_BASE_URL` 교체만으로 전환되게 설계한 점은 정확하다. 단 **도메인 없이 1차 운영 배포는 불가**(계획서 §5 "V-1 미확보 → 1차 배포 불가", 제약 C-4). 스테이징 HTTPS 선행 문제는 #2·#11
- [x] **일정** — G7a(10-30)까지 devops 소요와 선행 확보 항목은 §6 Q-7

## 6. §16 devops 질의에 대한 답변

> 호출 지시의 "Q-1~Q-4"는 설계서 §16 기준 **devops 앞 질의 4건 = Q-1 · Q-5 · Q-6 · Q-7** 로 해석했다(Q-2·Q-3·Q-4·Q-8은 qa 앞 질의다).

### Q-1 — §3.1 I-2-a 전제(운영 nginx = 호스트 설치, 앱은 `127.0.0.1:${APP_PORT}` 게시)가 맞는가

**현 시점에 "맞다"고 확인해 줄 수 없다.** infra 인터뷰 v0.5 §9.2의 I-2-a는 **미회신 상태**이고(설계서 §14.3 O-2도 같음), 운영팀에 확인해야 하는 항목이다. 추측으로 답하지 않는다.

**다만 설계 판단으로는 기본안을 그대로 유지하는 것이 옳다.**
1. `ports: "127.0.0.1:${APP_PORT}:8000"` 는 **호스트 설치 nginx에서 그대로 동작**하고 외부에 열리지 않아 가장 안전하다.
2. nginx가 컨테이너로 판명돼도 전환은 **override 한 블록**이다 — `ports` 제거 + 기존 외부 네트워크 참여(`external: true`), nginx 쪽은 `proxy_pass http://yogapass-app:8000`. **0.25작업일 이내 평가에 동의한다.**
3. 전환 비용을 더 낮추려면 `compose.prod.yaml`에 **주석 처리된 external network 블록**을 미리 넣어 두면 된다(권고이며 강제 아님, 설계 변경도 아님).

**devops가 지는 책임**: I-2-a~d를 운영팀에 확인해 **10-09(금)까지 배포 계획서 초안에 반영**한다(배포 리허설 10-26 기준 2주 전). 그때까지 회신이 없으면 PM 조치 필요 사항으로 올린다. **구현 착수는 막지 않는다** — 기본안으로 진행해도 손실이 없다.

**추가 확인 요청 1건**: 운영과 스테이징이 같은 서버에 있으므로 **`APP_PORT`가 2개 필요**하다(§3.5 "별도 포트"와 일치). 기존 서비스가 쓰는 포트 대역을 피해야 하므로 값은 devops가 배포 계획서에서 지정한다 — 설계에는 **환경 변수로만 두고 숫자를 박지 말 것**(현 설계가 이미 그렇다, 유지 요청).

### Q-5 — §12.3의 `proxy_intercept_errors off` 와 별도 로그 파일이 기존 운영 정책과 충돌하지 않는가

**충돌하지 않는다. 요청 목록 전체가 `server`/`location` 레벨 지시어이고 전역(`http`) 변경 요청이 0건인 점이 이 설계에서 가장 잘 잡힌 부분이다.**

| 요청 항목 | 충돌 여부 | 비고 |
|---|---|---|
| `proxy_intercept_errors off` | **없음** | nginx **기본값이 off**다. 따라서 "변경 요청"이 아니라 **"기존 `http` 블록에서 on으로 켜 두지 않았는지 확인"** 항목이다. 켜져 있어도 우리 `server`/`location`에서 off로 재정의할 수 있고 **다른 서비스의 상속값은 유지**된다. 설계 문구를 "요청" → "확인 + (필요 시) 우리 블록에서 재정의"로 바꿀 것을 권고 |
| 별도 access/error 로그 | **없음** | server 레벨 지정 가능. 단 **호스트 logrotate 대상에 새 파일 2개 등록**이 필요하다(운영팀 작업, 누락 시 디스크 증가). 문의 폼은 POST라 access 로그에 개인정보가 남지 않으며, 이는 식별 정보를 URL·쿼리에 넣지 않는 §6.1 설계와 일관된다 |
| `proxy_pass` + `X-Forwarded-*`·`Host` | 없음 | `$proxy_add_x_forwarded_for` 사용. **기존 nginx 앞에 또 다른 프록시(CDN 등)가 있는지**에 따라 `TRUSTED_PROXY_COUNT` 값이 달라진다 → 스테이징에서 실측해 확정(§13 #6). 환경 변수로 둔 현 설계가 옳다 |
| `client_max_body_size` | 없음 | server 레벨. 1차는 업로드가 없으므로 **2차에 올려도 된다**(1차 요청 목록에서 빼도 무방) |
| `error_page 502 503` | **조건부** | 지시어 자체는 충돌 없으나 **정적 파일 배치 권한(I-2-b)이 추가로 필요**하다 → 지적 #5 |
| 압축 | — | 지적 #4 — `gzip_proxied any`를 **우리 server 블록 한정**으로 추가 요청 |
| HTTPS·HSTS | devops 소관 | `includeSubDomains` 주의 → 지적 #12 |
| (추가) 스테이징 `auth_basic` | — | 지적 #2 |

즉 **최종 요청 목록은 8행 → 9행**이 되고 전부 우리 server 블록 안에서 끝난다. `deploy/nginx/yogapass.conf.sample`은 **운영용·스테이징용 2개로 분리** 제공할 것을 권고한다.

### Q-6 — 백업 보관 위치·퍼미션·오프사이트(O-3)와 O-1(운영자 PostgreSQL 숙련도)

**① 보관 위치·퍼미션 (REQ-N-039 — devops가 배포 계획서에 기록한다)**
- `${BACKUP_DIR}`는 **DB 데이터 볼륨과 다른 디렉토리**에 두고 디렉토리 `0700` · 파일 `0600` · 소유자를 배포 계정으로 제한한다. 컨테이너에는 해당 경로만 마운트한다.
- 개인정보(이름·연락처·문의 내용)가 평문으로 들어 있는 파일이므로 **웹 문서 루트·공유 디렉토리 아래에 두지 않는다**(가장 흔한 유출 경로다). 경로·권한·접근 가능 계정 목록을 `devops/07_deploy-plan.md`에 기록하고 qa가 P5에서 대조한다(REQ-N-039 검증 방법).

**② 오프사이트 부재 위험도 — 1차 "중", 2차 "높음". 1차 오픈은 이대로 진행해도 된다.**

| 자산 | 서버 전손 시 | 판단 |
|---|---|---|
| 소스·콘텐츠 시드(`content/*.yml`) | git 저장소에 존재 → **소실 없음** | — |
| DB (1차: 문의 접수 건) | **소실**. 오픈~사고 시점까지 수십 건 수준이고 SMTP 연결 시 알림 메일이 수신자 메일함에 사본으로 남는다 | 영향 **중** |
| `.env` (시크릿) | **소실**. 단 전부 재발급 가능(지적 #10) | 영향 중 |
| DB (2차: 회원·예약·상담·경고·해피콜) | **소실 = 서비스 재개 불가.** 대체 사본이 없다 | 영향 **높음** |

- **O-3에 대한 devops 권고**: 1차는 **ⓐ 같은 서버의 다른 디렉토리/디스크로 1차 복사**(즉시 적용, 비용 0, 디스크 장애만 대비) + **ⓑ 주 1회 암호화 반출**(`pg_dump` 결과를 `gpg`/`age`로 암호화해 운영팀 보유 다른 호스트로 전송) 조합. **암호화 없이 반출하지 않는다** — 개인정보 파일이 서버 밖으로 나가는 순간 유출 경로가 하나 늘기 때문이다.
- **클라우드 오브젝트 스토리지는 1차 기본안에서 제외**한다 — 외부 계정 생성·유료 결제는 `CLAUDE.md` §8상 **PM 명시 승인 사항**이고 1차 데이터 규모 대비 부담이 크다. 필요하면 2차 전 별도 안건으로 올린다.
- **2차 착수 전에는 오프사이트를 필수로 전환할 것을 권고**하고, 이를 배포 계획서·운영 가이드에 남긴다. **최종 결정(반출 대상 호스트·암호화 키 보관 주체)은 PM·운영팀 소관** → PM 조치 필요 사항.
- 부수 확인: 회전(일7/주4/월3)은 1차 규모에서 과하지 않다. **백업마다 `pg_restore --list` 성공을 확인**하는 설계(§12.5)는 그대로 유지 요청 — 오프사이트가 없을수록 "그 파일이 실제로 읽히는가"가 중요해진다.

**③ O-1 — 운영자의 PostgreSQL 숙련도**
- **현 시점 미확인**(infra I-7-a 연계). devops가 운영팀에 확인한다.
- **"DB 선택을 뒤집을 사유가 아니다"라는 developer 판단에 동의한다.** 배제 제약·부분 유니크가 주는 안전성은 숙련도와 교환할 성질이 아니고, 백업·복구는 `backup.sh`/`restore.sh` 뒤로 숨겨져 **운영자가 `pg_dump` 문법을 알 필요가 없다**.
- **대체 확인 수단**: 10-28 복구 리허설을 **운영자 입회 하에, 가능하면 운영자 손으로** 수행한다. 거기서 막히는 지점이 곧 P8 운영 가이드에 더 써야 할 내용이다. 미숙련으로 판명되면 리허설 1회 추가 + 가이드 상세화(+0.25작업일)이며 **devops 일정 안에서 흡수 가능**하다. 설계·일정 변경 사유가 아니다.

### Q-7 — §11.2 일정 차이(약 5작업일)에 대한 의견

**ⓐ(기준 오픈일 11-06 사용)에 동의한다. 조기 오픈 10-29는 devops 관점에서도 권고하지 않는다.**

근거는 작업량이 아니라 **직렬 의존성**이다. 조기 오픈 경로에서는 10-26~10-29 **4일 안에** 도메인 연결 → 인증서 발급·검증 → SPF/DKIM 반영(DNS 전파 대기) → 환경 변수·시크릿 주입 → 배포 리허설 → **복구 리허설(G7a 통과 조건 SC-6)** → 운영 배포 → 스모크가 전부 직렬로 들어간다. **DNS 전파나 인증서 발급이 한 번 실패하면 흡수할 여유가 0**이고, 하필 그 구간에 게이트 통과 조건이 걸려 있다. 기준일 11-06이면 11-02~11-05가 같은 사고를 흡수한다.

**G7a(10-30)까지 devops 작업과 소요** — 설계서 §11.1 #12의 1.5작업일은 developer의 *스크립트 작성*분이며 아래와 중복되지 않는다.

| 작업 | 소요(작업일) | 창 | 선행 조건 |
|---|---|---|---|
| 배포 계획서 작성 + developer·qa 리뷰 반영 | **1.0~1.25** | 10-19~10-21 | 기술 설계 승인 |
| 운영 nginx server 블록 확정 → 운영팀 협의·반영 | **0.5~1.0** (+운영팀 대기) | 10-19~10-26 | **I-2-a·b·c 회신** |
| 스테이징 수령 → 앱 스택 기동 → **TLS·접근 제어 선행 구성**(#2·#11) | **0.5~0.75** | 10-13~10-15 | 운영팀 스테이징 제공 |
| 도메인 연결·인증서·SPF/DKIM | **0.5~1.0** (+DNS 전파 최대 24~48h) | 10-26~10-28 | **V-1 도메인 10-16**, **PM DNS 변경 승인** |

| **합계** | **3.75~5.5** | 10-19~10-30 (가용 9작업일) | — |

**일정 자체는 성립한다.** 리스크는 전부 **선행 확보 항목**에 있다.
1. **I-2-a~d 회신** — 없으면 nginx 블록을 확정할 수 없다(devops가 10-09까지 추적).
2. **서버 접근 경로와 소스 반입 수단(I-6 미회신)** — §12.1이 "서버에서 릴리스 태그를 체크아웃해 빌드"를 전제하는데 **프로젝트 저장소에는 아직 원격이 없다**(원격 생성·push는 `CLAUDE.md` §8상 PM 승인 사항). 원격을 두지 않는다면 태그 스냅샷을 아카이브로 반입하는 방식이 대안이며, **어느 쪽인지 10-16까지 정해져야** 배포 계획서에 명령 단위로 쓸 수 있다 → **PM 조치 필요 사항**.
3. **V-1 도메인(10-16)** — 미확보 시 계획서 §5·제약 C-4에 따라 **1차 운영 배포 불가**. 임시 주소 오픈은 PM 결정 사항이다.

**§11.2 흡수 방안 ⓑ에 대한 의견**: 검증 도구 중 **⑨(실패 주입)는 1차 필수라는 developer 판단에 devops도 동의한다** — 백업 실패 알림(REQ-N-032 ③)·파기 실패 알림(REQ-N-038)·SMTP 실패(REQ-N-037)는 **실패 주입 없이는 "확인했다"고 보고할 수 없는 항목**이고, 그 3건이 곧 G7a와 운영 인계의 신뢰성이다. ⑦(로그인 세션)의 2차 이월에는 이견이 없다.
