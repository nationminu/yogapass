# 리뷰: 기술 설계서 v0.2 — devops (R2)

## 1. 총평

**R1 지적 15건(Must 2 · Should 9 · Could 4)이 전건 반영됐고, 미해결·부분 미해결은 0건이다.** 특히 Must #1은 권고한 "스케줄러 일원화"를 그대로 채택해 **실행 주체 → 무결성 확인 → 회전 → `core_jobrunlog` → 실패 시 `mailer_outbox` → 일일 요약**까지 한 경로로 이어졌고(§12.5.1), Must #2는 `auth_basic` + 출처 IP 제한 + **`QA_TOOLS_ENABLED` 마스터 스위치 + 검증 도구 HTTP 노출 0**의 4중으로 닫혔다(§3.5.1·§10.6). R1에서 "설계 문구 몇 줄"로 닫힌다고 본 항목들이 오히려 **절차·리스크·검증 경로까지 붙어서** 돌아왔다(2.5단계 스케줄러 정지, 이미지 보존 3중, 다운타임 60초 목표와 5분 롤백 룰, `.env` 재발급 가능성, TR-13·14·15 신규 등록). **배포·운영 관점에서 이 설계는 그대로 P7 배포 계획서의 입력이 된다.**

**남은 것은 신규 지적 3건이고 전부 Should다 — 게이트를 막지 않는다.** 셋 다 **이번 반영이 서로 교차하면서 생긴 운영 문제**이고, 문서 한 줄 또는 스크립트 조건 하나로 닫힌다.

1. **배포 직전 백업이 조용히 건너뛰어질 수 있다** — Must #1(어드바이저리 락)과 Should #6(2.5단계 스케줄러 정지)의 순서가 어긋나 있다. `# IRREVERSIBLE` 마이그레이션의 안전망이 무음으로 사라지는 경로다.
2. **백업 "미실행"은 2중 통지 어디에도 걸리지 않는다** — 실패는 잡지만 *안 돈 것*은 못 잡고, 통지 2중이 `scheduler` 한 컨테이너에 함께 얹혔다.
3. **`auth_basic` 예외 0건과 `/healthz` 호출 주체가 충돌한다** — 그대로 두면 스테이징에서 매일 `/healthz` 오탐이 나고, **`deploy.sh` 5단계가 401을 받아 자동 롤백이 오발동**한다(10-17 스테이징 배포 1회에서 바로 터진다).

**Q-11(스테이징 선행 조건 4건)은 §6에 답했다 — 조건 2(devops 책임분)는 성립하지만 조건 1과 I-2-b 회신에 묶여 있어 devops가 단독으로 보장할 수는 없다.** 그래서 **운영 nginx를 기다리지 않고 10-15를 달성하는 경로**를 함께 제시했다(로컬 `proxy` 프로필 재사용).

## 4. 지적 사항 (신규 5건 — Should 3 · Could 2)

| # | 위치 (문서·절·ID) | 등급 | 내용 | 제안 | 처리 결과 (Owner 기입) |
|---|---|---|---|---|---|
| 1 | `04_tech-design.md` §12.2 0~2.5단계 · §3.3 어드바이저리 락 · §12.5.1 (REQ-N-033 · §12.4 롤백 전제) | **Should** | **배포 직전 백업이 조용히 건너뛰어질 수 있다.** v0.2에서 ⓐ 모든 관리 명령이 **작업 이름 기준 어드바이저리 락**을 잡고 중복 시 `status=skipped`로 **정상 종료**하게 됐고(§3.3), ⓑ 스케줄러 정지는 **2.5단계**로 백업(1단계)보다 **뒤**에 있다. 따라서 03:00 정기 `run_backup`이 도는 중에 배포가 시작되면 1단계 `run_backup --label pre-deploy`가 **락에 막혀 `skipped`로 끝나고, 스크립트는 실패로 보지 않으므로 배포가 그대로 3단계 마이그레이션까지 진행**된다. 하필 그때 `# IRREVERSIBLE` 마이그레이션이면 **§12.4가 규정한 유일한 복구 수단("배포 직전 백업으로 DB 복구")의 전제가 없는 상태로 파괴적 변경이 적용**된다. 배포 창 권고가 "23:00 이후"(§12.2)라 03:00과 겹칠 여지가 실제로 있다 | **① 절차 순서를 바꾼다** — `0) 사전 점검 → 0.5) 스케줄러 정지 → 1) 백업 → 2) 빌드 → 3) 마이그레이션 → 4) 기동`. 현재 2.5단계를 0.5단계로 앞당기면 정기 작업과의 경합 자체가 사라지고, 정지 구간이 빌드 시간만큼 늘 뿐 §12.2가 이미 적은 "정지 구간 무해" 근거(1분 주기 + 재실행 안전)가 그대로 적용된다. **② 라벨 백업은 `skipped`를 성공으로 취급하지 않는다** — 라벨이 붙은 실행(`pre-deploy`·`pre-restore`)은 락 충돌 시 **대기 후 재시도하거나 비정상 종료**하고 `deploy.sh`는 이를 **배포 중단 사유**로 처리한다. ①만으로 닫히지만 ②는 `restore.sh`(§12.5.3 ⓒ)에도 같은 구멍이 있어 함께 권한다 | |
| 2 | `04_tech-design.md` §12.5.1 ⑤⑥ · §3.3 일일 요약 ⓒ (REQ-N-032 ③) | **Should** | **백업이 "실패"가 아니라 "실행되지 않은" 경우는 2중 통지 어디에도 걸리지 않는다.** v0.2의 통지 경로는 둘 다 **실행이 일어난 뒤의 결과**에 의존한다 — ⑤는 `run_backup`이 돌다가 실패해야 아웃박스에 넣고, ⑥은 `core_jobrunlog`의 기록을 읽는다. supercronic이 트리거하지 못했거나(컨테이너 unhealthy·정지, 배포 중 정지 구간, crontab 오설정) 락 경합으로 `skipped`된 경우 **`core_jobrunlog`에 `failed`가 없으므로 "이상 없음"으로 보인다.** 게다가 v0.1에서는 백업과 알림이 서로 다른 컨테이너였는데 v0.2에서는 **`run_backup`·`send_outbox`·`report_failures`가 전부 `scheduler` 한 컨테이너**에 얹혔다 — `scheduler`가 죽으면 **백업도 안 돌고 그 사실을 알릴 메일도 안 나간다**(§3.4가 스스로 적었듯 `unless-stopped`는 unhealthy를 재시작하지 않는다). ## 6. §16 Q-11 회신 — §12.6.2 선행 조건 4건이 devops 일정에서 성립하는가

> **질의**: 스테이징 제공 10-13 / TLS·`auth_basic` 10-15 / 구현 배포 가능 10-16 / `run_backup` 10-16. 특히 **10-15 TLS 선행 구성**이 R1 Q-7 작업표(10-13~10-15, 0.5~0.75작업일)와 맞는가.

### 결론

**조건 2(devops 책임분)는 성립한다. 단 조건 1과 I-2-b 회신에 묶여 있어 devops가 단독으로 보장할 수는 없다.** 아래 ⓑ 우회 경로를 쓰면 **운영팀 nginx 회신을 기다리지 않고 10-15를 지킬 수 있다.**

| 조건 | 책임 | devops 판단 | 근거 |
|---|---|---|---|
| **1. 스테이징 환경 제공(자원·포트·호스트명) — 10-13** | 운영팀·devops | **⚠ 보장 불가 — 외부 의존** | 스테이징 제공은 I-2 계열과 함께 **운영팀 미회신**(§14.3 O-2)이다. devops가 **10-09까지 추적**하고 미회신이면 PM 조치 필요 사항으로 올린다. **날짜를 지어내지 않는다** |
| **2. 스테이징 TLS + `auth_basic` — 10-15** | **devops** | **○ 성립한다 (조건 1이 10-13에 서는 경우)** | R1 Q-7 작업표의 "스테이징 수령 → 앱 스택 기동 → TLS·접근 제어 선행 구성 **0.5~0.75작업일 / 창 10-13~10-15**"가 그대로 유효하다. v0.2가 `auth_basic`·IP 제한·`X-Robots-Tag` 2중을 추가했지만 증분은 **`.htpasswd` 생성 + 계정 전달 절차 ≈ +0.1작업일**로 **0.75 상한 안에서 흡수**된다. **결정적으로 사설 인증서(self-signed)를 쓰므로 발급·검증 대기가 0이다** — 도메인(10-16)·CA 발급에 묶이지 않는다(R1 #11 → §12.6.2 반영분) |
| 3. 구현이 배포 가능(§11.1 #12 완료) — 10-16 | developer | **devops가 판단할 사안이 아님** | 다만 #12가 **14개 작업 중 12번째(2.0~2.25작업일)** 라 §11.2/PM-1(일정 차이 약 6작업일)이 그대로 이 조건의 리스크다. **PM-1이 ⓐ로 결정되지 않으면 조건 3이 가장 먼저 깨진다**는 점을 pmo에 함께 보고할 것을 권한다 |
| 4. `run_backup` 구현 완료 — 10-16 | developer | **동상** | 백업분만 ⓑ로 떨어지는 분기 처리(§12.6.2 표)가 이미 있어 설계적으로는 안전하다. **로컬 `backup` 프로필로 10-15 이전에 선검증**한다는 v0.2 문장이 이 조건의 실질 위험을 크게 낮춘다 |

### 보완 — 조건 2를 I-2-b에서 떼어 낸다 (devops가 실행한다)

조건 2에는 숨은 의존이 하나 더 있다: **스테이징 TLS·`auth_basic`을 "기존 nginx의 스테이징 server 블록"으로 세우면 I-2-b(설정 수정 권한·반영 절차)가 선행**되어야 한다. I-2-b는 미회신이고 회신 기한이 10-09라, **회신이 늦으면 devops 책임분인 조건 2가 devops 잘못 없이 깨진다.**

- **ⓐ 기본안**: 기존 nginx에 스테이징 server 블록 추가(§12.3 샘플 `yogapass-stg.conf.sample`). I-2-b 회신 후 진행.
- **ⓑ 우회안(권고 — 10-15 사수용)**: **스테이징에 한해 `proxy` 프로필을 켜서 우리 compose 안의 nginx로 TLS·`auth_basic`을 종료**하고 별도 포트로 노출한다. 운영 nginx에 **손대지 않으므로 I-2-b 회신 전에도 즉시 가능**하고, §3.2.1이 이미 만들어 둔 `deploy/nginx/local.conf`와 지시어 집합이 같아 **추가 제작이 사실상 0**이다. §3.2.1의 판정 정의상 `proxy`는 "override에서 정의되고 프로필로 켜는 환경 전용 보조 서비스"이므로 **REQ-N-034 판정에도 어긋나지 않는다.**
  - 이 경우 §13 #6(프록시 뒤 실제 IP)은 **우리 nginx 기준 실측**이 되므로, 기존 nginx로 편입한 뒤 **`TRUSTED_PROXY_COUNT`를 한 번 더 확인**해야 한다(1홉 → 2홉으로 바뀔 수 있다). 이 재확인을 devops가 배포 계획서 체크리스트에 넣는다.
  - **ⓑ는 설계 변경 요구가 아니라 devops의 환경 구성 선택이다. developer는 아무것도 바꾸지 않아도 된다.**

### 추가 소요와 흡수 가능성

v0.2가 P5 창 안으로 당긴 **10-17 스테이징 배포·롤백 1회**, **10-20 백업 실패 주입·회전 확인**은 실행 주체가 qa·developer지만 **환경 제공·입회는 devops**다. 증분은 **+0.25작업일**(배포 1회 입회 + 롤백 확인)로 보며, R1 Q-7 합계 **3.75~5.5작업일 / 가용 9작업일** 안에서 흡수된다. **devops 일정 재산정은 필요 없다.**

### devops가 약속하는 것 / 약속할 수 없는 것

- **약속한다**: 조건 1이 10-13에 서면 **10-15까지 스테이징 TLS + `auth_basic` + `X-Robots-Tag` 구성 완료.** I-2-b가 늦으면 **ⓑ 우회안으로라도 10-15를 지킨다.**
- **약속할 수 없다**: 조건 1(운영팀 스테이징 제공) 자체. **10-09까지 회신이 없으면 PM 조치 필요 사항으로 올리고, 10-13을 넘기는 즉시 §12.6.2 규칙대로 ⓑ(G7 이월) 전환을 pmo에 보고**한다 — 이 판단 기준과 전환 규칙이 v0.2에 문서화된 것이 가장 큰 소득이다.

- 신규 Should 3건은 **이번 반영의 교차 지점**에서 생긴 것으로, 합계 0.1작업일 미만이며 **구현 착수를 막지 않는다.** 다만 **#3(`/healthz` 호출 경로)은 10-17 스테이징 배포 전 반영이 필요**하다 — 미반영 시 401로 배포 확인이 실패해 **자동 롤백이 오발동**한다.
