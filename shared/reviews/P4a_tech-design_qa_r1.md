# 리뷰: 기술 설계서 v0.1 — qa (R1)

> **검토 범위(검증 관점)**: 검증 지원 도구 ①~⑩의 환경 요건 충족도 · 로컬 http/운영 HTTPS 차이의 판정 실행 가능성 · SMTP 미연결 상태의 메일 판정 · Safari·iOS 검증 수단 · **1차 판정 모수 96건(Must 60)의 P5 판정 가능성** · 성능·접근성 측정 조건(§5.0 M-1·M-2) 성립 여부 · 운영에서 검증용 설정 차단의 판정 수단.
> **문서 검토만 수행했다.** 테스트 도구 설치·실행, 코드 작성, 명령 실행은 하지 않았다(현재 `developer/site/`는 비어 있어 실행 검증 자체가 불가능하다).
> **판단 기준 한 줄**: "이 설계대로 구현되면 P5에서 다툼 없이 Pass/Fail을 찍고 증거를 남길 수 있는가."

## 1. 총평

검증 관점에서 **이 문서는 지금까지 받은 P4 산출물 중 가장 검증 친화적**이다. 요구사항 §5.3 말미의 검증 환경 요건 10항목을 **버리지 않고 전부 작업 단위로 산정(2.7~3.2작업일)** 했고, 특히 ④(항목별 독립 토글 — `QA_RETENTION_MINUTES__INQUIRY` + `QA_RATE_LIMIT_MODE` 조합 명시)·⑨(실패 주입 3종 독립 토글)·⑩(`core.clock.now()` 단일 진입점을 1차에 선반영)은 **qa가 요구한 형태 그대로**다. §13(로컬/운영 차이 10건의 판정 단계 구분)은 qa가 테스트 계획에 쓰려던 표를 developer가 먼저 만들어 준 것에 가깝다. 이 세 가지만으로도 P5 판정 불가 항목이 크게 줄었다.

막는 것은 **3건**이고 셋 다 "설계 사상"이 아니라 **판정 기준·판정 시점의 공백**이다. ① REQ-F-042가 수용 기준에서 **"실제 응답 형태(상태 코드·본문)를 P4 기술 설계에 기록하고 P5는 그 값으로 판정한다"** 고 명시했는데 그 표가 없다 — 1차 유일한 쓰기 경로(문의 폼)의 실패·차단 응답을 판정할 기준이 없다. ② REQ-N-034(Must)의 수용 기준은 "앱·DB·**프록시**가 모두 뜬다 / 세 환경의 **서비스 구성이 동일**하고 구조적 차이 0건"인데 §3.2의 구성은 로컬에 proxy·backup이 없고 운영에 mail이 없다 — **문면대로 판정하면 1차 Must 1건이 Fail**이다. ③ 1차 Must인 REQ-N-032·033의 실행 시점(§12.6 10-26~10-28)이 **P5 창(10-15~10-21) 밖**이라 G5 시점에 미검증으로 남는다.

나머지는 모두 "한 줄~한 표 추가"로 끝나는 Should다. Must 3건이 해소되면 **승인**으로 전환한다. 다만 §11.2의 일정 차이(약 5작업일)는 **구현 지연이 P5 창을 그대로 잡아먹는 구조**라 qa로서도 ⓐ(기준 오픈일 11-06 사용)를 지지한다(Q-7).

## 2. 이전 라운드 지적 확인 (R2 이상)

R1이므로 해당 없음. 다만 P2 리뷰에서 qa가 올린 요구(환경 요건 ④·⑦·⑧·⑨·⑩ 신설)의 반영 여부를 §3 체크리스트에서 확인했다.

## 3. 검토 관점 체크리스트

**(2) 로컬 http / 운영 HTTPS 차이** — §13의 10건 구분(로컬 재현 불가 → 스테이징 5건 / P7 4건 + 정적 확인 1건)은 요구사항 §5.3의 검증 단계 지정과 **충돌 없이 일치**한다. qa는 이 구분을 테스트 계획에 그대로 채택한다(Q-3). 실행 가능성의 전제는 **스테이징이 10-15에 HTTPS로 가용**하다는 것 하나이며, 이 전제가 설계에 명시되지 않았다(Should #6). #6(프록시 뒤 실제 IP)은 qa도 Major 위험으로 동의하나 **재현 절차가 없어 지금 상태로는 TC를 쓸 수 없다**(Should #7).

**(3) SMTP 미연결 상태의 메일 판정** — 반영됐다. §2.5(아웃박스 + 로그 즉시 기록)·§10 ②(Mailpit)·§13 #7(도달·SPF/DKIM은 P7)이 요구사항 §5.3·M-8의 분해("발송 요청·본문·로그 = P5 / 도달·발신 인증 = P7")와 같다. **1차 Must REQ-N-037·REQ-F-045는 P5에서 Mailpit 수신 + 아웃박스 로그로 판정 가능**하다. 다만 운영 SMTP 미연결로 오픈하면 P7 스모크에서 REQ-N-022·REQ-F-045의 운영 판정이 불가해진다 → qa도 §14.3 O-5의 ⓐ(오픈 전 연결)를 지지한다(Should #12).

**(4) Safari·iOS 검증** — **반영되지 않았다.** 설계는 G-9 **구현**(D-13 WebKit 폴백)만 다루고, G3a 게이트 조건 C1의 pmo 권고(**WebKit 자동화 + 실기기 체크리스트 병행**)는 문서에 없다. 자동화로 판정하려면 폴백의 적용 여부가 **관측 가능한 신호**여야 한다 → Should #8. (D-1은 PM 미결정 상태이므로 설계 결함이 아니라 "검증 수단 대응 미기재"로 본다.)

**(5) 1차 96건 판정 가능성** — §6 판정 가능성 점검 결과 참조. **판정 기준·시점 공백 4건(Must 3건이 커버)**, 증거 수단 공백 2건을 찾았다. 그 밖의 1차 Must는 이 설계대로 구현되면 P5 판정 경로가 보인다.

**(6) 성능·접근성 측정 조건(§5.0 M-1·M-2) 성립 여부** — **성립한다.** M-1의 "로컬 프로덕션 빌드"는 §8의 `compose.prod` 미리보기(gunicorn + WhiteNoise 사전 압축 + 해시 캐시 헤더)로 그대로 만들어지고, M-2 대상(1차 공개 화면 전량)은 §6.2의 화면 표와 1:1로 대응한다. 404를 404 상태로 측정(M-2 ③)하는 것도 §6.2의 "실제 404"로 가능하다. 서버 렌더·번들 없음·폰트 self-host는 오히려 90점 확보에 유리하다. 리스크는 하나 — **폴백 폰트 메트릭(§9.4, TR-4)이 수렴하지 않으면 CLS가 성능 점수를 끌어내린다**. 대응 절차가 문서에 있으므로 지적하지 않되, **P4 자체 점검의 1차 측정값을 개발 보고서에 반드시 남겨 달라**(§9.4에 이미 기재됨 — 확인만).

**(7) 운영에서 검증용 설정 차단** — **불충분하다.** §10.6의 3중 장치는 방향은 옳으나 ⓐ `DJANGO_ENV=production`이라는 **단일 값에만 의존**하고(스테이징 `.env`를 운영에 복사하는 사고가 정확히 이 값의 오설정이다) ⓑ `config/qa_settings.py`는 `qa/` 밖이라 `.dockerignore`의 제외 대상이 아니어서 **운영 이미지에 남는다**(§4 디렉토리 구조 대조) ⓒ §10.6이 "P5 체크리스트로 qa에 전달"한다고 했으나 **qa가 밖에서 확인할 수 있는 증거 수단이 없다** → Should #4.

### Q-2 — REQ-F-064의 1차 검증을 "파일 수정 → `seed_content` 실행 → 3곳 반영"으로 판정할 수 있는가

**판정할 수 있다.** 다음 조건을 붙인다.

1. **취지 판정**: REQ-F-064 1차의 취지는 "자주 바뀌는 값이 **소스 본문에서 분리**되어 **한 곳을 고치면 3곳에 일관 반영**되는가"이고, "재빌드"는 그 반영을 일으키는 **수단의 예시**다. `seed_content` 실행은 같은 취지를 더 짧은 경로로 만족하며, **2차 기준("관리자 화면에서 재빌드 없이")과의 구분도 유지된다** — 구분선은 "재빌드 유무"가 아니라 **"관리자 화면에서 고칠 수 있는가"** 이기 때문이다.
2. **증거 요건**: qa는 `content/site.yml`의 전화번호를 바꾸고 → 명령 1회 실행 → **헤더·푸터·오시는 길 3곳의 변경 전후 캡처 + 실행 명령·출력**을 증거로 남긴다(§5.3의 증거 열과 동일). **파일 → DB 단방향**임을 보이기 위해 `qa_show`로 반영된 레코드를 함께 남긴다.
3. **문구 정합**: 수용 기준 문면이 "재빌드"인 채로 두면 **P5 판정 시 문면-실행 불일치가 남는다**. qa는 테스트 계획의 해당 TC에 "판정 수단 = 데이터 파일 값 변경 → 반영 절차(재빌드 **또는** `seed_content`) 실행"을 명시하고, planner에게 REQ-F-064 1차 수용 기준의 문구 정렬을 요청하는 것을 권고한다(오케스트레이터 경유 — qa가 직접 타 팀 문서를 고치지 않는다). **정렬이 안 돼도 1·2의 근거로 Pass 판정은 가능하다.**
4. (추가) 이 절차는 **운영 가이드(REQ-N-026)의 "콘텐츠 수정 절차"** 와 같은 것이어야 한다 — 명령 실행이 필요하다는 사실을 운영 가이드에 적어야 고객이 오해하지 않는다.

- P5 창은 **10-15~10-21(5작업일)** 인데 여기서 판정할 것은 **96건(Must 60)** + §5.3의 화면 밖 검증 34건 + 스테이징 전용 항목이다. 구현이 하루 밀리면 **P5 창이 그대로 하루 줄어든다** — 검증은 구현 뒤에만 설 수 있기 때문이다.
- 범위 축소(ⓓ)는 검증 관점에서도 반대다. **1차 Must 60건은 G5 판정 모수 자체**라 줄이려면 CR이 필요하다.
- **ⓑ(검증 도구 이월)에는 조건부 동의**한다: **⑦ 본체(로그인 세션)는 2차 이월 동의**(1차에 로그인 화면이 없다), **⑧의 2차 시드(슬롯 400·예약 200·상담 100)도 이월 동의**. 반면 **⑧의 1차분(문의 동시 제출·빈도 제한 재현)은 REQ-F-046 ② 판정에 직접 쓰이므로 이월 불가**이며, **④·⑨·⑩이 1차 필수라는 developer 판단에 전적으로 동의**한다. 이 셋이 빠지면 1차 Must 중 최소 5건(REQ-N-019·032·037·038 + REQ-F-046)이 판정 불가가 된다.
- ⓒ(Could 3건 제외)는 검증 부담을 거의 줄이지 못한다. 덧붙여 **REQ-N-030(JS 없는 폼 제출, Could)은 이 설계에서 사실상 이미 충족**된다(§9.5 "JS 없이 제출해도 동일하게 동작한다") — **제외하지 말고 Pass로 가져가는 편이 이득**이다.
- **지적 #3(Must)과 함께 볼 것**: 일정이 밀리면 가장 먼저 희생되는 것이 스테이징 배포·롤백·백업 항목이고, 그것이 곧 G5 미검증 Must 2건이다.

### Q-8 — 1차 96건 중 이 설계로 충족 경로가 보이지 않는 항목

**§6에 표로 정리했다.** 요약하면 **판정 기준·시점 공백 4건**(REQ-F-042 / REQ-N-034 / REQ-N-032 / REQ-N-033 — 지적 #1~#3), **증거 수단 공백 2건**(REQ-N-020 / REQ-N-019의 사용량 알림 — 지적 #9·#11), **수단 미결 1건**(REQ-N-003 Safari — 요구사항이 "미검증" 보고를 허용하므로 Block 아님 — 지적 #8)이다. **구현 자체가 불가능해 보이는 1차 Must는 0건**이다.

### Q-5 (devops 대상) — qa 관점 코멘트

`proxy_intercept_errors off`는 **REQ-F-060(1차 Must, 실제 404)·REQ-F-065의 판정 전제**다. 기존 nginx 정책과 충돌해 적용할 수 없다면 **"앱의 404·500 화면이 nginx 기본 화면으로 대체된다"는 사실 자체가 결함**이 되므로 P5 전에 결론이 필요하다. 별도 로그 파일은 **REQ-N-039의 접근 범위 판정**에 영향을 준다 — 공유 로그면 qa가 보게 되는 범위가 다른 서비스까지 넓어져 오히려 권한 문제가 생긴다.

### Q-6 (devops 대상) — qa 관점 코멘트

백업 파일의 **보관 위치·퍼미션·오프사이트 여부는 REQ-N-039 1차 수용 기준의 판정 대상**이다(지적 #13). qa는 **배포 계획 문서를 증거로 인용**해 판정하므로 P5 시작 전에 초안이라도 존재해야 한다. O-1(운영자 숙련도)은 검증 자체에는 영향이 없으나 **복구 리허설의 소요 시간 기록**(REQ-N-032 증거)에는 영향을 준다.

## 7. 요약

- Must: **3건** · Should: **10건** · Could: **3건**
- 판정: **수정 요청**
- **Must 3건은 모두 "기준·시점" 문제**이고 설계 사상을 바꾸지 않는다. #1은 표 1개 추가, #2는 compose 프로필 추가 또는 수용 기준 정렬 합의, #3은 스테이징 1회 실행을 P5 창 안으로 당기는 일정 합의다. 3건이 해소되면 **승인**으로 전환한다.
- 검증 환경 요건 10항목은 **④·⑨·⑩을 포함해 사실상 전부 반영**됐다. qa가 P2부터 요구해 온 항목이 P4 설계에 작업 단위로 들어온 것은 이 프로젝트에서 처음이며, **1차 판정 가능성이 실질적으로 확보된 주된 이유**다.
- **구현 자체가 불가능해 보이는 1차 Must는 0건**이다.
