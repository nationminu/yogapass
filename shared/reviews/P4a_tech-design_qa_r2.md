# 리뷰: 기술 설계서 v0.2 — qa (R2 · 범위를 좁힌 확인 검토)

> **검토 범위(지시받은 것만)**: ① R1 지적 16건(Must 3 · Should 10 · Could 3)의 처리 결과 열 ↔ v0.2 원문 대조 ② developer Q-10 답변 ③ 그 반영으로 **새로 생긴 검증 문제만** 추가 지적 ④ 1차 96건(Must 60) 중 **판정 불가 항목 재집계**.
> **문서 전체 재검토는 하지 않았다. 테스트 도구 설치·실행, 명령 실행, 코드 작성은 하지 않았다**(지시대로). `developer/site/`는 여전히 비어 있어 실행 검증 자체가 불가능하다.
> **판단 기준 한 줄**: R1과 같다 — "이 설계대로 구현되면 P5에서 다툼 없이 Pass/Fail을 찍고 증거를 남길 수 있는가."

## 1. 총평

**Must 3건은 전부 해결됐고, 해결 방식이 qa가 요구한 형태 그대로다.** ① §9.6은 요청한 6행 × 5열 표에 **판정 주의 5건**까지 붙어 있어 P5 문의 폼 TC의 기대값을 **표에서 그대로 복사해 쓸 수 있다**(Q-12 = 확정 가능). ② 로컬 `proxy`·`backup` 선택 프로필은 부수 효과가 컸다 — §13의 스테이징 의존 항목 중 #6(프록시 IP)·#9(404·502)·#11(HTML 압축)이 **로컬 선검증 가능**으로 내려와, TR-14(스테이징 지연)가 현실화돼도 판정 경로가 통째로 사라지지 않는다. ③ §12.6.2는 일정을 당긴 데서 그치지 않고 **선행 조건 4건 + 깨질 때 ⓑ로 전환하고 pmo에 보고하는 규칙 + PM-5 승격**까지 갖췄다 — qa가 R1에서 요구한 "합의 없이 미검증으로 남기지 않는다"가 문서화됐다. Should 10건·Could 3건도 **전건 반영, 미반영 0건**이며 반영 위치를 원문에서 모두 확인했다.

**막는 것은 0건이다.** 새로 지적하는 5건은 전부 Should이고 **어느 것도 P5 판정을 불가능하게 하지 않는다** — 판정은 되지만 "근거가 한 줄 약하거나, 실행 중에 qa가 임의 해석을 해야 하는" 수준이다. 가장 실질적인 것은 **#2(스테이징 필수로 확정한 Mailpit이 운영에는 뜨지 않게 하는 수단이 없다 — 스테이징·운영이 같은 override를 쓴다)** 와 **#4(③ honeypot ↔ ⑤ 토큰 재사용은 로그가 유일한 구분 증거인데 로그 조회 수단·형식이 도구 규격에 없다)** 다. 둘 다 한두 줄 추가로 끝난다.

**판정 불가 항목은 0건이다.** R1의 6건(판정 불가 4 + 증거 수단 부족 2)이 전부 해소됐고 남은 것은 "조건부 판정 4건"(REQ-N-032·033·039 + REQ-N-003의 실기기분)인데 **넷 다 조건이 문서에 명시돼 있고 깨질 때의 보고·이월 경로가 정의돼 있다** — 즉 G5에서 "미검증"이 아니라 "이월(사유·합의 포함)"로 보고할 수 있다. **판정: 조건부 승인.** Should 5건은 구현 착수를 막지 않으므로 v0.3 또는 구현 중 반영으로 충분하며, qa는 이 문서로 테스트 계획·케이스 작성에 착수할 수 있다.

## 5. §16 확인 요청에 대한 답변 (qa 대상 Q-9 · Q-10 · Q-12)

### Q-9 — §3.2.1의 "세 환경 동일 구성" 판정 정의로 REQ-N-034를 Pass 판정할 수 있는가 / planner 문구 정렬이 필요한가

**Pass 판정할 수 있다. planner 수용 기준 문구 정렬 요청은 필요하지 않다.** 판정 절차를 여기서 확정해 둔다(테스트 계획에 그대로 옮긴다).

| 수용 기준 문면 | qa 판정 방법 | 증거 |
|---|---|---|
| "로컬에서 `docker compose up` → **앱·DB·프록시가 모두 뜨고 사이트가 동작한다**" | 문서에 적힌 로컬 기동 명령(`--profile proxy`, Should #1 채택 시 플래그 없이)을 실행 → `docker compose ps`에서 `app`·`db`·`proxy` **3개 healthy** → `http://localhost:8080`에서 SCR-001 렌더 + `POST /location` 정상 접수 | `ps` 출력 + 응답 헤더 + 화면 캡처 |
| "세 환경의 compose 정의 차이가 **환경 변수·override에만** 있다(구조적 차이 0건)" | ① `compose.yaml`이 세 환경에서 **동일 파일**임을 확인(저장소상 1개) ② `compose.local.yaml` ↔ `compose.prod.yaml` diff에서 차이가 **override 정의·환경 변수·프로필에만** 나타나는지 확인 ③ **`app`·`db`·`scheduler`가 3환경 모두 존재** | diff 출력 + `ps` 출력(로컬·스테이징) |
| 기준값 "1차부터 운영과 같은 구성(앱·DB·**리버스 프록시·백업**)" | 프록시: 로컬 `proxy` 프로필 ↔ 운영·스테이징 **기존 nginx**(§12.3의 같은 지시어 집합 + 샘플 3종) / 백업: 로컬 `backup` 프로필 ↔ 운영·스테이징 **`scheduler`의 `run_backup`** — **같은 코드·같은 명령**임을 확인 | `run_backup` 실행 로그 + `core_jobrunlog` |

**정렬 요청이 필요 없다고 보는 이유 3가지.**

1. 수용 기준의 취지는 "**로컬에서 운영과 같은 구성으로 띄워 볼 수 있는가**"이고, 프로필은 **구성이 없는 것이 아니라 켜는 방식**이다. §3.2.1이 "로컬은 켤 수 있다(구조가 없는 것이 아니다)"를 판정 정의로 못박았으므로, qa는 임의 완화가 아니라 **문서화된 정의를 인용해 판정**하게 된다.
2. R1에서 우려한 실질 손해(백업 판정의 스테이징 전량 의존)는 **`backup` 프로필로 실제로 해소**됐다 — 문면 충돌이 가리키던 위험 자체가 사라졌다.
3. planner 회귀 경로는 요구사항 개정 → planner 반영 → qa 판정 기준 갱신으로 **팀 3곳·최소 이틀**이 들고 그 기간이 P5 테스트 계획 확정(10-14)과 겹친다. **얻는 것이 문구 한 줄인데 비용이 일정 리스크**라는 §3.2.1의 판단에 동의한다.

다만 **문면-실행 간극 자체를 0으로 만드는 값싼 수단**이 있어 Should #1(`COMPOSE_PROFILES` 기본값)을 제안한다. **채택 여부와 무관하게 판정은 Pass로 가능**하며, 미채택 시 qa는 테스트 케이스에 **"판정 근거 = 기술 설계 §3.2.1 판정 정의"** 를 명시하고 실행 명령 전문을 증거로 남긴다.

### Q-12 — §9.6 표로 REQ-F-042·044·046의 TC 기대값을 확정할 수 있는가 / ④만 429·③⑤ 200 판단에 이견이 있는가 / ③·⑤의 3요소 판정이 실행 가능한가

**세 가지 모두 긍정이다.**

**(1) 기대값 확정 — 가능하다.** 표 6행이 그대로 TC 6개(+파생)의 기대값이 된다. 초안 매핑을 적어 둔다.

| TC(초안) | 입력 | 기대값(§9.6 인용) | REQ |
|---|---|---|---|
| 정상 접수 | 유효 입력 + 동의 | 200 · 성공 블록 · 저장 1 · 아웃박스 1 · `inquiry.created` | REQ-F-041·045·046 |
| 서버 검증 우회 | 클라이언트 검증 우회(빈 값·초과 길이·형식 오류·동의 미체크) | 200 재렌더 · 오류 요약 + `aria-invalid` · **입력 보존·토큰 유지** · 저장 0 · 발송 0 | **REQ-F-042** |
| honeypot | honeypot 필드 채움 | 200 · **성공 화면과 동일** · 저장 0 · 발송 0 · `reason=honeypot` | REQ-F-044 · N-019 |
| 빈도 제한 | 10분 내 6회째 | **429 + `Retry-After`** · 실패(일반) 블록 · 저장 0 · 발송 0 · 카운터 증가 | REQ-F-044 · N-019 |
| 중복 제출 | 같은 `submit_token` 재전송·새로고침 | 200 · 성공 화면 · **저장 총 1건**(`--count-only`) · **발송 총 1건** | **REQ-F-046 ②** |
| 서버 오류 | 강제 예외 | 500 · SCR-009 · 저장 0 · 발송 0(롤백) | REQ-F-065 |

**(2) ④만 429 / ③⑤는 200 — 이견 없다.** §9.6의 설명에 동의하며 qa 관점 근거를 하나 더 든다: REQ-F-044의 수용 기준은 *"저장·발송하지 않고 사용자에게는 **일반 오류만** 표시"*(honeypot)와 *"초과분이 거부되고 **안내 문구가 표시되며 기록이 남는다**"*(빈도 제한)로 **두 경우를 다르게 적고 있다** — 후자는 숨김을 요구하지 않는다. 따라서 **④에 429를 주는 것이 수용 기준과 더 잘 맞고**, ③⑤를 200으로 두는 것도 "차단 사실 미노출"과 충돌하지 않는다. P5에서 "429가 나오면 Fail"이라는 해석이 생기지 않도록 테스트 계획의 기대값 표에 **§9.6을 출처로 인용**하겠다.

**(3) 3요소 판정 — 실행 가능하다.** 단 실행상 유의 2건이 있고 둘 다 qa가 절차로 흡수한다.

| 유의 | 내용 | qa 대응 |
|---|---|---|
| **③ vs ⑤의 구분** | 두 경우는 상태 코드·화면·저장 0·발송 0이 **전부 같고** 로그만 다르다 → **로그 접근·형식이 유일한 구분 증거**다 | 신규 **Should #4**로 요청했다(`key=value` 고정 + 조회 수단 1줄). 미반영이어도 **TC 설계상 원인이 자명**하므로(honeypot을 qa가 직접 채워 보낸다) 판정 자체는 가능하다 — 증거의 강도만 떨어진다 |
| **④ 판정 중 알림 메일 혼입** | §5.3의 사용량 알림 임계를 낮춘 상태(`…_PER_SOURCE_DAY=1`)로 두면 **빈도 제한 TC 실행 중 `rate_limit_alert` 메일이 발생**해 §9.6 ④의 "발송 0건"과 겉보기 충돌한다 | **요건 ④의 항목별 독립 토글 덕에 분리 실행이 가능하다.** 빈도 제한 응답 TC는 알림 임계를 기본값(높게)으로 두고 `kind=inquiry_notify` 0건을 판정하고, 알림 TC는 별도 회차에서 임계를 낮춰 `kind=rate_limit_alert` 1건을 판정한다. `qa_mail_log --kind`가 이미 규격에 있어 그대로 된다 |

추가로 **Should #3(`Retry-After` 값·차단 지속 시간)** 이 확정되면 "429 → 해제 → 200 복귀" TC까지 기대값이 생긴다. 미확정이면 qa는 **헤더 존재와 값 > 0**까지만 판정하고 해제 시점 TC는 쓰지 않는다(누락으로 보고).
